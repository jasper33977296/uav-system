# 029 含 RTL 的任務一律上不去：無座標項的 frame 預設錯

- 嚴重度：**high**（一整類任務不可用）
- 狀態：**closed**（2026-08-12 修復並實測驗證，commit `32943a2`）
- 位置：`apps/command/app/main.py`（`build_items`）、`apps/backend/app/plan_check.py`
- 發現：前端 2026-08-12 回報「建任務時顯式給 command/frame 會被機端拒」

## 症狀

上傳任務時機端回 `MAV_MISSION_UNSUPPORTED`，**整包任務被拒收**。失敗訊息只有
一句「機端拒絕任務」，不指出是哪一項、哪個欄位。

## 根因

`build_items` 對所有任務項一律預設 `frame=3`（`GLOBAL_RELATIVE_ALT`）。但
**無座標的任務項——RTL(20)、CONDITION_*(112–159)、DO_*(176+)——在 MAVLink
慣例裡是 `MAV_FRAME_MISSION`(2)**。QGC 產的 `.plan` 也是這樣寫。

## 這不是「使用者給錯值」

原始回報的歸因是「顯式給 command/frame 會被拒、只給 action 反而成功」。**實際
相反**：`action:"rtl"`（完全不給 command/frame，走我方預設路徑）**同樣失敗**。

也就是說：**任何以返航結尾的任務都上不去。**

回報者當時同時改動了兩個變因（拿掉顯式欄位＋拿掉 RTL 項），因此歸因到錯的那個。

## 教訓

**（1）我們建議的做法，我們自己做不到。** `plan_check` 會對不以返航/降落結尾的
任務發出警告「最後一個導航項不是返航/降落」——**而照著這個建議做出來的任務，
上傳必定失敗**。自我矛盾類的 bug 特別隱蔽：兩邊各自看都合理，只有走完整條路
才會撞上。

**（2）與 028 同一個模式：我方預設值悄悄讓一整類功能不可用。**

| | 028 | 029 |
|---|---|---|
| 錯的預設 | 高度取「主機」而非該台 | frame 一律取 3 |
| 為何長期沒發現 | 單機測試永遠正確、SITL 同址掩蓋 | 沒人用返航結尾的任務走完整條上傳路徑 |
| 表面症狀 | 「未達目標高度」 | 「機端拒絕任務」 |
| 真正範圍 | 所有非主機的起飛序列 | 所有含 RTL 的任務 |

兩案並排的共同點：**預設值是「沒人明確決定過」的決定**，而它一旦錯了，錯的是
一整類情境而不是單一案例。

**（3）使用者以為自己錯了的回報，最容易被打發掉。** 回報者以為是自己用法不對
（「不該顯式給值」），實際是系統缺陷，而且比他以為的嚴重。**當回報聽起來像
「我可能用錯了」時，要特別小心——那正是最容易被歸檔成「使用者教育問題」而
真 bug 存活下來的情境。**

## 修法（兩層，刻意不互相取代）

**第一層 `build_items` 加 `default_frame(cmd)`**——只在**沒給** frame 時依指令
推導（無座標項→2，其餘→3）。**顯式值一律照送、不覆寫**：那是 MAVLink 保真度的
核心（`.plan` 原值原樣送出），偷改成「看起來對」的值會讓保真度承諾失效。

**第二層 `plan_check` 補一條 problem**——顯式 frame 與無座標指令不搭時，**建任務
當下就講**：

    seq 6：command=20 是無座標項，frame 應為 2（MAV_FRAME_MISSION），
    目前是 3——機端會拒收整包任務

第二層存在的理由：第一層的取捨會留下一個洞——**保真度代表我方不偷改，不代表
可以讓使用者盲猜**。錯誤訊息要講清楚「seq 幾、哪個欄位、應為何值、後果是什麼」。

| 案例 | 修復前 | 修復後 |
|---|---|---|
