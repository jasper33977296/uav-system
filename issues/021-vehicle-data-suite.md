# 021 · 機上資料（Vehicle Data）：QGC 式機上全量即時資訊蒐集與檢視

- 狀態：open
- 嚴重度：medium
- 位置：`apps/backend/app/mavlink_rx.py`（解讀層）＋前端新「機上資料」檢視
- 建立：2026-08-12

## 現象

使用者需求：「QGC 能蒐集無人機本身的即時資訊，我要在我們系統上也做一套」——
不只訊號事件，是機上全量即時資訊。

## 原因（現況差距）

QGC 的能力＝遙測串流＋tlog 側錄＋MAVLink Inspector（全訊息型別即時清單）＋
參數檢視＋感測健康＋機上 ulog 下載。我們的底子：原始層全量收集（014 capture）
與遙測入庫已有——缺**解讀層**（通用解碼）與**呈現層**（Inspector 式檢視），
以及參數/ulog 兩條協定。

## 修法建議（PM scope 定案 2026-08-12，分四期）

1. **Phase 1（本期）**：014 Phase B 通用解碼——單埠流每型訊息 generic decode，
   per-機登錄表（型別/頻率/最新欄位值）以 1–2Hz 廣播；UI 三層（儀表 IMU→
   事件 log→Inspector 原始）；SYS_STATUS 感測健康位併入。誠實原則：欄位名/
   單位照方言原樣、未知型別顯示 id。
2. **Phase 2**：每架次參數快照（PARAM_REQUEST_LIST 唯讀存檔可查）；
   **只讀不改**，參數編輯維持 QGC 分工。
3. **Phase 3**：機上 ulog 落地自動回收歸檔到架次（MAVLink FTP/log 協定）。
4. **Phase 4**：視需求再議（欄位歷史曲線等）。

排序：多機模擬環境 → IMU 驗收/事件 modal → 本案 Phase 1。
UI 規格由設計師出、走使用者核准流程。

## Phase 2 前置盤點（2026-08-12 實測，動工前的已知條件）

**規模與成本（對 SITL 實測）**
- 每台 **851 個參數**（PX4 1.14 SITL；真機依機型與模組數略有出入）。
- 全量抓取 **約 3 秒**（實測 339 參數/秒，loopback）。資料量約數十 KB
  ——與影像（1.17 GB/飛行小時）差好幾個數量級，**儲存不是問題**。
- ⚠️ 真機 5G 未測：3 秒是 loopback 值，鏈路差時會拉長並與遙測搶頻寬。
  真機階段要重測，必要時改為「連線時抓一次」而非每架次抓。

**回應走哪條路（架構關鍵，會決定由誰發請求）**
PX4 的 PARAM_VALUE **不會回給發請求的人**，而是送到它設定的固定 remote
（多機環境＝fanout → backend/command）。這與 bring-up 時發現的「PX4 不回連線者」
是同一件事。**所以請求必須由 backend 的 `mavlink_rx` 發**——它才收得到回應，
而且它已經有現成的 `_collector` 機制（任務下載用的同一套「送查詢→收集回應」）。
從別的行程發請求會拿不到任何東西（實測：從臨時 socket 發，851 筆全進了 backend）。

**read-only 邊界要動一行（需明示決策）**
`mavlink_rx.SEND_WHITELIST` 目前只有三個任務下載用的訊息。Phase 2 需要加入
`PARAM_REQUEST_LIST`（與可能的 `PARAM_REQUEST_READ`）。這**符合**既有邊界定義
（「不含改變機上狀態的能力」——參數查詢是唯讀），但白名單就是用來讓這種擴充
被看見的，所以要在 commit 明講、不可順手加。**`PARAM_SET` 永遠不得加入**
（參數編輯維持 QGC 分工）。

**儲存策略建議：內容雜湊去重，而非每架次存一份**
參數在飛行之間**通常不變**，每架次存 851 筆全量會累積大量重複。建議：
參數集算內容雜湊，同一組只存一份，架次只記雜湊參照＋（若有）與前一組的差異。
這樣「可重現性」（知道當時到底設了什麼）與「不囤重複資料」兩者兼得。
變更偵測可搭 PX4 主動送的 PARAM_VALUE（改參數時會廣播）。

**未定**：抓取時機（連線時 vs 每架次 arm 時）、真機 5G 的耗時、UI 呈現
（設計師規格）。

### Phase 2 定案（2026-08-12，使用者裁決＋PM 核可）

1. **抓取時機：連線時抓一次 ＋ 改參數時自動更新**（不在 arm 當下抓——那一刻的鏈路
   要留給操作員，真機 5G 更是）。
   ⚠️ **兩者都要做，只做連線那一次會讓快照說謊**：實際流程常是「用 QGC 調完參數
   再飛」，只做連線抓取的話，調參之後的快照就是過期的舊值——而那恰好是最常發生的
   情境。PX4 改參數會主動廣播 PARAM_VALUE、backend 本來就在收，接上即可。
2. **`SEND_WHITELIST` 加 `PARAM_REQUEST_LIST` / `PARAM_REQUEST_READ`**：符合既有
   邊界定義（唯讀查詢不改變機上狀態）。**要在 commit 訊息明講，不順手加。**
   **`PARAM_SET` 永遠不得加入**（參數編輯維持 QGC 分工）。
3. **內容雜湊去重**：同一組參數只存一份，架次記參照。
   ⚠️ 雜湊要對「參數名＋值」**排序後的正規化序列**做——抓取順序會變（PARAM_VALUE
   是非同步到達），不正規化就會讓同一組設定算出不同雜湊，去重直接失效。
4. **真機 5G 的抓取耗時**列為上機量測項（現場跑部署清單時順手記一筆）。

排序：**排在 022 Phase 2 收尾之後**動工。UI 呈現等設計師規格。
