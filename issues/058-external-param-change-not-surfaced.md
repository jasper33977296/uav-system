# 058 · 別人改了飛控參數，我們的畫面不說——2026-09-21 花了很久才找到

- 狀態：in-progress（**A 完成 2026-09-22**，真機那一輪還沒看到——見〈解決方式〉；B、C 未做）
- 嚴重度：**high**（會把人導向完全錯誤的排查方向；實際損失數小時）
- 位置：`apps/backend/app/mavlink_rx.py`（收 `PARAM_VALUE` 的地方）、
  即時頁的預檢呈現（`SimpleHud.tsx`／`lib/prearm.ts`）
- 建立：2026-09-21

## 現象

2026-09-21：無人機無法解鎖、校正也跑不完。排查花了很久，而原因之一是
**飛控上的參數被我們系統以外的人改過**，我們的畫面完全沒有提示這件事。

畫面上看得到的只有飛控吐出來的預檢字串：

```
PreArm: Vehicle breaching Polygon fence
PreArm: Fences enabled, but none selected
PreArm: Fence requires position
```

而真正的事實是 `FENCE_ENABLE=1`、`FENCE_TYPE=5`、`FENCE_TOTAL=6`、
`FENCE_ALT_MAX=6`——飛控裡存著一個**沒有人記得的六點多邊形**，機子站在它外面。
要知道這件事，得 ssh 上機器、停代理、拿 tlog 或直接問飛控。**畫面一個字都沒說。**

## 原因

1. **我們不記錄參數，所以說不出「它變了」。** `mavlink_rx` 收得到 `PARAM_VALUE`
   （代理開機會讀一輪，地面站要參數時也會走這條），但那些值沒有被留存，
   自然也沒有「上次是多少、誰改的、什麼時候」。
2. **預檢字串被原樣轉出。** `PreArm: Vehicle breaching Polygon fence` 對飛控來說
   是完整的，對操作員來說少了最重要的一半：**哪個圍欄、在哪裡、我離它多遠**。
3. **沒有「這台機的設定和我們以為的不一樣」這個概念。** `set-fc-params.py` 的
   PLAN 表就是我們對這台機設定的主張，但它只在有人手動跑的時候比對一次，
   平常沒有任何地方拿它跟現況對帳。

## 影響

排查方向被帶偏：畫面說「圍欄」，但因為看不到圍欄的內容與自己的相對位置，
第一直覺會往 GPS／定位／校正去猜——而那天確實同時有校正跑不完的問題（059），
兩件事混在一起，更難拆開。

**這類失效會重演**：只要有第二個人碰得到飛控（用 Mission Planner、MAVSDK、
或另一支腳本），而我們既不記錄也不比對，下一次一樣是從零猜起。

## 修法建議

按價值排序，三條可以獨立做：

### A. 參數快照與變更事件（建議先做）

`mavlink_rx` 收到 `PARAM_VALUE` 就存進 DB（`drone_id` + 參數名 + 值 + 時間）。
值與上一筆不同就發一則 `param_changed` 事件進事件流。**這是最小的改動，
而且立刻回答「它是什麼時候變的」**。

注意：代理開機會讀一整輪 1244 個參數，**第一輪不該噴 1244 則事件**——
首次建檔與後續變更要分開。

### B. 拿 PLAN 表對帳

`set-fc-params.py` 的 `PLAN` 已經是「我們主張的設定」。把它做成後端也讀得到的
一份資料，收到參數時比對，不符就在即時頁掛一條「機上設定與預期不同」。
**021（參數快照）與這條是同一族**，可以一起規劃。

### C. 預檢字串加上我方知道的脈絡

畫面顯示 `Vehicle breaching Polygon fence` 時，旁邊補上我們手上就有的資訊：
圍欄型別、頂點數、機目前在圈內或圈外、距離多遠。**不要改寫飛控的原句**
（那是權威），是在它旁邊補。

## 解決方式

### A：參數基準與變更事件（2026-09-22）

`apps/backend/app/param_watch.py`，由 `mavlink_rx` 的 `PARAM_VALUE` 分支餵（一行，只排程不等 DB）。

* **新表 `drone_params`**：每台機每個參數「最後一次確認的值」與確認時刻。
  **存在 DB 不存記憶體**——後端重啟、代理重開之後重讀一輪，**我們不在的時候被改的**
  也比得出來。`param_sets`（021）是**架次**的快照，這張是**機**的現況，兩者分工不同。
* 收到的值先緩衝，**靜下來 2 秒才比對**（一整輪一千多筆約 3 秒，逐筆比會在讀到一半就開始報）。
* **第一次建檔只發一則** `param_baseline`（「記下 N 個參數，之後變了才說得出來」），
  不發 1244 則——本案原文的提醒。
* **沒有基準時先借上一趟的架次快照**（實作時加的）：否則真機第一次連上只能建檔，
  **上一趟飛完到現在被改的看不出來**——而 09-21 那個圍欄正是飛與飛之間被改的。
  借來的事件標 `compared_to: session_snapshot`，畫面說「對照上一趟 9/22 14:49 解鎖時的快照」，
  與「我們一路看著的舊值」分開講。
* **值變了**發 `param_changed`：舊值 → 新值、**上次確認舊值的時刻**（變更發生在那之後、
  這次讀到之前；**確切時間不知道就不編一個**）。
* **是不是本系統改的**：查 `command_log` 裡這段期間 accepted 的 `param_set`，
  **名字與值都要對上、而且在上次確認之後**才算。值取 `detail.written`（讀回確認過、
  含飛控夾值的結果），**不是 `params`**——實測 `params` 裡混著呼叫端的 `why: "fc_fence"`，
  直接比會把非參數名當參數。對不上就說「**不是經由地面站的指令服務**」而不說「別人改的」：
  機上的 `set-fc-params.py` 也是我們的，它直接寫飛控、不經過指令服務。
  本系統改的是 info，其餘是 warning。
* 一次變超過 10 個 → 一則 `params_changed` 彙總（帶清單與其中幾個不是經由指令服務）；
  以前沒見過的名字 → `params_added`（多半是韌體更新）。
* **先發事件、再寫基準**：第一版反過來，事件寫入失敗時新值已成「已知」，那個變更就
  **永遠不會被說出來**——e2e 測試翻出來的。現在事件失敗就不動基準，下一輪再報一次
  （重複一則比漏掉一則好，同 057）。
* NaN：快照是 JSONB，NaN 存成 null；借快照當基準時 null 對 NaN 算相同，
  不然每個 NaN 參數都會被報成變了。

前端 `evText`：「參數 FENCE_ALT_MAX：100 → 6（不是經由地面站指令服務；上次確認舊值是 9/22 15:10）」。

### 驗證

| | 結果 |
|---|---|
| `scripts/test-param-watch.py`（容器內，純邏輯）| ✅ 比對、float32 表示差、NaN／null、歸因（值不對不算、上次確認之前的寫入不算）、`written_of` 用實際紀錄的形狀 |
| 對真 DB 的端到端（暫時的機體記錄，跑完刪）| ✅ 1246 筆只發一則建檔；**清掉記憶體模擬後端重啟**，重讀比得出 2 個變更；沒變不再說；12 個併一則；新參數另一則；**事件寫入失敗的那一輪下一輪會再報** |
| 借快照當基準（暫時的架次＋快照，跑完刪）| ✅ 不發建檔、比得出上一趟之後被改的 `FENCE_TYPE`、標明對照快照、NaN 不誤報 |
| 歸因對真的 `command_log`（唯讀）| ✅ 2026-09-14 #783 對到 `FENCE_TYPE`（修正前對到的是 `why`）|
| 畫面（headless Chrome，資訊頁）| ✅ 四種事件都是人話 |

**沒驗到的：真飛控讀一輪。** 做這條時機上的代理被人**手動停掉並 disable**
（2026-09-22 14:49，從 `192.168.142.201` 在 `~/hct/qoe` 下的 `sudo systemctl stop/disable uav-agent`
——別的工作，沒有去動），地面站收不到 MAVLink。SITL 的 sysid 1 會與真機撞號（038），沒有開。
**驗收方式**：代理恢復後第一次連上，事件流應該出現的是對照 9/22 14:49 那一趟快照的
`param_changed`（有變的話）或什麼都沒有，**而不是** `param_baseline`；
`SELECT count(*) FROM drone_params WHERE drone_id = <那台>` 應為 1244。
