# 039 · 全自動飛行的狀態機與安全守門

- 狀態：**needs-decision**（設計已出，逐條待核可後才實作）
- 嚴重度：**high**（飛安）
- 位置：設計見 [`doc/autonomous-flight-state-machine.md`](../doc/autonomous-flight-state-machine.md)
- 建立：2026-08-24

## 起因

使用者要求：「以狀態機的方式設計無人機全自動飛行的操作，要避免所有可能造成
誤動作導致無人機墜毀的操作」。

## 觸發本案的實測發現

2026-08-24 在 SITL 實測「任務執行途中上傳另一份任務」：

```
任務 A（往北）執行中：       北 +0 → +18 → +37 → +57m
飛行中上傳任務 B（往南），
**完全沒有下 mission_start**：北 +74 → +57 → +18 → −2 → −22 → −80m
```

**上傳完成的那一刻飛機就掉頭了。** 模式全程停在 AUTO.MISSION，沒有任何確認
步驟。而 `mission_upload` 端點**沒有任何飛行中的守門**——整個系統目前唯一的
飛行安全守門是 `_guard_bare_arm`（issues/031）。

危害的本質：**「上傳」在地面是存檔，在空中是立即生效的航線變更。**
同一個動作、兩種語意，而操作者可能以為自己只是存一份任務。

## 設計要點（詳見設計文件）

1. **狀態一律由機端遙測導出，地面站不得自己記。** 飛手用遙控器接管、飛控自己
   觸發 failsafe 時，地面站的記憶會與實況分岔——然後拿虛構的狀態去下判斷。
   本專案已有教訓：`job_set_mode` 註解寫著「ACK 是我收到了，不是我做到了」。
2. **`PILOT_CONTROL` 必須是顯式狀態**：飛手切走模式時，系統只觀察、不下指令。
3. **空中改航線走三步序列**（pause → upload → resume），每步都讀回機端確認。
   把一個瞬間動作變成可被中斷的序列——任何一步沒確認就停在懸停。
4. 既有守門（裸 arm、地面直接 mission_start、能力 gating、無定位禁位置操作）
   併入同一張表，理由與證據逐條列明。

## 定案（2026-08-25 使用者裁定，詳見設計文件 §6）

1. **狀態機兩邊都放、即時同步，失聯時以代理為準跑完。**
   實作上要先分清楚：**同步的是「意圖」不是「狀態」**——導出狀態（在飛/懸停/
   已解鎖）兩邊從同一份遙測各自算出，同步它反而製造第二個事實來源；
   真正需要同步的是不在遙測裡的東西（改航線序列走到第幾步、這趟飛的是哪份任務、
   操作者確認過了沒）。
2. **續飛從離當前位置最近的航點開始**，但加三個限定：只算導航航點（續飛到
   takeoff 項＝叫空中的機重新起飛、續飛到 land 項＝當場降落）、用**水平距離**
   （3D 最近可能是正下方的低點，會把飛機往下拉）、選出來的航點**必須在確認
   畫面上標出來**（系統沒有障礙物感知，幾何最近不等於路徑安全）。
3. **飛行中改航線必須 UI 二次確認，且要說明會怎麼調整。** 確認畫面不得只問
   「確定嗎」——要顯示續飛航點是哪一個、暫停後的懸停高度與當前高度差、
   從現在位置飛到續飛航點的距離與方位。**且只在機在空中時出現**，
   地面上傳不跳確認——每次都跳會訓練人閉眼按，然後空中那次也照按。

## ⚠ 未裁定：失聯「跑完任務」與現行「30 秒 RTL」互斥

定案 1 說失聯後跑完，但代理現行實作是**失聯 30 秒且 armed → RTL**
（2026-08-24 實測驗過）。兩者不能同時成立，需要飛安裁定。

三個選項與代價列在設計文件 §7。建議是**分狀態決定**（執行任務中→跑完再 RTL、
其餘狀態→立刻 RTL），並加「剩餘任務時間上限」與「低電量一律 RTL」兩個上限——
因為「跑完」在 3 分鐘的任務與 40 分鐘的測繪任務上風險完全不同。

**裁定之前，代理維持現行行為**（不擅自放寬既有的安全行為）。
