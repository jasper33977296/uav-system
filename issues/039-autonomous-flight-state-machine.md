# 039 · 全自動飛行的狀態機與安全守門

- 狀態：**in-progress**（複裁 A／C／E／G 機端已實作待上機；`FS_GCS_ENABLE` 2026-09-01 裁定開、逾時 45s）
- 嚴重度：**high**（飛安）
- 位置：設計見 [`doc/autonomous-flight-state-machine.md`](../doc/autonomous-flight-state-machine.md)
- 建立：2026-08-24

## 起因

使用者要求：「以狀態機的方式設計無人機全自動飛行的操作，要避免所有可能造成
誤動作導致無人機墜毀的操作」。

## 觸發本案的實測發現

2026-08-24 在 SITL 實測「任務執行途中上傳另一份任務」：

```
任務 A（往北）執行中：       北 +0 → +18 → +37 → +57m
飛行中上傳任務 B（往南），
**完全沒有下 mission_start**：北 +74 → +57 → +18 → −2 → −22 → −80m
```

**上傳完成的那一刻飛機就掉頭了。** 模式全程停在 AUTO.MISSION，沒有任何確認
步驟。而 `mission_upload` 端點**沒有任何飛行中的守門**——整個系統目前唯一的
飛行安全守門是 `_guard_bare_arm`（issues/031）。

危害的本質：**「上傳」在地面是存檔，在空中是立即生效的航線變更。**
同一個動作、兩種語意，而操作者可能以為自己只是存一份任務。

## 設計要點（詳見設計文件）

1. **狀態一律由機端遙測導出，地面站不得自己記。** 飛手用遙控器接管、飛控自己
   觸發 failsafe 時，地面站的記憶會與實況分岔——然後拿虛構的狀態去下判斷。
   本專案已有教訓：`job_set_mode` 註解寫著「ACK 是我收到了，不是我做到了」。
2. **`PILOT_CONTROL` 必須是顯式狀態**：飛手切走模式時，系統只觀察、不下指令。
3. **空中改航線走三步序列**（pause → upload → resume），每步都讀回機端確認。
   把一個瞬間動作變成可被中斷的序列——任何一步沒確認就停在懸停。
4. 既有守門（裸 arm、地面直接 mission_start、能力 gating、無定位禁位置操作）
   併入同一張表，理由與證據逐條列明。

## 定案（2026-08-25 使用者裁定，詳見設計文件 §6）

1. **狀態機兩邊都放、即時同步，失聯時以代理為準跑完。**
   實作上要先分清楚：**同步的是「意圖」不是「狀態」**——導出狀態（在飛/懸停/
   已解鎖）兩邊從同一份遙測各自算出，同步它反而製造第二個事實來源；
   真正需要同步的是不在遙測裡的東西（改航線序列走到第幾步、這趟飛的是哪份任務、
   操作者確認過了沒）。
2. **續飛從離當前位置最近的航點開始**，但加三個限定：只算導航航點（續飛到
   takeoff 項＝叫空中的機重新起飛、續飛到 land 項＝當場降落）、用**水平距離**
   （3D 最近可能是正下方的低點，會把飛機往下拉）、選出來的航點**必須在確認
   畫面上標出來**（系統沒有障礙物感知，幾何最近不等於路徑安全）。
3. **飛行中改航線必須 UI 二次確認，且要說明會怎麼調整。** 確認畫面不得只問
   「確定嗎」——要顯示續飛航點是哪一個、暫停後的懸停高度與當前高度差、
   從現在位置飛到續飛航點的距離與方位。**且只在機在空中時出現**，
   地面上傳不跳確認——每次都跳會訓練人閉眼按，然後空中那次也照按。

## 失聯處置（2026-08-25 裁選項 C／2026-08-31 逐條複裁）

**選項 C（逐狀態決定）2026-08-25 裁定並實作**於代理 `_loss_state`／
`_loss_verdict`，16 格判定表測試通過（`tools/link-loss-table.py`，含反向驗證）。
兩個門檻值同日定案為 **30s／15%**。

> **文件曾比程式碼舊六天**：本檔與設計文件在 2026-08-31 之前都還寫著「未裁定、
> 上限暫定 120s／40%」，而代理跑的是 30s／15%。**安全規則的文件與實作落差本身
> 就是隱患**——照文件覆核會覆核到一組不存在的值。

2026-08-31 把剩餘項攤開逐條裁定，七條全數有結論（完整理由見設計文件 §7 複裁表
與協定 §6）：

| # | 裁定 | 落地狀態 |
|---|---|---|
| A | `ARMED_GROUND` 維持「只告警」，**補一條前置：RC 未連線不得起飛、不得開始任務**（單機與群組同時起飛皆適用） | **待實作** |
| B | 單飛上限維持 **30s**——已知它讓續飛實際只剩 20 秒（處置門檻 `LINK_ACTION_S` 是 10s），選項 C 因此很接近選項 A，接受 | 已是現值 |
| C | 「跑完」補 `mission_seq == mission_total` 替代判定，**真機覆核 ArduPilot 4.7 前不啟用** | **待實作** |
| D | 失聯處置一律 RTL，不因低電量改 LAND | 已是現值 |
| E | **讀不到電量＝不准續飛**（原本 `battery_pct is None` 會跳過檢查＝把「不知道」當成「充足」） | **待實作** |
| F | 鏈路恢復不自動改變當下行為，只解除警戒並留痕 | 已是現值 |
| G | 意圖通道：逐則 `ack`、不做週期同步、斷線期間的 intent 恢復後補送，且**補送一律重算提案再要人確認** | **待實作** |

**A 是這輪最重要的一條**：「只告警」的整個理由是遙控器在旁邊待命，而那是一個
**從未被驗證的假設**。RC 掉線時前提不成立，機在地上失聯就沒有任何人能接管。

**G 的補充**：狀態守門擋得住「恢復後狀態已變」的舊 intent，擋不住「狀態又剛好
合法」的——它附帶的幾何是斷線前算的，40 秒 × 10 m/s ＝ 400 公尺誤差，而守門只
看狀態不看新鮮度。所以補送要接協定 §5.1 已實作的提案過期重算。

**代理現在沒有解 RC 狀態**（`agent.py` 裡與 RC 相關的只剩搖桿移除時留下的註解），
A 要新增訂閱；判定來源與哨兵值列為待覆核（協定 §7.2）。

### ⚠ 2026-09-02 真機覆核：**A 這條守門目前沒有訊號可用**

兩側都實作完了（代理送 `rc_link`、地面站自己也算一份並比對），但從真機讀回來
的 `SYS_STATUS` **回報 18 個感測器、RC 接收機不在其中**——ArduPilot 4.7 沒有設
`MAV_SYS_STATUS_SENSOR_RC_RECEIVER` 的 `present` 位元。

所以 `rc_link` 恆為 `None`，而 **`None` 不擋**（那是對的：把「不知道」當成
「沒有 RC」會讓所有還沒回報這個位元的機都起飛不了）。淨結果：
**複裁 A 的 RC 前置條件在這台機上從未生效過。**

**要修的不是政策，是訊號來源。** 三個候選，都還沒驗：

1. **`RC_CHANNELS` 有沒有在送**（以及 `chancount` > 0）。問題是「沒收到」
   可能只是沒串流，分不出「沒有接收機」——**那正好是 `rssi` 被否決的同一個
   理由**（沒有「不知道」這一態）。
2. **ArduPilot 的 RC failsafe 走 STATUSTEXT**（"Radio Failsafe" 之類）。
   事件式訊號：**只在轉態時出現**，接上系統時的當下狀態問不到。
3. **讀參數**（`FS_THR_ENABLE` 等）只說得出「有沒有設定失效保護」，
   不是「現在接得到遙控器」。

**在有訊號來源之前，033 第 3 層（實體遙控器）的「在場待命」仍然是一個
未被驗證的假設**——而複裁 A 存在的全部理由就是要驗證它。這件事要記著。

## `FS_GCS_ENABLE`：2026-09-01 裁定「開」（選項 B）

選項 C 的整套設計文件與部署查核表都寫著「飛控的 GCS failsafe 盯的是機上代理的
心跳，5G 斷了代理照樣心跳，所以飛控完全無感」。**那句推論是錯的**——GCS 心跳是
**地面的指令服務**每秒發的（`mav.py:189-193`，`source_system = 255`），代理只是
把地面站的封包原封轉發進序列埠、自己從不送心跳。**5G 一斷，飛控那邊的心跳就
真的停了。**

所以 `FS_GCS_ENABLE` 是一個真的取捨，而不是文件原本以為的技術細節：

* **開（1）**：多一層完全獨立於 5G 與地面站的防線。**但飛控會搶在選項 C 前面**
  ——它的逾時遠短於我們的 30 秒單飛上限，「失聯後跑完任務再 RTL」實際上不會發生。
* **關（0）**：選項 C 照裁定生效，但失聯時只有代理這一層；代理自己掛掉（乙類
  失聯）時就沒有任何人了。

**裁定：開，`FS_GCS_TIMEOUT = 45`。** 飛控那層當代理的後備，只在代理沒有動手
時才出手。

> **裁定當下我寫的條件是錯的（太弱），一併更正**：原本寫
> `FS_GCS_TIMEOUT > LINK_ACTION_S`（10s）。但代理在第 10 秒只是**開始判斷**，
> `FLYING_MISSION` 那一格會**繼續飛到單飛滿 `LINK_LOSS_MAX_SOLO_S`（30s）**
> ——所以**代理最晚動手的時刻是 30 秒**。逾時設 15 秒的話，飛控會在代理續飛
> 的中途搶先，「跑完任務再 RTL」那一格照樣不會發生，而那正是 08-31 裁過的
> 那一格。正確的不變式是：
>
>     FS_GCS_TIMEOUT  >  LINK_LOSS_MAX_SOLO_S（30s）  >  LINK_ACTION_S（10s）
>
> **代價**：代理自己掛掉（乙類失聯）時沒有任何人管到第 45 秒；出廠的 5 秒只要
> 5 秒。這是在賭「代理活著」的機率高於「任務被無謂打斷」的成本——甲類在本場域
> 是常態、乙類罕見，所以合理，但它是一個賭。要調整就調 45。

完整事實鏈見 [`doc/verification-checklist.md`](../doc/verification-checklist.md)
與 [`doc/emergency-availability-design.md`](../doc/emergency-availability-design.md) §1.3。
順帶：開啟時 [034](034-healthz-hides-zombie-router.md) 的殭屍 router 會讓 5G
明明正常、飛控卻進 GCS failsafe——因為心跳的來源正是那個停擺的迴圈。

## 實作分工（2026-08-31）

系統側（本 repo）與機端（`~/uav-agent`）分兩個 session 做。**地面站這邊先落地
並且對機端的舊行為完全相容**——沒有送新欄位的代理照舊能跑，不會因為升級順序
而擋掉飛行操作。

### 已完成：系統側

| 項 | 內容 | 檔案 |
|---|---|---|
| G | `intent` 逐則 `ack`：地面站收下並記進 `receipts`，**逾時的說法因此分得出**「代理連回執都沒回＝沒送達」與「回執收到了但算不出判決」 | `agent_link.py`／`main.py` |
| G | 失聯中的 intent 壓進佇列回 **`queued`**（上限 8 則、TTL 10 分鐘，丟棄要留 log），指令服務收到 `queued` **擋下**而不是放行 | `api.py`／`guard_client.py` |
| G | 重連後補送，**每則都帶 `dry_run`**、結果推 `agent_intent_replay` 給前端，並寫一筆 `intent_replayed` 事件 | `main.py:_replay_pending` |
| A | 鏡像 `rc_link`，`rc_link === false` 時**起飛與「開始任務」按鈕按不下去**並說明原因 | `store.ts`／`CommandPanel.tsx` |

驗證：`scripts/test-intent-replay.py`（14 項全過，含「補送只做一次」與
「每則都帶 dry_run」的反向驗證）；`test-intent-guard.py`／`test-ws-agent.py`
兩份既有測試同步改成新契約後全過。

### 待做：機端（另一個 session）

1. **`state` 加 `rc_link`（bool）**——地面站已經在鏡像並據此擋按鈕。
   **沒送＝`null`＝不知道＝不擋**：把「不知道」當成「沒有 RC」會讓所有還沒
   升級的機都起飛不了（issues/036 的同一個教訓）。
2. **收到 `intent` 先回 `{"type":"ack","of":"intent","intent_id":…}`**，再照
   原本的流程回 `event`。地面站收下 ack 但不回話（對回執再回 ack 會沒完沒了）。
3. **`params.dry_run` 為真時只問判決／算提案，不動飛機**——補送全部走這條。
   乾跑模式已經有了（`cb41ef9`），確認補送路徑也吃這個旗標。
4. **A**：訂閱 RC 狀態，`guard.check()` 加 RC 前置條件。它**橫跨狀態**，
   建議不要塞進 `_ALLOW`（會讓 `READY`／`ARMED_GROUND` 各分裂成兩格），
   而是在 `check()` 裡獨立一道，理由訊息照既有紀律說得出「現在能做什麼」。
5. **E**：`_loss_verdict` 裡 `battery_pct is None` 改成不准續飛。
6. **C**：`mission_seq == mission_total` 替代判定，旗標預設關，真機覆核後才開。
