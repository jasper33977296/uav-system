## 現象

2026-09-16，飛控串列被外部改掉 baud（見 [049](049-link-display-gated-on-mavlink.md)，成因是 `uart-probe.sh` 對代理正開著的
裝置下 `stty`），結果飛控整整 **25 分鐘**一個字都進不來。這段期間代理：

1. **不知道**——沒有任何一行 WARNING 說「飛控沒聲音了」。唯一的線索是
   10 秒一次狀態列裡的 `fc_heartbeat_age_s` 一路長到 1220，沒有人會盯著那個數字。
2. **不出聲**——地面站完全收不到東西，即時頁連 5G 訊號都一起空白（見 [049](049-link-display-gated-on-mavlink.md)）。
3. **不救**——沒有重開序列埠、沒有重設 termios、什麼都沒做，就這樣空轉到人工重啟。

最後是人重啟 `uav-agent` 才恢復（11:45:44），而重啟之所以有效，只是因為 pyserial
在 open 時會重設 termios——**純屬副作用，不是設計**。

## 原因

### 1. 開埠之後就不再回頭（`agent.py:1055`、`:1110`）

```python
self.connect_serial()          # 1055：只在 run() 開頭呼叫這一次
...
fd = self.serial.port.fileno() # 1110：fd 在進迴圈前取一次，之後永遠是這個值
```

`connect_serial()` 自己有重試迴圈，但**只在啟動時有用**。進了主迴圈之後，
不論是 termios 被改、USB 被拔（ENODEV）、還是 fd 壞掉，都沒有任何路徑會重開。
`tick()` 外面那層 try/except 只保證迴圈不死——它吞掉例外繼續跑，
於是壞掉的 fd 會**安靜地空轉到天荒地老**。

### 2. 看門狗只管「心跳在、遙測停」，不管「心跳本身不見了」（`:1201-1207`）

```python
hb_ok = (now - self.mon.last_hb) < 5.0
telem_stale = (now - self.last_telem_rx) > 5.0
if hb_ok and telem_stale and not quiet and ...:
    log.warning("心跳在但遙測停了 %.0f 秒，重新請求串流", ...)
```

這條處理的是「飛控重開機把串流速率歸零」，是對的。但 `hb_ok` 為 False 時
**沒有任何 else**——心跳不見了反而比遙測停了更嚴重，卻沒人管。

### 3. 對地面站的唯一出口是「轉發飛控的框架」（`:1168`）

```python
self.telem.send(buf)          # buf 來自飛控
self.cmd.send(buf)
```

代理對地面站說的每一句話都是飛控說的話的轉發。**飛控不講話，代理就完全靜音**——
這正是即時頁整塊空白的機上側成因。

### 4. 開埠時沒有任何防護（`:701`）

沒有 `TIOCEXCL`（pyserial 的 `exclusive=True`），任何人都能再開一次這個裝置。

## 修法建議

### 需求 1：偵測

- **每拍比對 termios**：`termios.tcgetattr(fd)` 取出的速率與 `self.a.baud` 不符
  ＝有人動過。成本是每 0.2 秒一次 syscall，可忽略。偵測到就大聲 WARNING
  ＋事件，並**直接用 `tcsetattr` 改回來**（比重開埠輕，且不掉 fd）。
- **`TIOCEXCL`（開埠時 `exclusive=True`）**：擋掉非 root 的第二次 open。
  **注意這擋不住本次的成因**——`sudo ./uart-probe.sh` 是 root，而 root 可以
  無視 TIOCEXCL。所以兩條都要有：TIOCEXCL 擋意外，termios 比對抓 root。

**實作結果（`a02f7d3`）與上面的差異**：

- 比對改成**每秒一次**而不是每拍（`PORT_CHECK_S`）——讀取熱路徑不需要每 0.2 秒
  問一次核心，1 秒的解析度對「有人下 stty」綽綽有餘。
- 改回去**不是自己拼 termios 結構**，是重設 pyserial 的 `baudrate`，讓它的
  `_reconfigure_port()` 把 raw／-echo／-crtscts／parity 整套重新套用——外部
  `stty` 動到的不一定只有速率。之後清掉輸入緩衝（錯速率讀進來的是垃圾）。
- **`TIOCEXCL` 沒做。** 它擋不住本次的成因（root），優先度低於需求 2。
- **事件沒發，只有 `log.error`。** 查的時候發現 `Monitor.events` 這個清單
  **從頭到尾沒有人讀**（全庫只有 `.append`，沒有任何消費者），append 進去
  等於什麼都沒做。那是另一個問題，不在本條範圍——但在它被接起來之前，
  往裡面丟東西只是自我安慰。
- 非 tty 的裝置（`--dev udpin:`，SITL 走同一條路徑）用 `os.isatty` 跳過，
  否則對 socket 問 termios 會每秒拋一次例外。

### 需求 2：取回

心跳消失超過門檻（建議 3s 告警／10s 開始動作）進入復原狀態機，逐級加壓：

1. 重設 termios（最輕，解掉本次這種）
2. 關掉重開序列埠（`connect_serial()` + **更新 `fd`**——注意 `fd` 目前是
   `tick(fd)` 的參數，要改成從 self 讀，否則重開後主迴圈還抓著舊的）
3. 持續重試並退避，**永不放棄**（飛控可能只是比 Pi 晚上電）

飛行中的取捨要另外決定：`LINK_ACTION` 那套是為「地面站失聯」設計的，
**飛控失聯是不同的問題**（代理連下指令的對象都沒了，RTL 也送不出去）。
本條先只做「地面上與待命時」的復原，飛行中的處置留給 issues/039／033 一起看。

**實作結果（`17e5765`）與上面的差異**：

- 門檻用 **5s 告警／15s 開始重開／退避 10s**，不是建議的 3s／10s。重開比告警重，
  而飛控重開機本來就要幾秒、termios 那層每秒也在修——先讓輕的手段有機會。
- 第 1 級（重設 termios）**不在這個狀態機裡**：它由需求 1 的看門狗每秒獨立在做，
  所以走到重開這一步，就已經代表那一層沒救回來。
- **「飛行中不做」這條最後沒有採用。** 重開修的是代理自己的鏈路，不是對飛機
  下指令，與 `LINK_ACTION` 那套處置無關；而飛行中失去飛控鏈路時，最不該做的
  事就是不試著把它拿回來。留給 039／033 的仍然是**處置**（拿不回來時要做什麼），
  不是**復原**。
- 多做了一項上面沒寫的：**讀取失敗（USB 被拔＝ENODEV）直接觸發重開**。壞掉的
  fd 會讓 `select` 每次都說它可讀，不重開的話主迴圈變成 100% CPU 空轉，
  而外面看起來一切正常——這是原本的 try/except 吞掉例外續跑會留下的洞。
- 一個原本沒想到的約束：**執行期重開絕不能阻塞**。`connect_serial()` 原本是
  「開到成功為止」的迴圈，主迴圈卡在那裡的每一秒，地面站那一側也跟著停擺，
  而地面失聯處置正是靠主迴圈在跑。所以拆成 `_open_serial_once()`（開一次就回來）
  與 `connect_serial()`（只在開機時用）。
- `self.fd is None` 成為一個合法狀態＝「現在沒有可用的埠」，主迴圈照樣跑地面站
  那一側；期間地面站送來的上行記進 `fc_write_dropped`，**不假裝轉發成功**。

### 需求 3：復原期間持續出聲

**絕對不可以合成假的飛控 MAVLink。** 後端 `mavlink_rx.py:404-406` 對任何收下的
框架都會做：

```python
st.telem_seen_mono = ent["seen"]   # 畫面數字的年齡被刷新
st.connected = True
st.ever_connected = True
```

代理若在飛控失聯期間送自己的心跳到遙測埠，後端會把這台機標成**連線中、數字新鮮**
——那是謊話，而且正是 issues/036 花了一整個案子在消滅的那種謊話。

建議改走**代理自己那條通道**（`ws://GS:38000/ws/agent`，與飛控完全無關、
本次全程都連著），送明確的 `fc_link` 回報：狀態（ok／lost／recovering）、
失聯多久、**最後已知的狀態快照**、復原嘗試第幾次。地面站據此：

- 即時頁繼續顯示這台機，但誠實標示「飛控失聯，數字是 N 秒前的」
- 5G 訊號照常顯示（它本來就還在送）——[049](049-link-display-gated-on-mavlink.md) 那條從後端側解同一個問題

## 影響

- 飛安：代理是飛控與地面站之間唯一的橋，而當時它對「橋的一端塌了」完全無感。
  本次是在地面、未解鎖，所以只損失 25 分鐘。飛行中發生就不只是資料問題。
- 排查：故障期間機上與地面都沒有任何告警，25 分鐘後靠人眼看狀態列裡的數字才發現。

### 驗證

`uav-agent/tools/fc-link-watchdog.py`，31 項，用 pty 當序列埠、不碰真飛控。

**真機驗證（2026-09-21，機子在台架上、未解鎖）兩項：**

1. **重現原始故障**：對 agent 正開著的 `/dev/ttyAMA0` 下
   `sudo stty -F /dev/ttyAMA0 1500000`。3 秒後埠已自己回到 57600，
   `port_tampered=1`，`fc_link_ok` 全程 True，期間 `msgs_from_fc` 仍 +2011
   ——**鏈路一秒都沒斷**。同一個動作 09-16 花掉 25 分鐘的靜默。
2. **真 UART 上的關掉重開**（趁部署停機窗口跑，agent 停著避免兩個 fd 搶位元組）：
   重開後 26 種訊息型別立刻全部回來、速率不變，fd 編號被重用（3 → 3）證明舊的
   確實關掉了。**飛控沒有被重置**——GPIO14/15 三線接法沒有 DTR/RTS 可以被拉低。
   換成 USB 數傳或有接 DTR 的轉接板時這個保證不成立，要重新確認。

部署後 30 秒觀察無誤觸發：`fc_reopens=0`、`port_tampered=0`、`fc_write_dropped=0`。
