# 038 · 系統不知道哪台是哪台：註冊資訊沒有任何機體識別

- 狀態：in-progress（**本階段只做「請求並記錄 UID」**，比對與告警未做）
- 嚴重度：medium（識別基礎；撞號時的後果是資料混料，靜默發生）
- 位置：`apps/backend/app/mavlink_rx.py`、`state.py`、`db.py`；
  請求端在 [uav-agent](https://github.com/jasper33977296/uav-agent)
- 建立：2026-08-24

## 現象

使用者問：「目前的註冊資訊都沒有可以辨識是哪台無人機的必要資訊，那系統要怎麼
知道哪台是哪台？」

查證後：**確實不知道。** 身分鏈只有一環：

    實體飛機 → 飛控上的 SYSID_THISMAV 參數 → drones.mav_sysid → 這筆記錄

註冊表單的其他欄位沒有一個能辨識機體：

| 欄位 | 實際內容 |
|---|---|
| `name` | 人取的標籤 |
| `serial_no` | **name 的複製品**（`INSERT ... VALUES ($1, $1, ...)`），不是序號。實際作用只是「名稱不可重複」的唯一鍵 |
| `model` | **從來沒有任何地方寫入**，永遠 NULL |

資料庫實況佐證：`pi5-ardu-quad | pi5-ardu-quad`（序號＝名稱）、
`ai-model-rb5 [掛掉了] | test`（當初名稱欄打的字）。

## 這造成的失效模式

1. **兩台都是預設 sysid 1** → 分不出來。系統會發 `sysid_addr_change` 告警，
   但那句話是「來源位址變了」，不是「這是兩台不同的機」。
2. **先到先得的自動認領**（`drone_for_sysid` 的第 2 條：主機若 `mav_sysid` 為空
   就認領第一個看到的 sysid）→ **2026-08-24 實際發生**：新接的四旋翼被認成
   已經掛掉的 RB5 記錄，`/api/live` 顯示的是別台機的名字。
3. **飛控換到另一個機架、或參數重置** → 記錄描述的變成另一台實體機，靜默發生。
4. [016](016-rb5-platform-connectivity.md) 記著 voxl-mavlink-server <1.4.12 有
   「全機 sysid 被重設為 1」的韌體 bug——同一個家族。

## 可以當身分的東西：板子 UID

`AUTOPILOT_VERSION` 帶 `uid2`——燒在飛控板上的唯一硬體 ID。

**但它不會自己來**：實測這台機至今送過 28 種訊息，**沒有 AUTOPILOT_VERSION**
（ArduPilot 不主動送）。全庫 grep 也確認我們從來沒請求過。

主動請求後拿到（2026-08-24 實測）：

    uid   : 0                                     ← 舊的 64-bit 欄位是 0
    uid2  : 2a0020001151333139383538              ← 12 bytes，去掉尾端補位
    board_version     : 76480512 (0x048F0000)
    vendor_id         : 4617     (0x1209)
    product_id        : 22337    (0x5741)
    flight_sw_version : 0x040700ff → 4.7.0 (official)

`uid2` 是 STM32 的 96-bit 唯一裝置 ID（其中 `333139383538` 是 ASCII `319858`，
晶圓批號——典型的 STM32 UID 結構）。

### ⚠ 必須誠實說清楚的限制

**`uid2` 認的是飛控板，不是機架。** 把飛控拆到另一台飛機上，UID 跟著板子走。
所以它是比 sysid 好得多的錨點，但仍然只回答「哪塊板子」。

**機架身分只能由人維護**——那正是 `serial_no` 與 `model` 該做的事，而它們
現在一個是名稱複製品、一個永遠空白。合理的設計是兩層：

| 層 | 內容 | 誰維護 | 系統能做什麼 |
|---|---|---|---|
| 機器可驗證 | 板子 UID、板型、韌體版本 | 自動偵測 | UID 變了就示警＝這筆記錄現在指的是別塊板子 |
| 人工維護 | 機架序號、型號 | 註冊時填 | 存著、顯示、**不假裝知道** |

## 本階段做了什麼（使用者定案：先做請求並存 UID，看實際拿到什麼）

- **請求端放在機上代理**，不是地面站。理由：請求要送 `COMMAND_LONG`，那是個
  **通用信封**（同一個型別可以裝 arm），把它加進 backend 的 `SEND_WHITELIST`
  等於在 read-only 邊界上開洞——那道邊界的註解明寫「要發任何別的，這行就是
  攔你的人」。代理本來就是下達者（[026](026-autopilot-driver-abstraction.md)
  待決點 1 定案），回應隨遙測一起轉發回來，backend 照收即可。
- **一次性請求**，不設串流間隔：板子身分不會變，訂成串流只是浪費 57600 的頻寬。
- backend 解碼並存進 `LiveState` 與 `drones.board_uid`，`/api/live` 帶出來。
- 韌體版本一併解碼成人話（`major<<24|minor<<16|patch<<8|type`）。

## 刻意還沒做

- **不比對、不告警。** 「UID 變了＝這筆記錄指向別塊板子」這種告警，要先有一段
  真實資料確認 `uid2` 在同一塊板子上**跨重開機與韌體升級是穩定的**——
  沒驗證過就先加告警，只會製造假警報，而假警報會訓練人忽略真警報
  （同 deploy-checklist 開頭那條「常態性存在的警告等於沒有警告」）。
- `serial_no` 仍是 name 的複製品、`model` 仍是死欄位。
- 前端還沒顯示板子身分。
- 註冊時仍不能指定 sysid（自動認領照舊）。
