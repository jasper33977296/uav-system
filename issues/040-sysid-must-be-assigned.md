# 040 · sysid 必須由系統指派，不是由機自報

- 狀態：**in-progress**（設計 [`doc/drone-admission-protocol.md`](../doc/drone-admission-protocol.md) 已交付；2026-09-02 使用者四條裁定收斂了原本的待裁，**剩兩條**；分五批實作）
- 嚴重度：**high**（資料歸屬的根，撞號時後果是靜默混料）
- 位置：跨 `apps/backend/app/mavlink_rx.py`（歸屬）、`drones` 表、uav-agent（落地）
- 建立：2026-09-02

## 起因：同一件事至少發生過兩次，都沒有人發現

2026-09-01 為了跑 026 B4-d 起了 PX4 SITL。它的 sysid 是 **1**，而真機
`pi5-sdmodelh7v2-ardu`（ArduPilot 4.7，board_uid `2a00…`）的 sysid 也是 1。
系統**直接把模擬器認領進那台真機的記錄**，log 裡只有一行 `info`：

```
sysid 1 → pi5-sdmodelh7v2-ardu（既有主機）
```

結果：**PX4 1.14.3 的 `vehicle_event` 寫進了一台 ArduPilot 真機的事件流**。
清理時才發現**最早的一筆來自 08-24**——同樣的事以前就發生過，總共
**46 筆**假事件躺在真機的記錄裡，沒有任何人察覺。

遙測沒有被污染，但**那是運氣不是防護**：issues/004 的修法讓未 armed 不入庫，
而 SITL 從頭到尾沒解鎖。armed 過的話，模擬器的軌跡會直接進真機的飛行記錄。

## 根因：sysid 是機端自報的，而它是我們唯一的歸屬鍵

- 歸屬、路由、指令定址全部靠 sysid。
- 而 sysid 由機端自己宣告，我們**照單全收**。
- [038](038-board-identity.md) 記錄了 `board_uid`（真正穩定的身分），
  但**只記錄、不比對**——所以身分鏈存在卻沒有接上。
- 更糟的一段：認領時會把 DB 裡的 `board_uid` **回填**到新機的狀態上，
  **等於我們替它答了身分**。

同一個病在 [016](016-rb5-platform-connectivity.md) 也記過：
voxl-mavlink-server < 1.4.12 把全部機重設為 sysid 1。

## 已做（2026-09-02，038 的比對半邊）：讓它看得見，不是根治

`mavlink_rx._identity_guard`：

| 訊號 | 處置 | 為什麼強度不同 |
|---|---|---|
| **廠牌不合**（記錄是 ArduPilot、來的是 PX4）| **硬擋**：`identity_ok=False`，遙測與事件都不再記入該筆記錄，發 `critical` 事件 | 一台機不會重開機之後換廠牌，沒有誤判空間 |
| **`board_uid` 不合** | 只發 `warn`、**不擋**，但**不覆蓋** DB 的期望值 | uid2 跨重開機／韌體升級的穩定性還沒實測（`set_board_uid` 原註解的顧慮仍成立）；但覆蓋會把唯一的期望值抹掉 |

實測：同一個情境重跑，污染從 46 筆變 **0 筆**。
測試 `scripts/test-identity-guard.py`（10 項，含反向驗證）。

**但這只是讓撞號看得見。** 兩台機仍然可以宣告同一個 sysid，而先到的那台佔住
記錄、後到的被擋在門外——**被擋的如果是真機，那就是真機飛不了**。

## 需求（使用者 2026-09-02）：sysid 由系統指派

## 待決

1. **依據什麼身分指派？** 只有 `board_uid` 是機端不能亂改的（038）。
   但它要**開口問**（`AUTOPILOT_VERSION`）才拿得到——而問到之前，機已經在
   用某個 sysid 送遙測了。**指派必然晚於第一個封包**，所以要定義那段空窗
   怎麼處理（暫掛未指派區？照收但不歸屬？）。
2. **怎麼落到機上？** `MAV_SYS_ID` 是飛控參數，設了要重開才生效。
   誰來設——**代理最適合**（它在飛控旁邊、且已經有參數讀寫路徑），
   但那代表**沒有代理的機無法被指派**（第三方的機永遠不會有代理）。
3. **指派不了的機怎麼辦？** 至少三類：第三方的機、還沒裝代理的機、
   **SITL**。
   > ⚠ **實測（2026-09-01）**：對 PX4 SITL 送 `PARAM_SET MAV_SYS_ID=9`，
   > 回讀確認是 9，送重開之後**又變回 1**——那個映像每次啟動都是原廠狀態，
   > 參數不持久。所以「指派」對開發環境的 SITL 天生無效，
   > 得另想辦法（改映像啟動參數、或讓 SITL 走一條不參與指派的路徑）。
4. **撞號當下要做什麼？** 現在是「先到的佔住、後到的被擋」。指派制度下應該
   反過來：**未經指派的 sysid 一律不得入列**，而不是比誰先到。
   但那會讓「還沒被指派過的新機」連不上——第一次連線的雞生蛋要解。
5. **`is_primary` / 「既有主機認領」那條路徑要一起重看**：2026-08-24 已經
   因為它出過一次事（一筆停用的舊記錄仍是主機，新機一開機就被認領進去）。

## 設計已交付（2026-09-02）

[`doc/drone-admission-protocol.md`](../doc/drone-admission-protocol.md)。
使用者的需求是兩句：**sysid 必須由系統指派**、**身分驗證完成前不可以指派任務
或嘗試控制無人機**。設計把它拆成一台機的**入列狀態機**（SEEN／IDENTIFYING／
ADMITTED／QUARANTINED／UNMANAGED）、一組配號規則、與四層守門落點。

**先劃清楚的一件事**：MAVLink 本身沒有認證，所以這是**識別不是認證**。
它防得了撞號與設定錯誤（本專案至今所有身分事故都是這一類），
**防不了蓄意偽造**。真正的認證只有 MAVLink 2 簽章那條路，本階段不做——
但這件事必須寫明，否則它會被當成一道其實不存在的安全防線。

**兩條不可妥協的原則**：

* **不指揮 ≠ 不顯示。** 未入列的機照樣畫在畫面上、標明未驗證。天上有一台認不
  出來的機，**看不見比不可控更危險**。
* **嚴格入列之所以可以接受，是因為它從不移除最後的退路**——被擋下的機仍然可以
  用實體遙控器飛（033 第 3 層）。**沒有那一層的話，這套規則就會變成「把一台在
  天上的機鎖死」，那時它就不該這樣設計。**

**最需要小心的一格是「飛行中失去驗證」**：不撤銷指揮權（把在天上的機交給沒有
人更糟），只擋新任務指派，**緊急動作永遠放行**。

## 2026-09-02 使用者四條裁定，把設計收斂掉一半

| # | 裁定 | 效果 |
|---|---|---|
| 1 | **要被本系統控制，機上一定要有代理**（不接受純飛控）| 身分的錨點從 `sysid` 換成代理通道上的板號。**順手消掉一個待決點**：沒有代理的機不可指揮，所以也不需要配號 |
| 2 | **識別的唯一鍵值是板號** | `sysid` 降級成純地址 |
| 3 | **註冊時發現 sysid 被佔用 → 地面站配新號給那台的代理** | **撞號從兩難變成事務**——不必再判斷「要隔離誰」 |
| 4 | **MAVLink 2 簽章要排** | 成為 A5，但先做設計 |

**裁定 3 特別值得記**：本文原本兩個版本都在爭論「先到先得 vs 兩台都隔離 vs
看誰的綁定連續」——而**那整個問題是因為我們把 sysid 當成身分才產生的**。
身分收斂到板號、地址撞了就換一個，兩難整個消失。

**使用者的一句追問也修掉一個實質錯誤**：「飛行中失去驗證是什麼意思，板子總不會
在天上被換掉吧」——原本 §5 把「另一個來源冒用號碼」寫成了「這台機失去驗證」，
照那個寫法，**一台在天上的機會因為地面有人起了模擬器而被關掉指揮權**。

**剩兩條待裁**：號碼回收政策（建議明確釋放而非自動）、
簽章要保護哪一段（只保護代理↔地面站的話 TLS 更便宜——**這是 A5 設計的第一個
問題，不是實作細節**）。

**A1＋A2 就能擋掉本檔記載的全部三次事故**，而 A3 才需要動到飛機。
**但 A2 會影響開發流程**：代理強制之後 SITL 要被指揮就得掛代理，而現在沒有——
那要排進 A2 一起做，否則 A2 上線那天所有 SITL 都會變成指不動。

## 進度

### A1 配號登錄（2026-09-02 完成）

* `drones.assigned_sysid` ＋ **partial unique index**（`WHERE assigned_sysid IS
  NOT NULL`）。**與 `mav_sysid` 刻意分成兩欄**：前者是「我們配給這塊板子的
  號碼」（決定），後者是「這台機現在自報的號碼」（觀察）——
  **合成一欄就再也分不出「它跑錯號碼了」這件事**。
* `db.allocate_sysid(board_uid, claimed)` 實作設計 §3.2 的四格查表，
  回傳 `keep`／`change` 與人話理由。
* 號碼池 1–254；**255 永不配出**（我方 GCS）。用盡時**丟出明確錯誤**並說出
  該怎麼辦（釋放退役機的號碼），不是靜默給一個重複的。
* **號碼不自動回收**：釋放必須是明確動作。一個剛釋放又立刻配給別台機的號碼，
  會讓歷史資料的歸屬無法回溯——**同一個號碼在時間軸上指過兩台飛機，
  而遙測只記得號碼**。
* 一次性回填：既有記錄同時有板號與觀察號碼的，那組配對是既成事實，直接登錄
  （實測：真機拿到 `assigned=1`；沒有板號的 `uav-s3` 不回填——我們不知道它是
  哪塊板）。**衝突的不自動改**，留給人處理。

驗證 `scripts/test-sysid-allocation.py`（要在 backend 容器內跑）：四格全覆蓋、
09-01 情境（第 4 格）、255 不配出、用盡要明說，加一條反向驗證——
**直接對資料庫寫入重複配號，唯一索引真的擋得住**。

**本批不接執法、不寫機端**：拿到 `change` 目前只用於顯示與留痕。
執法是 A2、下發是 A3。

## ⚠ A2 開工前的實測發現：**SITL 給不出板號，而它的替代值是一個常數**

2026-09-02 直接問 PX4 SITL 要 `AUTOPILOT_VERSION`：

```
uid2 raw    = 000000000000000000000000000000000000   ← 全 0
uid2 去補位  = （空）
uid (舊欄位) = 0x4954414c44494e4f                      ← ASCII "ITALDINO"
```

**`uid2` 全是 0**，所以 `mavlink_rx.py:387` 的退路生效，改用舊的 `uid` 欄位——
而那個值解出來是 **ASCII 字串 "ITALDINO"**。**一個看起來像常數的東西，
不是一塊板子的序號。**

### 為什麼這件事會把整個設計推倒

裁定是「**識別的唯一鍵值是板號**」。若每一台 PX4 SITL 都回同一個 `uid`，那麼在
新制度下**所有 SITL 都是同一架飛機**——`ensure_drone_by_board` 會把它們全部解析
成同一筆記錄。那比原本的 sysid 撞號**更嚴重**：sysid 撞號至少還會被 09-02 的
`_identity_guard` 抓到（廠牌不同），而板號相同的多台 SITL 連矛盾都不會產生，
它們會**安靜地合併成一台**。

013 的群組任務是用 3–4 台 SITL 驗的。這條路不修，多機開發環境會直接壞掉。

> **誠實的界線**：我只問過**一台** SITL。「每台都回同一個值」是從那個值長得像
> ASCII 常數推論的，**不是實測**。要確認得同時起兩台比對——但無論是否為常數，
> 下面那條修法都成立。

### 修法方向：**全 0 的 `uid2` 不該退回舊欄位假裝有身分**

`uid2` 全 0 的意思是「這塊板子沒有 uid2」，而舊的 `uid` 欄位在 SITL 上是常數。
把常數當成板號，等於**發明一個身分**——那正是本案要防的事的鏡像。

建議：**`uid2` 全 0 → 沒有板號**（不是退回 `uid`）。後果是 SITL 永遠註冊不了，
也就永遠不可指揮——**而那正是「代理強制」裁定下應有的結果**：SITL 要被指揮，
就得由代理提供一個**明確標記為合成**的板號，而不是讓系統從一個常數裡誤讀出身分。

**這條要使用者裁定**，因為它會讓現行的開發環境立刻失去指揮能力。

## 機端待做（原本要交辦給 uav-agent session，該 session 已結束）

1. **`say_hello()` 的 body 加 `sysid`**（`self.mon.state.get("sysid")`，手上已有）。
   地面站據此判斷「它跑錯號碼了沒」；不送的話只能配號給它、無法判斷。
2. **收到 `sysid_action: "change"` 之後真的換號**（A3）：
   `PARAM_SET MAV_SYS_ID` → 讀回確認 → 重開飛控 → 用新號碼回來 → 再註冊一次拿到
   `keep`。四個注意事項：**只在地面做**（用現成的 `flight_state()` 擋，
   只在 `DISARMED`／`NOT_READY`／`READY` 執行）；**`REASSIGNING` 期間要回報**
   （重開的是飛控不是 Pi，意圖通道不會斷——**沒有這一格，換號動作本身會觸發
   039 選項 C**）；**設了要讀回確認**；**PX4 SITL 參數不持久**（實測：設 9、
   回讀 9、重開又變回 1）。
3. **SITL 掛代理的形狀**——見上方的板號問題，這是最硬的一格。

> 代理的 `say_hello()` **本來就是照「板號為鍵」寫的**（docstring：「鍵是
> board_uid 不是 sysid」「等拿到 board_uid 才送」），所以上述是延伸不是改方向。
