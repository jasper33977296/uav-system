# 040 · sysid 必須由系統指派，不是由機自報

- 狀態：**needs-decision**（設計 2026-09-02 交付：[`doc/drone-admission-protocol.md`](../doc/drone-admission-protocol.md)；**四條待裁**，核可後分六批實作）
- 嚴重度：**high**（資料歸屬的根，撞號時後果是靜默混料）
- 位置：跨 `apps/backend/app/mavlink_rx.py`（歸屬）、`drones` 表、uav-agent（落地）
- 建立：2026-09-02

## 起因：同一件事至少發生過兩次，都沒有人發現

2026-09-01 為了跑 026 B4-d 起了 PX4 SITL。它的 sysid 是 **1**，而真機
`pi5-sdmodelh7v2-ardu`（ArduPilot 4.7，board_uid `2a00…`）的 sysid 也是 1。
系統**直接把模擬器認領進那台真機的記錄**，log 裡只有一行 `info`：

```
sysid 1 → pi5-sdmodelh7v2-ardu（既有主機）
```

結果：**PX4 1.14.3 的 `vehicle_event` 寫進了一台 ArduPilot 真機的事件流**。
清理時才發現**最早的一筆來自 08-24**——同樣的事以前就發生過，總共
**46 筆**假事件躺在真機的記錄裡，沒有任何人察覺。

遙測沒有被污染，但**那是運氣不是防護**：issues/004 的修法讓未 armed 不入庫，
而 SITL 從頭到尾沒解鎖。armed 過的話，模擬器的軌跡會直接進真機的飛行記錄。

## 根因：sysid 是機端自報的，而它是我們唯一的歸屬鍵

- 歸屬、路由、指令定址全部靠 sysid。
- 而 sysid 由機端自己宣告，我們**照單全收**。
- [038](038-board-identity.md) 記錄了 `board_uid`（真正穩定的身分），
  但**只記錄、不比對**——所以身分鏈存在卻沒有接上。
- 更糟的一段：認領時會把 DB 裡的 `board_uid` **回填**到新機的狀態上，
  **等於我們替它答了身分**。

同一個病在 [016](016-rb5-platform-connectivity.md) 也記過：
voxl-mavlink-server < 1.4.12 把全部機重設為 sysid 1。

## 已做（2026-09-02，038 的比對半邊）：讓它看得見，不是根治

`mavlink_rx._identity_guard`：

| 訊號 | 處置 | 為什麼強度不同 |
|---|---|---|
| **廠牌不合**（記錄是 ArduPilot、來的是 PX4）| **硬擋**：`identity_ok=False`，遙測與事件都不再記入該筆記錄，發 `critical` 事件 | 一台機不會重開機之後換廠牌，沒有誤判空間 |
| **`board_uid` 不合** | 只發 `warn`、**不擋**，但**不覆蓋** DB 的期望值 | uid2 跨重開機／韌體升級的穩定性還沒實測（`set_board_uid` 原註解的顧慮仍成立）；但覆蓋會把唯一的期望值抹掉 |

實測：同一個情境重跑，污染從 46 筆變 **0 筆**。
測試 `scripts/test-identity-guard.py`（10 項，含反向驗證）。

**但這只是讓撞號看得見。** 兩台機仍然可以宣告同一個 sysid，而先到的那台佔住
記錄、後到的被擋在門外——**被擋的如果是真機，那就是真機飛不了**。

## 需求（使用者 2026-09-02）：sysid 由系統指派

## 待決

1. **依據什麼身分指派？** 只有 `board_uid` 是機端不能亂改的（038）。
   但它要**開口問**（`AUTOPILOT_VERSION`）才拿得到——而問到之前，機已經在
   用某個 sysid 送遙測了。**指派必然晚於第一個封包**，所以要定義那段空窗
   怎麼處理（暫掛未指派區？照收但不歸屬？）。
2. **怎麼落到機上？** `MAV_SYS_ID` 是飛控參數，設了要重開才生效。
   誰來設——**代理最適合**（它在飛控旁邊、且已經有參數讀寫路徑），
   但那代表**沒有代理的機無法被指派**（第三方的機永遠不會有代理）。
3. **指派不了的機怎麼辦？** 至少三類：第三方的機、還沒裝代理的機、
   **SITL**。
   > ⚠ **實測（2026-09-01）**：對 PX4 SITL 送 `PARAM_SET MAV_SYS_ID=9`，
   > 回讀確認是 9，送重開之後**又變回 1**——那個映像每次啟動都是原廠狀態，
   > 參數不持久。所以「指派」對開發環境的 SITL 天生無效，
   > 得另想辦法（改映像啟動參數、或讓 SITL 走一條不參與指派的路徑）。
4. **撞號當下要做什麼？** 現在是「先到的佔住、後到的被擋」。指派制度下應該
   反過來：**未經指派的 sysid 一律不得入列**，而不是比誰先到。
   但那會讓「還沒被指派過的新機」連不上——第一次連線的雞生蛋要解。
5. **`is_primary` / 「既有主機認領」那條路徑要一起重看**：2026-08-24 已經
   因為它出過一次事（一筆停用的舊記錄仍是主機，新機一開機就被認領進去）。

## 設計已交付（2026-09-02）

[`doc/drone-admission-protocol.md`](../doc/drone-admission-protocol.md)。
使用者的需求是兩句：**sysid 必須由系統指派**、**身分驗證完成前不可以指派任務
或嘗試控制無人機**。設計把它拆成一台機的**入列狀態機**（SEEN／IDENTIFYING／
ADMITTED／QUARANTINED／UNMANAGED）、一組配號規則、與四層守門落點。

**先劃清楚的一件事**：MAVLink 本身沒有認證，所以這是**識別不是認證**。
它防得了撞號與設定錯誤（本專案至今所有身分事故都是這一類），
**防不了蓄意偽造**。真正的認證只有 MAVLink 2 簽章那條路，本階段不做——
但這件事必須寫明，否則它會被當成一道其實不存在的安全防線。

**兩條不可妥協的原則**：

* **不指揮 ≠ 不顯示。** 未入列的機照樣畫在畫面上、標明未驗證。天上有一台認不
  出來的機，**看不見比不可控更危險**。
* **嚴格入列之所以可以接受，是因為它從不移除最後的退路**——被擋下的機仍然可以
  用實體遙控器飛（033 第 3 層）。**沒有那一層的話，這套規則就會變成「把一台在
  天上的機鎖死」，那時它就不該這樣設計。**

**最需要小心的一格是「飛行中失去驗證」**：不撤銷指揮權（把在天上的機交給沒有
人更糟），只擋新任務指派，**緊急動作永遠放行**。

**四條待裁**見設計文件 §9，其中兩條方向性最強：撞號時**兩台都隔離**而不是
先到先得（09-01 那次先到的是模擬器，先到先得會擋掉真機）；以及沒有代理的機
**不自動寫參數**（對一台還不確定是誰的機寫參數並重開，本身就是危險動作）。

**A1＋A2 兩批就能擋掉本檔記載的全部三次事故**，而 A4 才需要動到飛機。
