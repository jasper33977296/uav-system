# 終局目標：本系統作為 MCP 供 agent 使用

- 狀態：**定案**（2026-08-11 與使用者討論確定）
- 前提：agent **不具備無人機知識**，只會下達「讓 XX 台無人機飛 XX 路徑」
  等級的意圖。所有航空知識（起飛序列、模式、failsafe、能力差異）由系統內建。
- 使用者三決策：實機任務要人確認（SITL 直接飛）；目標層納入範圍但排在
  任務層之後；使用者＝實驗室內部研究 agent（單一信任域，認證簡化）。

## 1. 控制程度：MCP 只暴露任務層

| 層 | 內容 | MCP 暴露 |
|---|---|---|
| 操作層 | arm/模式/takeoff/上傳（command 服務現有端點） | **否**——需要航空知識，agent 沒有 |
| **任務層** | 「N 台機、此路徑、此高度，去飛」→ 系統包辦預檢/能力檢查/起飛序列/監看/返航 | **是**——MCP 主介面 |
| 目標層 | 「量測此區域」→ 系統自己規劃路徑（與 013 V2/V3 同套能力） | 是，**排在任務層之後** |

**工具面（任務層草案）**：
- `submit_mission(path, drones, alt, …)` → mission_id（提交即驗證：幾何預檢
  ＋capabilities gating＋機隊可用性；不過就拒收＋人話原因）
- `get_mission_status(mission_id)` → pending_approval／flying／completed／
  failed＋原因（沿用 PX4 拒絕原因回傳機制）
- `abort(mission_id)` → 全機 RTL。**唯一暴露給 agent 的安全工具**
- 讀取類工具見 §3

**執行門檻（定案）**：實機任務 agent 提交後進 `pending_approval`，
**前端跳確認、操作員按下才起飛**——飛安責任在人；SITL 環境直接執行。
環境屬性（實機/SITL)由系統判定，不由 agent 聲明。

## 2. 飛行紀錄程度：足以回答 agent 的三個問題

「飛了沒？照計畫飛了嗎？量到了什麼？」——紀錄的完備標準。

既有基礎：兩層收集（原始 tlog＋結構化入庫）、逐台架次、指令留痕、事件流。
需補：

1. **因果鏈打通**：任務 ↔ 架次 ↔ 指令 ↔ 事件 ↔ 量測資料可互相查詢。
   任務生命週期狀態落地＝**issue 010 的閒置欄位正式啟用**
   （missions.status/drone_id 有了資料來源）。
2. **架次機器可讀摘要**：實飛 vs 計畫路徑偏差、訊號統計、電量消耗、
   異常事件清單——`get_flight_summary` 的資料源。
3. **指令留痕加記主體**：操作員 vs 哪個 agent（MCP 呼叫帶 agent 身分），
   追責鏈不斷。內部單一信任域，身分標記即可，不做多租戶權限。

## 3. 訊號比較分析：API-first（UI 是 API 的消費者之一）

agent 的查詢工具（聚合規則沿用誠實原則：**聚合值必附樣本數、
不對未量測區域插值**）：

- `get_flight_summary(session_id)` — 單架次訊號統計
- `query_signal_map(bbox, grid)` — 空間網格聚合（每格 SINR/RSRP 統計），
  回答「哪裡訊號差」
- `compare_flights(a, b)` — 同路徑兩架次逐段差異（/compare 頁的機器版；
  實作時與 /compare 共用查詢層，避免兩套邏輯）

## 4. 落地順序

1. **多機驗收先行**（進行中）——MCP 的「N 台機」承諾以此為底。
2. 任務層資料模型與生命週期（010 復活、因果鏈、架次摘要）。
3. 分析 API 三工具（與 /compare 共用查詢層重構）。
4. MCP server 皮層（工具定義＋agent 身分＋實機確認流）。
5. 目標層（區域→自動路徑，與 013 V2/V3 合流）。
