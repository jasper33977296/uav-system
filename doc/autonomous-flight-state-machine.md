# 全自動飛行的狀態機設計

> 目標：系統負責「載入／執行／中斷／中途更改飛行路徑」，並**絕對確保飛行過程
> 的安全操作**。本文把它拆成一台機的狀態機，並逐條列出**哪些操作在哪些狀態下
> 必須被擋掉、以及擋它的理由**。
>
> 狀態：設計提案（issues/039）。實作前需逐條核可。

---

## 0. 兩條不可妥協的原則

### 0.1 狀態一律由機端遙測導出，地面站不得自己記

地面站若維護自己的狀態變數，只要機體因為**我方以外的原因**改變狀態（飛手用
遙控器接管、飛控自己觸發 failsafe、GPS 掉了退出位置模式），兩邊就分岔——
而地面站會繼續拿著一個虛構的狀態去下判斷。

這條在本專案已經有血的教訓：`job_set_mode` 的註解寫著「PX4 對 DO_SET_MODE 常回
ACCEPTED，但 commander 可能沒真的轉……只看 ACK 會**誤報成功**」。**ACK 是「我
收到了」，不是「我做到了」。**

所以每個狀態都必須有明確的**遙測判定式**（見 §1），而且**每次要下決定時重新
判定**，不是查自己上次記的值。

### 0.2 任何會讓飛行中機體改變航線的操作，都不得是「順手」的

今天（2026-08-24）在 SITL 實測到的事實：

```
任務 A（往北）執行中：       北 +0 → +18 → +37 → +57m
飛行中上傳任務 B（往南），
**完全沒有下 mission_start**：北 +74 → +57 → +18 → −2 → −22 → −80m
```

**上傳完成的那一刻，飛機就掉頭了。** 模式全程停在 AUTO.MISSION，沒有任何確認
步驟，地面站也沒有任何守門。操作者可能以為自己只是「存一份任務到任務庫」。

**「上傳」在地面是存檔，在空中是改航線——同一個動作、兩種語意。**
狀態機存在的首要理由就是把這兩種語意分開。

## 1. 狀態定義與判定式

判定只用機端遙測（`LiveState`），欄位都已存在：

| 狀態 | 判定式 | 說明 |
|---|---|---|
| `DISCONNECTED` | `connected == false` | 沒有心跳。**不得下任何指令** |
| `NOT_READY` | `connected ∧ ¬armed ∧ (prearm_ok≠true ∨ ekf_ok≠true ∨ gps_fix<3)` | 連得上但飛不了 |
| `READY` | `connected ∧ ¬armed ∧ prearm_ok ∧ ekf_ok ∧ gps_fix≥3` | 地面待命 |
| `ARMED_GROUND` | `armed ∧ landed_state == on_ground` | 已解鎖、還在地上 |
| `TAKING_OFF` | `armed ∧ landed_state == takeoff` | 爬升中 |
| `FLYING_MISSION` | `armed ∧ in_air ∧ mode_verb == mission` | 執行任務中 |
| `HOLDING` | `armed ∧ in_air ∧ mode_verb == hold` | 空中暫停 |
| `RETURNING` | `armed ∧ in_air ∧ mode_verb == rtl` | 返航中 |
| `LANDING` | `armed ∧ (landed_state == landing ∨ mode_verb == land)` | 降落中 |
| `PILOT_CONTROL` | `armed ∧ in_air ∧ mode_verb ∉ {mission,hold,rtl,land}` | **飛手接管**（遙控器切了模式）|
| `EMERGENCY` | `mav_state ∈ {CRITICAL, EMERGENCY}` | 機端 failsafe 中 |

> **`PILOT_CONTROL` 必須是一個顯式狀態。** 沒有它，飛手用遙控器切到
> STABILIZE 之後，地面站會把機體歸類成「未知模式」然後繼續照自己的計畫走——
> 那是最危險的一種分岔。進到這個狀態時，**系統只觀察、不下任何指令**，直到
> 飛手把模式交還。

## 2. 允許的轉移

```
DISCONNECTED ──連上──▶ NOT_READY ──預檢過──▶ READY
                                                │
                          ┌─────── 上傳任務 ────┤（僅此狀態可上傳，見 §3-A）
                          │                     │
                          ▼                     ▼
                    （任務已就位）      arm ──▶ ARMED_GROUND ──▶ TAKING_OFF
                                                                     │到達高度
                                                                     ▼
                                        ┌──────────────▶ FLYING_MISSION
                                        │                    │      ▲
                                    resume                 pause    │
                                        │                    ▼      │
                                        └──────────────── HOLDING ──┘
                                                             │
                                    ┌────────────────────────┼────────────┐
                                    ▼                        ▼            ▼
                               RETURNING                  LANDING     （改航線
                                    │                        │          見 §3-A）
                                    └────────▶ 落地上鎖 ◀─────┘
```

**任何狀態**都可以轉到 `RETURNING`／`LANDING`／`EMERGENCY`——中止永遠是允許的。
**任何狀態**都可能被飛手搶進 `PILOT_CONTROL`，那不是我們的轉移，是既成事實。

## 3. 禁止的操作與理由

每一條都對應一個真實危害，不是假想。

### A. 空中上傳任務（**最高優先**）

| | 現況 | 應有 |
|---|---|---|
| 地面（`READY`） | 允許 | 允許——這是「存檔」 |
| 空中（`FLYING_MISSION`） | ~~允許，且立刻改道~~ → **2026-08-25 已擋下** | **擋下**。要改航線必須走 §3-A2 的三步 |

**實作**：`apps/command/app/main.py` 的 `_inflight_upload_block()`，擋在幾何
預檢**之前**——幾何預檢問的是「這份航線本身合不合理」，空中守門問的是「現在
做這件事會不會讓飛機立刻轉向」，一份完美的航線在空中上傳一樣危險。
回 409 並附 `how_to`（三步的合法路徑），前端直接顯示。
**刻意不提供 force 參數**：留一個繞道就等於沒擋。
12 格判定測試見 `scripts/test-inflight-guard.py`（兩家方言都驗）。

**理由**：見 §0.2 的實測。上傳不是一個資訊操作，它在空中是**立即生效的航線變更**。

**A2 空中改航線的唯一合法路徑（三步，每步都要機端確認）**：

1. `pause`：切 `HOLDING`（並可指定安全高度，見 §5）。**確認機端真的進了 hold**
   （讀回 `mode_verb`，不是看 ACK）。
2. `upload`：此時上傳新航線。機體在 hold，上傳不會造成移動。
3. `resume`：切回 `mission`。**確認機端真的進了 mission**。

這三步把「改航線」從一個瞬間動作變成一個**可被中斷的序列**——任何一步沒確認
就停在安全狀態（懸停），而不是繼續往一個沒人確認過的方向飛。

### B. 裸 arm（已實作，issues/031）

自動模式下裸 arm ＝ 立即自主起飛。已有 `_guard_bare_arm`，需帶顯式
`intent=start_mission` 才放行，且**繞過本身會留痕**。**保留，不得放寬。**

### C. 地面直接 `mission_start`

實戰教訓（2026-08-11）：地面直接 MISSION_START 在實機上會失敗。序列必須是
起飛 → 到達高度 → 才切 AUTO。已由 `mission/fly` 實作。
**禁止**在 `READY`／`ARMED_GROUND` 狀態下單獨呼叫 `mission_start`。

### D. 未驗證的動詞

能力四態的 gating 已經在做（`_require_capability`）。**不得為了方便而繞過**——
`_harness.py` 明寫「繞過 gating 去測，等於測一條產品上不存在的路徑」。

### E. 沒有定位時的位置類操作

`gps_fix < 3` 時禁止 takeoff／mission／位置類模式。理由不只是飛不好——
**無定位時 `GLOBAL_POSITION_INT` 回 0,0**，而那是哨兵值不是座標
（issues/036）。拿它當位置去算航線會得到荒謬的結果。

### F. 飛行中重啟後端服務

`issues/033` 已列為 deploy guard：偵測到任一真機 armed／在空中時，阻擋
backend/command 重啟、映像重建、`--reload` 類操作。**目前只靠人記得。**
本專案的 backend／command 是 bind-mount ＋ `--reload`——**改一行程式碼就會重啟
服務**，而飛行中重啟等於指令通道中斷。

## 4. 失效處理（誰負責哪一層）

| 失效 | 偵測者 | 處置 | 現況 |
|---|---|---|---|
| 遙控器失聯 | 飛控自己 | RC failsafe | ✔ 機端參數，**不得關閉預檢的 RC 檢查** |
| 地面站失聯 | **機上代理** | 5s 告警／30s RTL（僅 armed 時） | ✔ 已實作 |
| 飛控失聯（代理看不到心跳） | 機上代理 | 目前只告警 | ⚠ 未定案 |
| 低電量 | 飛控自己 | 機端 failsafe 參數 | ⚠ 未逐項核定（033） |
| 越界 | 飛控自己的 Geofence | — | ⚠ 我方預檢預設**不擋**，只報告 |

> **地面站失聯必須由代理處置的理由**：飛控的 GCS failsafe 盯的是 `SYSID_MYGCS`
> 的心跳，而那是**機上代理**——5G 斷了代理照樣心跳，飛控完全無感。整條鏈路上
> 只有代理看得見「地面沒人了」。

## 5. 需要新增的能力：指定高度的懸停

現行 `mode/hold` 是**純模式切換**，機體停在**當下高度**——無法「先升到安全
高度再暫停」。而那正是 §3-A2 第一步最該做的事（低空暫停時的障礙物風險最高）。

作法是 `MAV_CMD_DO_REPOSITION`，但**兩家的「維持現值」慣例不同**（issues/026
差異點 9 的同一條）：PX4 用 `NaN`，而 **ArduPilot 對 NaN 不回 ACK、指令靜默
丟棄**。所以要走驅動層抽象：加一個 `hold_plan(alt, lat, lon)` 動詞，兩家各自
實作，呼叫端不知道廠牌。**實作後必須在兩家 SITL 各驗一次**才開能力鍵。

## 6. 定案（2026-08-25 使用者裁定）

### 6.1 單一權威狀態機在代理，地面站是鏡像＋意圖來源

> **2026-08-25 修正**：原裁定是「兩邊都放並即時同步」。使用者隨後提出更好的
> 作法——**代理接收地面站的意圖，結合機端資訊自己判斷**。這個形狀更好，
> 而且**順帶解掉「兩個事實來源」的問題**：不是兩個狀態機互相同步，而是
> 一個權威（代理）、一個鏡像（地面站）。
>
> 好在哪，三個具體理由：
> 1. **地面站的位置永遠是過期的**——遙測經 5G 回來（RTT 22–40ms 且會抖），
>    而「離當前位置最近的航點」正是對位置最敏感的判斷。代理直讀飛控。
> 2. **意圖層的指令斷線後跑得完，步驟層的不行**。送了「暫停」還沒送「續飛」
>    就斷線，飛機會卡在半途懸停。「失聯照代理跑完」**只有在意圖層才成立**。
> 3. 與 026 待決點 1 的定案一致——「哪個航點安全」是載具領域知識。
>
> 介面契約見 [`agent-intent-protocol.md`](agent-intent-protocol.md)。

下面這段關於「同步什麼」的分析仍然成立，只是對象變成
**代理推鏡像、地面站推意圖**：

**但要先分清楚兩種「狀態」，否則同步會製造第二個事實來源：**

| 種類 | 例子 | 要不要同步 |
|---|---|---|
| **導出狀態** | `FLYING_MISSION`、`HOLDING`、`armed`、高度 | **不同步**。兩邊各自從**同一份機端遙測**導出，天然一致；同步它等於讓地面站的記憶有機會覆蓋機端事實，正好違反 §0.1 |
| **意圖狀態** | 「正在執行改航線序列的第 2 步」、「這趟飛的是任務 X」、「操作者已確認過這次變更」 | **必須同步**。它不在遙測裡，機端無從得知 |

也就是說：**同步的是意圖，不是狀態。** 導出狀態各算各的，因為它們算出來必然
相同（同一份輸入）；一旦不同，那本身就是一個要報警的事實（見 §6.4）。

失聯後代理**照最後同步到的意圖繼續執行**——它手上有完整的任務與序列進度，
不需要地面站。

### 6.2 續飛從「離當前位置最近的航點」開始

⚠ **「最近」必須加三個限定，否則它會是個危險的規則：**

1. **只考慮導航航點**，排除 `NAV_TAKEOFF`／`NAV_LAND`／`NAV_RETURN_TO_LAUNCH`
   與所有 `DO_*` 設定項。續飛到一個 takeoff 項＝叫一台在空中的機重新執行起飛；
   續飛到 land 項＝當場降落。
2. **用水平距離，不用 3D 距離。** 3D 最近可能是一個**正下方但低很多**的航點，
   續飛過去＝立刻下降。高度差不該把飛機往下拉。
3. **選出來的航點必須在確認畫面上顯示**（§6.3），由人看過才送。系統沒有障礙物
   感知——「最近」只是幾何最近，不代表**飛過去的路徑**是安全的。

### 6.3 飛行中改航線必須經 UI 二次確認，且要說明「會怎麼調整」

確認畫面**不得只問「確定嗎？」**——那種確認框沒有資訊，人只會照按。必須顯示：

| 要顯示的 | 為什麼 |
|---|---|
| 目前位置與目前正在飛的航點 | 讓人知道「現在在哪」 |
| 新航線的完整幾何（疊在地圖上） | 讓人看出它跟舊的差在哪 |
| **續飛航點是哪一個**（依 §6.2 選出，在地圖上標出來） | 這是系統替人做的判斷，必須攤開 |
| **暫停後的懸停高度**，以及它與當前高度的差 | 會不會先爬升／下降 |
| **從目前位置飛到續飛航點的直線距離與方位** | 「飛機下一秒會往哪走」——這是最容易出事的一步 |
| 這是三步序列（pause→upload→resume），**每步都可以中止** | 讓人知道按下去不是不可逆的 |

> **禁止把這個確認做成 `mission_upload` 的預設行為。** 地面上的上傳不需要它，
> 而每次都跳確認框會訓練人閉著眼睛按——然後空中那次也照按。
> **確認只在「機在空中」時出現**，讓它保持稀有、保持有意義。

### 6.4 兩邊狀態不一致時

導出狀態理論上必然相同（同一份遙測）。**不同就是有事**：可能是遙測丟包、
時間差、或某一邊的判定式有 bug。處置：

* 以**機端遙測**為準（§0.1），不是以任何一邊的記憶為準。
* **記一筆事件並在畫面上顯示**——不一致本身是要被看見的資訊，靜靜地選一邊
  等於把 bug 藏起來。

## 7. 失聯處置：**裁定選項 C**（2026-08-25）

逐狀態決定，並加兩個上限。完整規則見
[`agent-intent-protocol.md`](agent-intent-protocol.md) §6。

* `FLYING_MISSION` → **跑完任務再 RTL**
* `HOLDING`／`TAKING_OFF` → **立刻 RTL**
* **改航線序列進行中 → 立刻 RTL（不論當下是哪個狀態）**：飛機停在一個沒有人
  確認過的中間狀態，而接下來每一步都需要地面站
* `ARMED_GROUND` → 只告警（實作時改掉的一格，理由見協定 §6）
* `RETURNING`／`LANDING` → 不介入；`PILOT_CONTROL` → **永不介入**
* 上限：單飛時間 > 120s（暫定）、或電量 < 40%（暫定）→ 一律立刻 RTL

**2026-08-25 已實作於代理**（`_loss_state`／`_loss_verdict`），16 格判定表
測試通過（`tools/link-loss-table.py`，含反向驗證）。兩個上限值仍是暫定，
待實機續航測試定案。

### 原始的三選項與代價（保留備查）

§6.1 說失聯後照代理的意圖**跑完**；而代理現在的實作是
**地面站失聯 30 秒且 armed → 下 RTL**（`LINK_ACTION=rtl`，2026-08-24 實測驗過）。

**兩者不能同時成立。** 這是飛安決策，需要明確裁定：

| 選項 | 行為 | 代價 |
|---|---|---|
| **A. 現行**：失聯 30s → RTL | 保守，人一失去監看就回家 | 自動任務會因為一次 5G 抖動而中斷；而 5G 抖動在本場域是常態 |
| **B. 跑完再 RTL** | 失聯時繼續執行任務，**任務結束後自動 RTL** | 失聯期間飛機仍在按計畫飛，但**沒有人看得到它**。若任務本身有問題，沒人能中止 |
| **C. 分狀態決定** | `FLYING_MISSION` → 跑完再 RTL；其餘狀態（HOLDING、改航線序列進行中、PILOT_CONTROL）→ 立刻 RTL | 較貼近意圖，但規則變複雜，複雜的安全規則本身是風險 |

**我的建議是 C，並加兩個上限**：任務剩餘時間超過 N 分鐘就不續飛（避免無人監看
的長時間飛行）、電量低於門檻一律 RTL。因為「跑完」在一個 3 分鐘的任務與一個
40 分鐘的測繪任務上，風險完全不同。

**在裁定之前，代理維持現行的 A**——不擅自放寬既有的安全行為。
