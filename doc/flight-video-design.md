# 飛行影像設計（issue 022）

- 狀態：**技術方案（未動工）**，2026-08-12
- 範圍：地面站錄製架次影像 → 回放同步播放；即時畫面沿用既有 `video_url` 骨架
- 依據：issue 022 使用者定案（地面站從串流錄／保留 30 天／先用測試來源）

本文的數字都是**本機實測**（`linuxserver/ffmpeg`、`bluenviron/mediamtx`），
不是估算；量測方法附在 §7 末，可複驗。

## 0. 一句話結論

用 **MediaMTX 獨立容器**收流、錄 **fragmented mp4 分段**、每段在 DB 記
**絕對時間錨點**，回放以時間對齊、缺片段照實留白。**不轉碼（remux）**——
檔案大小由機上編碼器決定，省空間要動的是相機端的解析度/幀率/位元率。

## 1. 元件選型

| 方案 | 判定 | 理由 |
|---|---|---|
| **MediaMTX 獨立容器** | ✅ **建議** | 收流／錄製／保留清理／瀏覽器播放四件一次滿足；與 backend 完全解耦 |
| ffmpeg 常駐容器 | 備案 | 錄製可行，但即時串流轉發、保留清理、播放端點都要自己寫 |
| backend subprocess | ❌ **否決** | backend 掛 `--reload`，改一行程式就重啟＝**錄影中斷**。錄影不該綁在最常改動的服務上 |

MediaMTX 預設值（官方 `mediamtx.yml` 實測確認）已經對上本案需求：

```yaml
record: true
recordFormat: fmp4              # 見 §2：這是硬需求，不是偏好
recordPath: /rec/%path/%Y-%m-%d_%H-%M-%S-%f
recordSegmentDuration: 10m      # 預設 1h，本案建議縮短（見 §4）
recordDeleteAfter: 720h         # 30 天，對齊量測資料生命週期
api: true                       # 架次觸發用（見 §3）
playback: true                  # 依時間區間取片段
```

### ⚠️ 接入方向更正（2026-08-12，使用者提供機端事實）

**RB5 上的 RTSP 不會主動推送，要由系統端主動拉。** 原設計寫的是「機端主動推進
8554」，對 RB5 不成立，已更正為**地面站拉流**（MediaMTX 原生支援：path 設
`source: rtsp://<機IP>:<port>/<path>`，它當 RTSP client 去連）。

**但這與系統其餘部分的假設相反，必須實測而非假設**：MAVLink 與 5G 量測資料都
刻意設計成**機端主動外連**，理由是 5G 的機端通常在 NAT 後、地面站連不進去。
拉流要求的正好是反過來的「**地面站能 reach 機端 IP**」——這在使用者的私有 5G
＋VPN 拓撲下**可能成立也可能不成立**，是本案最需要現場驗證的前提。

- 成立 → 用拉流（本節主方案）。
- 不成立 → 退回推流：在 RB5 上跑一支推流程序（ffmpeg 或 MediaMTX）把相機
  RTSP 推到地面站 8554。**兩種 MediaMTX 都吃，不必改架構**，只是機端多一個
  要顧的程序（與「運行期間零人為連線」的原則衝突較大，所以是備案）。

**拉流反而有一個好處**：`sourceOnDemand` 可以做到**沒人看也沒在錄時就不拉流**
——閒置的機不佔 5G 上行。推流模式下機端是持續送的，不管有沒有人要。考慮到
「影像與量測資料共用上行、錄影本身可能影響被測鏈路品質」這個研究效度問題
（見 §9），這個差別不只是省頻寬。

**設定分兩個 URL，不要混用一欄**：
- `drones.video_url`（現有）＝**瀏覽器播放位址**（地面站 WHEP）。
- **相機來源 URL**（新增）＝地面站要去拉的 `rtsp://<機IP>/...`。兩者用途、
  指向、使用者都不同（一個給前端播放器，一個給 MediaMTX 當 source）。

拓撲（**主方案＝地面站拉流**；箭頭方向就是連線發起方向）：

```
                    ┌──(5G) 地面站主動連進去拉 ──┐
機上相機 RTSP server ◀───────────────────────────┤ 地面站 MediaMTX ─┬─▶ 錄檔 fmp4 分段
（RB5，不主動推）                                  └─▶ WHEP → 瀏覽器即時畫面

備案（拉不到時）：機上跑推流程序 ──RTSP 推──▶ 地面站 MediaMTX:8554（其餘相同）
```

地面站這台同時是**即時畫面的來源**：前端 `video_url` 從「指向每台機」改成
指向地面站的 WHEP 端點（`http://<GS>:8889/uav-<sysid>/whep`），少一條跨 5G
的瀏覽器直連，且與錄的是同一份流。

## 2. 為什麼一定要 fragmented mp4（實測，非偏好）

一般 mp4 的 `moov` atom 寫在**檔案結尾**：行程被砍就沒有索引，整個檔報廢。
實測（錄製中 `SIGKILL`）：

| 格式 | 已寫入 | 事後能否播放 |
|---|---|---|
| 一般 mp4 | 45,824 KB | ❌ `moov atom not found`＝**45 MB 全損** |
| fragmented mp4 | 45,056 KB | ✅ ffprobe 讀到 133 秒，完整可播 |

本案「斷流是常態」「地面站可能重啟」，用一般 mp4 等於每次意外都丟掉整個架次
的影像。**fmp4 是硬需求**。

> 瀏覽器相容備註：fMP4 現代瀏覽器 `<video>` 可直接播。若實測遇到個別瀏覽器
> 不吃，安全閥是落地後 `ffmpeg -i seg.mp4 -c copy out.mp4` **remux 不轉碼**
> （秒級、不掉畫質），不影響本設計。

## 3. 架次關聯（沿用 020 因果鏈）

`armed → disarmed` 觸發，但**不靠「準時開關」保證正確性**：

- **開錄**：armed 時經 MediaMTX API 打開該 path 的 `record`。
- **收錄**：disarmed 後**延遲數秒**再關（收尾片段不被切掉）。
- **歸屬以時間為準**：片段屬於哪個架次＝用片段的絕對時間區間去對
  `flight_sessions [started_at, ended_at]`，**不是**用開關事件配對。
  這樣即使開關晚了幾秒、或服務中途重啟，歸屬仍然正確。

**不錄假資料**（issue 022 明列）：`origin='test'` 的架次與 `is_simulated`
的機預設**不錄**，用設定開關可放行（開發時要錄測試來源才打開）。否則測試
殘留會直接吃掉磁碟——這比量測資料的殘留貴上千倍。

### Schema（照慣例與 `migrate()` 同批更新 `doc/data-schema.md`）

```sql
CREATE TABLE video_segments (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  drone_id     UUID NOT NULL REFERENCES drones(id) ON DELETE CASCADE,
  session_id   UUID REFERENCES flight_sessions(id) ON DELETE CASCADE,  -- 事後對齊可為 NULL
  started_at   TIMESTAMPTZ NOT NULL,   -- ★ 影片第 0 秒＝這個絕對時間（錨點）
  -- 另在 flight_sessions 加 video_mode（on/off/no_source），見 §6b：
  -- 「沒錄」與「錄了但斷流」必須分得開，零片段才有得判讀
  duration_s   DOUBLE PRECISION,       -- 實際長度（收檔後回填）
  path         TEXT NOT NULL,          -- 相對於錄影根目錄
  codec        TEXT,                   -- h264/h265…（回放相容性判斷）
  width        INT, height INT, fps    DOUBLE PRECISION,
  bytes        BIGINT,
  source       TEXT NOT NULL DEFAULT 'ground',  -- 地面站錄（未來若有機上錄可分辨）
  UNIQUE (drone_id, started_at)
);
CREATE INDEX idx_vseg_session ON video_segments (session_id, started_at);
```

## 4. 時間對齊與「缺片段不得假裝連續」（硬約束）

- **錨點逐段獨立**：每段一列 `started_at`，**不假設段與段相接**。
- **錨點事實源是 DB 不是檔名**：實測 `-strftime` 用的是**寫檔當下的牆鐘**，
  非即時輸入時會與媒體時間脫節；即時流雖然大致相等，仍以入庫的 `started_at`
  為準（檔名只當人類可讀線索）。
- **回放 seek**：目標絕對時間 `T` → 找 `started_at <= T < started_at+duration`
  的段 → 在該段內 `offset = T - started_at`。跨段就換檔，不做拼接。
- **缺片段＝資料，不是瑕疵**：兩段之間的空白**照實回報**（回放頁畫成缺口、
  播放到缺口就停/跳，不靜默續播下一段假裝連續）。斷流時刻正是 RF 劣化的證據，
  磨平它等於湮滅研究資料。
- 建議 `recordSegmentDuration: 10m`（預設 1h）：段越短，崩潰損失上限越小、
  時間定位越細；代價是檔案數量變多（30 天 × 3 台仍只有數千個檔，可接受）。

## 5. 測試來源（實測結論）

- 機隊映像**沒有** `sitl_rtsp_proxy`、也沒有 `gst-launch-1.0`（只有
  gst-rtsp-server 的 dev 套件），**不能直接用**。
- 建議：`ffmpeg` 推測試圖樣進地面站 MediaMTX，逐台一條 path：
  ```bash
  ffmpeg -re -f lavfi -i testsrc2=size=1280x720:rate=30 \
         -c:v libx264 -preset veryfast -tune zerolatency -pix_fmt yuv420p \
         -f rtsp rtsp://localhost:8554/uav-1
  ```
  `-re` 是關鍵（照真實時間推流，否則瞬間灌完、時間錨點失真）。
- **模擬環境維持推流不動**（測試鷹架，MediaMTX 推拉並存都吃）——真相機走的是
  拉流（見 §1 接入方向更正），兩者共用同一套錄製/回放設計，只有 path 的
  `source` 設定不同：測試流是 `publisher`（被推進來），真機是
  `rtsp://<機IP>/...`（我方去拉）。

## 6. 磁碟預算與保留策略（使用者 2026-08-12 定案）

只在 armed 時錄，所以耗量由**飛行時數**決定，不是牆鐘時間。以 3 台、
每天 2 飛行小時計：

| 設定 | GB/飛行小時/台 | 3 台 × 2h/天 | 7 天（**定案**） | 30 天（參考） |
|---|---|---|---|---|
| 1080p30（離線編碼） | 2.26 | 13.6 GB/天 | 95 GB | 407 GB |
| 720p30（離線編碼） | 1.17 | 7.0 GB/天 | 49 GB | 211 GB |
| 720p15（離線編碼） | 0.83 | 5.0 GB/天 | 35 GB | 150 GB |
| **720p15（預設；實流實測）** | **1.17** | **7.0 GB/天** | **≈49 GB** | 211 GB |
| 480p15（離線編碼） | 0.36 | 2.2 GB/天 | 15 GB | 65 GB |

> 表格讀法：前四列除最後一列外都是**離線編碼**（`-crf 23` 正常調校）的量測；
> 粗體那列是**實際跑完串流鏈路**的量測。**「720p30 離線」與「720p15 實流」
> 剛好同為 1.17，是巧合不是筆誤**——成因不同：前者是幀率高但壓縮正常，後者是
> 幀率減半但 `-tune zerolatency` 關掉了前瞻壓縮。要拿來估磁碟的是**粗體那列**。

> ⚠️ **數字修正（2026-08-12，端到端實測後）**：先前給的 720p15 ≈0.83 GB/hr 是
> **離線編碼**（`-crf 23` 正常調校）的值。實際走完「推流 → MediaMTX → 錄檔」
> 之後量到 **1.17 GB/hr**——因為即時串流慣用 `-tune zerolatency`（關掉 B-frame
> 等前瞻壓縮以降延遲），代價就是約 +40% 位元率。**即時串流的現實值要用 1.17**。
> 於是 7 天預算是 **≈49 GB**（不是 35 GB）。結論不變（現有 ≥100GB 磁碟仍夠用），
> 但數字要誠實。真實航拍素材可能再高一些，Phase 3 用真相機再量一次。

**定案：影像保留 7 天、預設 720p15（≈49 GB，實流實測值）——影像保留與量測
資料的 30 天脫鉤。** 理由：影像比量測資料大兩三個數量級，跟著留 30 天要數百 GB；研究要
長期保留的是量測資料，**重要架次的影像先匯出**。

- `recordDeleteAfter: 168h`（7 天）打底，另做一支與 `flight_sessions` 連動的
  清理（刪架次時一併刪其片段），兩層都有才不會出現孤兒檔。
- ⚠️ **這個磁碟結論綁定「7 天 ＋ 720p15」這組前提**：改 1080p（95 GB）或把
  保留拉回 30 天（150 GB）就要重算、可能要加碟。已寫進 `deploy-checklist.md`。

## 6b. 「沒錄」與「錄了但斷流」必須分得開（使用者定案）

錄影**預設開**，特定實驗可關（影像與量測共用 5G 上行，錄影本身可能影響被測
的鏈路品質——見 §9）。但關掉時**必須在架次上留痕**：事後分析看到「這趟沒有
影像」，要能分辨是**沒錄**還是**錄了但鏈路斷光**——兩者對研究的意義完全相反
（前者是實驗設定，後者是實驗結果）。

`flight_sessions.video_mode TEXT`：

| 值 | 意義 | 判讀 |
|---|---|---|
| `on` | 本趟預期要錄 | 有片段＋有缺口＝**錄了但斷流**（研究資料）；**零片段＝異常**（該錄卻整趟沒收到流） |
| `off` | 本趟刻意不錄 | 零片段是預期，不是異常 |
| `no_source` | 該機沒有影像來源 | 零片段是預期 |

架次建立時寫入（依設定開關與該機是否有來源決定），不靠事後推測。

> **三態分離的實證價值（2026-08-12 真實案例，寫給日後想簡化它的人）**：一次多人
> 共用環境的意外中，某個架次的錄影檔在飛行途中被誤刪。系統回報 `missing`
> （該錄卻沒錄到）→ 前端立刻察覺並回報 → 十分鐘內查到根因。**若當初把 `missing`
> 併進 `off`（「本趟未啟用錄影」），同一件事會被讀成設定問題，沒有人會去追**——
> 資料就這樣靜默少一塊。省下一個列舉值的代價，是失去「知道自己壞了」的能力。

## 7. 檔案大小：畫質 vs 大小 vs 瀏覽器相容（實測）

30 秒樣本 ×120 推算，`testsrc2`（帶運動）。**本節全部是離線編碼（`-crf 23`
正常調校）的量測**，用途是「同條件下比較各選項」——所以下面的比較是
apples-to-apples、結論成立。實際串流會因 `-tune zerolatency` 各加約 40%
（見 §6 的實流實測），估磁碟請用 §6 的粗體列，不要用本節數字。

| 設定 | 30s 實測 | GB/hr | 瀏覽器 |
|---|---|---|---|
| 1080p30 H.264 crf23 | 19.3 MB | 2.26 | ✅ 全支援 |
| 720p30 H.264 crf23 | 10.0 MB | 1.17 | ✅ 全支援 |
| **720p15 H.264 crf23** | **7.1 MB** | **0.83** | ✅ 全支援 |
| 480p15 H.264 crf23 | 3.1 MB | 0.36 | ✅ 全支援 |
| 720p30 **H.265** crf28 | 7.5 MB | 0.87 | ⚠️ Chrome/Firefox 預設不播 |

**關鍵結論（回答「檔案太大就換輕量格式」）**：

1. **不需要換編碼。** H.265 只省 26%（1.17→0.87），卻要賭瀏覽器相容；
   同樣是 H.264，把幀率降到 15fps 就得到 **0.83 GB/hr——比 H.265 還小、
   且零相容風險**。研究看的是鏈路品質與畫面劣化，15fps 完全夠。
2. **省空間的順序**：幀率 → 解析度 → 位元率，最後才考慮換編碼器。
   （`mp4` 是容器不是編碼，改副檔名不會變小。）
3. **建議不轉碼（remux）**：地面站照收到的樣子存。理由三個——
   3 台並行轉碼的 CPU 成本、轉碼會**改動畫面劣化的樣貌**（那正是研究證據）、
   以及來源已是 H.264 時轉碼純屬多餘。**於是大小的控制點在機上相機設定**
   （建議 720p15、2 Mbps 上限），這同時也減輕 5G 上行負擔。
4. **硬條件把關**：來源必須是 **H.264 + yuv420p**，否則瀏覽器播不了。
   MediaMTX 收流時即可得知編碼，入庫寫進 `video_segments.codec`；非 H.264
   就告警（並可選擇性地只對該路轉碼），**不要靜默存一個播不出來的檔**。

> 量測方法（可複驗）：`docker run --rm linuxserver/ffmpeg -f lavfi -i
> testsrc2=size=WxH:rate=R -t 30 -c:v libx264 -crf 23 -preset veryfast
> -pix_fmt yuv420p out.mp4`，取位元組數 ×120。位元率換算交叉驗證：
> 1.17 GB/hr ≈ 2.66 Mbps，與 crf23 720p30 的典型值一致。
> **注意**：合成圖樣比真實航拍畫面易壓縮，真實素材會**偏高**；正式數字要等
> 真相機接上再量一次（Phase 3 驗收項）。

## 8b. API 契約（與 UI/UX ui-spec §5.4 對稿；前端據此實作）

### `GET /api/sessions/{id}/video`

```jsonc
{
  "retention_days": 7,              // ★ 動態帶出，UI 不寫死（見下「為何」）
  "video_status": "available",      // available | off | no_source | expired | missing
  "segments": [
    { "id": "…", "started_at": "2026-08-12T03:44:09.271686Z",  // ★ 影片第 0 秒的絕對時間
      "duration_s": 600.0, "codec": "h264", "width": 1280, "height": 720,
      "fps": 15, "bytes": 421337600,
      "url": "/api/video/segments/<id>/file" }                  // 同源直供，免 CORS
  ]
}
```

**`retention_days` 為何一定要動態帶**：保留天數的事實源是 `.env` 的
`VIDEO_RETENTION_DAYS`，**同一個變數同時餵**錄製器（`MTX_PATHDEFAULTS_
RECORDDELETEAFTER`，真正在刪檔的那個）與 backend（本欄）。UI 寫死或後端另設
一份，就會出現「畫面說 7 天、實際清 14 天」的假話。改保留策略＝只改 `.env`，
前端零改、文件與實際設定不會漂移。

**`video_status` 五態**（後端算好，UI 不做日期運算；UI 的三種空態嚴格對應）：

| 值 | 意義 | UI |
|---|---|---|
| `available` | 有片段（**段間可能有空白**） | 播放器＋涵蓋帶；空白處照實留白 |
| `off` | 本趟刻意未啟用錄影（opt-out） | 空態句「本趟未啟用錄影」 |
| `no_source` | 該機沒有影像來源 | 空態句「這台沒有影像來源」 |
| `expired` | 已過保留期、檔案已清除 | 空態句「影像已過保留期（N 天），已清除」← N 用 `retention_days` |
| `missing` | 保留期內、該錄卻整趟沒收到流＝**異常** | 不可與上面三者混用；這是故障不是空態 |

> `available` 但**有缺口**≠空態：缺口是斷流的證據（研究資料），畫在涵蓋帶上。
> 「沒錄」（`off`）與「錄了但斷流」（`available` 有缺口）意義相反，不得同句。
> 清理時**片段列與檔案一起刪**，不留指向已刪檔的列——否則涵蓋帶會指向空氣。

### ⚠️ `started_at` 的精確語意（研究效度攸關，必讀）

`started_at` ＝**這一格抵達地面站的時刻**，**不是相機拍下它的時刻**。兩者相差一個
管線延遲（機上編碼＋傳輸＋抖動緩衝）。

- **時鐘源已驗證同源**（2026-08-12 實測）：錄製器／DB／backend 是同一台 host 上的
  容器，共用核心時鐘。量測方法：比對段**結尾** vs 收錄指令（**−0.192s**）——用不受
  關鍵影格影響的那一端才驗得準；段起始有 +1.4s 是等 I-frame（`-g 30` @15fps 每 2 秒
  一個關鍵影格），**不是錨點錯誤**：檔案第 0 影格就是那一刻拍到的影格。
- **模擬環境基準：管線延遲 < 0.5s**（2026-08-12 實測 **0.41s**，方向恆定：
  **UI 定位到遙測時刻 T，看到的是 T+0.41s 的畫面**）。
  成因**不是**等關鍵幀——實驗推翻了這個假設：同一條流分別用 1 秒與 4 秒 GOP 錄製，
  「錨點−錄製指令」為 +1.616/+1.519s（GOP 1s）與 +1.554/+1.555s（GOP 4s），
  **與 GOP 無關**（若是等關鍵幀，4 秒 GOP 應明顯較久）。完整鏈路：
  錄製指令 T → 錨點 T+1.55 → 首幀內容產生於 T+1.96。
- **現階段不修正這 0.41s，改為記載**（2026-08-12 PM 核可）。理由：唯一正確的修法是
  拿第一幀自己的時戳蓋錨（要在 backend 加媒體探測能力＝架構改動）；而**硬編
  0.41s 補償一定會錯**——那是這條合成流在 loopback 的值，真相機的編碼器／GOP／
  網路都不同，拿它去「修正」比不修更糟。
  > **重啟觸發條件**（滿足任一就回來重議「讀第一幀時戳蓋錨」）：
  > (a) **真機實測偏差 > 1s**（設計師的阻斷線）；
  > (b) 研究上出現「影像與 SINR 對照的時間精度不足」的實際需求。
- **真機 5G：未知，且與鏈路品質相關**——這是本案最危險的失真，比恆定偏移難抓：
  > 畫面愈糊（鏈路愈差）該影格的時戳愈晚，於是「畫質劣化」看起來總是**發生在**
  > SINR 下降**之後**，使用者可能因此推出**錯誤的因果方向**。而且好鏈路時完全正常，
  > 最難察覺。
  它不是可事後校正的固定偏移，因為它與被研究的自變數相關。
- **處置（誠實優先，不假裝精準）**：UI 於影片窗／回放頁標示「影片時間＝抵達地面站
  時刻，與拍攝時刻差一個傳輸延遲」；真機驗收**在好鏈路與劣化鏈路各測一次**（兩者
  偏移不同即證實延遲與鏈路相關）。真要根治需機端配合——RTCP sender report 的 NTP
  對映，或機上把時碼燒進畫面（Phase 3+，需真機支援）。

### 其他

- **不轉碼原樣**：`codec`/`width`/`height`/`fps` 是**實際收到的流**的屬性，
  非後端指定。畫質劣化是研究證據，後端不美化（實測確認錄下來就是 h264/
  yuv420p/1280x720/15fps，與來源一致）。
- **即時畫面**：地面站 WHEP `http://<GS>:8889/uav-<sysid>/whep`（與錄的是同一份流）。

## 9. 未定／風險

- **fMP4 在目標瀏覽器的實播**：需前端實測（安全閥見 §2）。
- **真實素材的大小**：合成圖樣偏低估，Phase 3 必須重量。
- **5G 上行是否吃得下**：影像與量測資料共用鏈路，錄影可能反過來影響被測的
  鏈路品質——**這是研究方法論問題不只是工程問題**，建議與使用者確認是否要
  在特定實驗中關閉影像（設定開關預留）。
- **時鐘**：地面站時鐘決定錨點；若地面站與機上時鐘差異大，影片與遙測會系統性
  偏移。建議地面站開 NTP，並在 Phase 1 驗收時用一次「畫面裡的事件 vs 遙測
  時間」交叉核對。
