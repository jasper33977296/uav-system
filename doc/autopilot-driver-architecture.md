## 0. 一句話建議

**先定「動詞介面」，再分兩批把現有 10 處差異搬進去**：MAVLink 家族走**程序內
驅動**、非 MAVLink 未來走**獨立 adapter 程序**（同一份介面，兩種實作形態）；
跨服務用**共用套件目錄＋repo 根 build context**，不再靠副本＋漂移測試；
能力四態改由**一致性測試的結果**決定，不再人工判斷。

## 1. 決策一：驅動放哪裡

**建議：混合，但介面只有一套。**

| 機型 | 形態 | 理由 |
|---|---|---|
| MAVLink 家族（PX4／ArduPilot／未來其他） | **程序內模組** | 它們共用整條 MAVLink 傳輸與路由。拆成獨立程序等於為每一則訊息加一層 IPC，或把 router 複製一份——**成本很高而收益是零**（抽象效益在介面，不在程序邊界） |
| 非 MAVLink（DJI 等需 vendor SDK） | **獨立 adapter 程序** | 它們帶自己的執行期、相依與授權條款，**本來就無法共用 MAVLink 程式碼**；隔離在獨立程序也讓 SDK 崩潰不會拖垮主服務 |

**關鍵設計：介面不隨形態改變。** 系統呼叫的永遠是同一組動詞；「程序內」只是
本地實作，「獨立 adapter」是同一份契約的遠端實作。這樣未來把某個驅動從程序內
移出去（或反過來）**不需要動呼叫端**。

> 使用者原話是「獨立成不同的工具」——我理解那個訴求的核心是**隔離與可替換**，
> 而不是「一定要是獨立程序」。介面統一就達成了訴求；程序邊界只在技術上必要時
> （非 MAVLink SDK）才付出。這點若理解有誤請指正，它會改變整個提案的成本。

## 2. 決策二：跨服務怎麼共用

現況：`backend`（解碼：模式名、readiness、串流初始化）與 `command`（編碼：切
模式、起飛、任務上傳）是兩個服務、**build context 各自獨立**。模式表已經撞過
這道牆，當時決議是「canonical 表＋副本＋drift-guard 測試」。

**建議：改用共用套件目錄 `libs/autopilot/`＋repo 根 build context。**

| 選項 | 評估 |
|---|---|
| 維持副本＋漂移測試 | ❌ **漂移測試是事後偵測**：它在兩邊已經不一致之後才告訴你。10 處差異、還在增加，副本數量 × 差異數量就是出錯面積 |
| 發布成內部套件（pip） | ❌ 單一 repo 內為了共用一個目錄而引入版本發布流程，是**沒有收益的儀式** |
| **repo 根 build context ＋ `libs/autopilot/`** | ✅ **一份程式碼、編譯期就一致**，不需要任何漂移偵測。代價：build context 變大（用 `.dockerignore` 收斂）、共用層改動時兩個映像都要重建——**而那正是正確行為** |

驅動天生跨兩服務（解碼在 backend、編碼在 command），所以它是**真正共用的程式碼**
而非重複邏輯——這是選共用目錄而非各自複製的根本理由。

## 3. 決策三：一致性測試套（conformance suite）

**建議：把 015 的驗收清單正式化成每個驅動都必須通過的同一套測試，並讓能力值
由測試結果決定。**

但這裡有一個**必須分清楚的區別**，否則會做出假的自動化：

| 類別 | 問的問題 | 何時判定 | 例子 |
|---|---|---|---|
| **一致性測試** | 「**我們的程式**會不會講這個方言？」 | CI／SITL，離線 | 模式號對不對、任務 seq 慣例對不對、起飛序列對不對 |
| **執行期前提檢查** | 「**這一台機**的設定接不接受我們？」 | 連線時，逐台 | `SYSID_MYGCS=254`？串流請求收到回應？ |

**能力＝兩者的交集**：`ok` 當且僅當「驅動通過該動詞的一致性測試」**且**「這台
機的執行期前提滿足」。把兩者混為一談會得到兩種錯誤——用測試結果宣告一台沒設好
的機可用，或用單機設定否定驅動本身的正確性。

**還有一個誠實邊界要寫進能力值**：一致性測試跑在 **SITL**，SITL ≠ 真機。所以
能力宣告的準確語意是「**對 <韌體版本> 的 SITL 驗證通過**」，不是「真機保證可用」。
建議 capability reason 帶上驗證基準（韌體版本／日期），讓操作員知道這個 `ok`
的證據強度。

實作形狀（沿用既有慣例，不新增框架）：`scripts/conformance/<verb>.py` 各自可獨立
執行、輸出結構化結果；驅動宣告 `capabilities()` 時讀該結果，而不是寫死字典。

## 5. 業界先例：QGroundControl 的 FirmwarePlugin（**已查證**）

快照位置：`reference/qgc/`（`FirmwarePlugin.h`／`FirmwarePluginManager.h`／
`PX4FirmwarePlugin.h`／`APMFirmwarePlugin.h`，取於 2026-08-12）。以下數字都是
從該快照量出來的，不再是既有認知。

QGC 面對的是**完全相同的問題**（同時支援 PX4 與 ArduPilot），解法就是本提案的
形狀：`FirmwarePlugin` 抽象基底 ＋ 兩個實作 ＋ 依 `MAV_AUTOPILOT` 選用的管理器。

### 5.1 對照 (a)：什麼留在共用層 → **我們的邊界畫對了**

`FirmwarePlugin.h` **沒有任何成員狀態**，而幾乎每個方法都把 `Vehicle*` 當參數
傳進來：

```cpp
virtual void initializeVehicle(Vehicle* vehicle) {}
virtual bool isCapable(const Vehicle* vehicle, FirmwareCapabilities capabilities) const;
virtual QStringList flightModes(Vehicle* vehicle);
```

也就是說 **plugin 是無狀態的「行為建議者」，機體狀態全部留在共用的 `Vehicle`**。
這正是本提案的設計：驅動不持有狀態，遙測狀態留在 `backend/state.py`。**這一點
不需要修改。**

### 5.2 對照 (b)：介面有多大 → **比我們的 10 個大，但沒有 8 倍**

| 量測 | 數字 |
|---|---|
| `FirmwarePlugin.h` 虛擬方法總數 | **81** |
| PX4 覆寫 / APM 覆寫 | 50 / 42 |
| **兩家都覆寫**（＝真正的分歧軸） | **40** |
| 其中落在我們業務範圍內 | **約 30** |

81 是**誤導性的比較**：其中很大一塊是我們刻意不做的事（UI 機體圖、韌體版本
檢查、參數 metadata 檔、搖桿 TX 模式、馬達配置）。誠實的比較是 **30 對 10**。

而這 30 之中，**大部分只是粒度差異而非我們漏掉的差異**：

| QGC 方法群 | 數量 | 對應我們的 |
|---|---|---|
| 模式（`flightMode`／`flightModes`／`setFlightMode`／各具名模式存取子） | ~7 | 差異 1、2 |
| guided 動作（`guidedModeTakeoff`／`RTL`／`Land`／`GotoLocation`／`ChangeAltitude`／`startMission`／`pauseVehicle`…） | ~12 | 差異 3、4（＋未來 `mission_start`） |
| 任務慣例（`supportedMissionCommands`／`missionCommandOverrides`／`sendHomePositionToVehicle`） | ~4 | 差異 5 |
| 連線初始化 `initializeVehicle` | 1 | 差異 6 |
| 能力 `isCapable` | 1 | capabilities |
| **每廠牌數值限制**（`minimumTakeoffAltitudeMeters`／`maximumHorizontalSpeedMultirotorMetersSecond`／空速上下限…） | ~5 | ❌ **沒有對應** |
| **逐訊息方言修正**（`adjustIncomingMavlinkMessage`／`adjustOutgoingMavlinkMessageThreadSafe`） | 2 | ❌ **沒有對應** |

**結論：我們漏掉的不是 20 個差異，是 2 個「軸」。** 其餘都是同一批知識切得更細。

### 5.3 兩個漏掉的軸（兩個我們都已經以臨時形式踩過）

**軸一：每廠牌數值限制。** QGC 讓 `minimumTakeoffAltitudeMeters` 逐韌體覆寫；
我們的起飛高度是 `command/main.py:290` 的 `takeoff_alt: float = 10.0`——一個
**全域 API 預設值，不分廠牌**。目前沒出事，只因為 10 m 對兩家都安全。這是
「條件變了誰會發現」的同一個形狀：**沒有任何機制會在某廠牌下限不同時告訴我們**。

**軸二：逐訊息方言修正。** `adjustIncomingMavlinkMessage` 是**兩家都覆寫**的方法
——不是 APM 特例。它的存在說明：**有一類方言差異不是動詞，是「同一則訊息在不同
廠牌要先修正再解讀」**。我們的 `mavlink_rx.py:238` `_handle()` 是單一 dispatch
配內嵌分支，沒有這個鉤子；差異 8（EKF 訊息名）其實就是這一類，我們用 if 分支
硬解了。

### 5.4 這對介面定義的影響

驅動契約在動詞之外要再加兩項（**新增，不是重畫**）：

```
Driver.limits()                      → 每廠牌數值限制（起飛下限、速度上限…）
Driver.adjust_incoming(msg) / adjust_outgoing(msg)   → 逐訊息方言修正鉤子
```

`adjust_incoming` 同時讓差異 8 有正確的歸屬：它不該是 `decode_telemetry()` 裡的
廠牌 if，而該是進 dispatch 前就被正規化掉。

### 5.5 兩項新成員的規格（PM／UI-UX 2026-08-12 裁決，B1 實作依據）

**`adjust_*` 的使用準則（規格，不是註解）**：

> **需要知道「值代表什麼意思」的，就不屬於 adjust。** 正規化只認結構、不認
> 語意——改訊息型別名／欄位名，讓下游看到單一標準形；不得對映模式、不得算
> 就緒、不得構造指令。

配套機制（防止它變成垃圾抽屜）：`adjust_*` **必須明文宣告它碰哪些訊息型別**，
配一個測試釘住那份清單——與 `SEND_WHITELIST` 同一手法。往裡加東西就會測試失敗，
逼加的人回來面對「這到底該不該是 adjust」。

**還有一條 B0 實作時查出的硬約束**：訊息等價往往**只在某個範圍內成立**
（實例：EKF 兩個 enum 只有 bit 1..512 同義，bit 1024 同位元不同意義）。所以
每個等價宣告都要帶**適用範圍常數**，不能只寫「A 等於 B」。

**`limits()` 是 UI 可讀的契約，不是內部常數**（UI-UX ui-spec §0.2c 條款 5b）：

> 輸入欄位的預設值／最小值／最大值凡因機型而異者，一律由後端 `limits()` 隨
> capability 提供，UI 不寫死。

關鍵補充——**缺資料時要明確回「未知」，不得回通用值**。回一個通用預設會讓 UI
無法區分「這是該廠牌的真實下限」與「這是我們湊的」，而 UI 端的約定是缺 limits
就不套用任何數字（顯示佔位提示要求使用者輸入）。這與 `readiness()` 回
`bool | None`、影像五態、`msg_registry` 停掉的 hz 留 null 是同一條原則：
**缺乏證據不是給出一個看似權威數字的理由。**

現況待修的實例：起飛高度 `apps/command/app/main.py` 的 `takeoff_alt: float = 10.0`
（全域），前端寫死 min 3／max 100／預設 10。B1 落地後兩邊都改由 `limits()` 供給。

## 6. 與 019 MCP 的接口關係

MCP 對研究 agent 暴露的是**任務層動詞**（如 `submit_mission(N 台)`、`start`、
`abort`）。它們**必須落在驅動動詞之上，不得直接接觸廠牌**：

```
研究 agent ──▶ MCP 任務層動詞 ──▶ 系統邏輯（編隊/架次/資料）──▶ 驅動動詞 ──▶ 各廠牌
```

兩個具體要求：

1. **MCP 不得出現任何廠牌條件**。否則我們只是把方言問題從系統內部搬到 agent
   介面上——而那個介面的使用者是**自動化的 agent**，它比人更不會處理「這個廠牌
   要多做一步」。
2. **capabilities 是 MCP 的契約而不只是 UI 提示**：agent 呼叫某動詞前可以先查
   能力，得到 `ok`／`unverified`／`unsupported` 與**可讀原因**，而不是送出去後
   遭遇靜默失敗。這對 agent 尤其重要——**人看到沒反應會去查，agent 只會重試**。

### 9.1 先解決一個會讓整個計畫走偏的問題：沒有代理的機

待決點 2 原本寫著「地面站不再持有驅動」。**照字面做會壞掉**，因為
「這台機有沒有代理」是**執行期的事實，不是編譯期的**：

| 機 | 有代理嗎 | 後果 |
|---|---|---|
| 現役真機（Pi 5 ＋ uav-agent） | 有 | 正常 |
| SITL | 技術上可以（代理的 `--dev` 直接餵給 `mavutil.mavlink_connection`，吃 `udpin:`／`tcp:`），**但沒驗過** | 沒接代理就整個開發流程斷掉 |
| **第三方的機**（別人的飛機連進我們地面站） | **永遠不會有** | 完全無法顯示 |

**建議：驅動不從地面站刪除。** 但處置不是簡單的「有代理就用代理的」——
協定 §4.2 早就定了一條更好的規則，B4 沿用它而不是另立一條：

* **地面站認得那個廠牌** → 兩邊各自算，**不一致就報警**。不是拿來選一邊的。
  這讓「搬家有沒有搬對」變成**執行期**的性質，而不是只有測試時才問得到。
* **地面站不認得**（新廠牌）→ 地面站沒有意見，用代理的值並**標明來源是機上**。
  這才是搬家真正的收穫：加一款自駕儀時，只要那台機上有代理，地面站一行都不用改。
* **沒有代理** → 照舊由地面站自己解讀。

**而且必須看得出來用的是哪一條**——「機上算的」「地面站算的」「兩邊不一致」
是三種不同的可信度，畫成一樣就是本專案一路在防的那件事（ui-spec §0.2e）。

代價：待決點 2 想解決的「backend 與 command 跨服務共用驅動」不會消失。
**但那個問題現在並不痛**——`libs/autopilot` 掛進兩個容器就解決了，
而為了消滅它去換一個「第三方機完全無法顯示」的新問題，方向是反的。

> **這條是建議不是裁定**，因為它偏離了待決點 2 的字面。要照字面做（地面站
> 真的不持有驅動）也是一個選項，代價就是上表第二、三列。

### 9.2 為什麼搬家仍然值得做（就算保留後備）

因為**權威與後備不是同一件事**。今天地面站的解讀是唯一的一份，它錯了沒有人
知道；搬家之後，有代理的機由機上算，而地面站那份退成「沒有代理時才用」——
它的錯誤範圍就從「所有機」縮到「沒有代理的機」。

而且真正的收穫在**新廠牌**：加一款自駕儀時，只要那台機上有代理，
地面站一行都不用改。這是 019 MCP「agent 不需要無人機知識」的地基。

### 9.3 分批（每批獨立可驗，任何一批之後喊停系統都比現在好）

| 批 | 內容 | 誰做 |
|---|---|---|
| **B4-a** | **協定先行**：`state` 訊息補齊正規化欄位（模式名、模式動詞、就緒與其原因、限制值），寫進 `agent-intent-protocol.md` §4.2 | 地面站（本 repo） |
| **B4-b** | 代理送這些欄位：把 `libs/autopilot` 的驅動移植過去，由它解讀後送正規化值 | 機端 repo |
| **B4-c** | 地面站改成「**有代理用代理的、沒有就用自己的**」，並在畫面上標示來源 | 地面站 |
| **B4-d** | 一致性測試套改成兩邊都跑：同一台 SITL，比對「代理算的」與「地面站算的」**必須逐鍵相同** | 兩邊 |
| **B4-e** | 驅動版本與機隊漂移（待決點 6）：代理自報驅動版本、地面站看得見差異 | 兩邊 |

**B4-a 必須先做**：協定沒定就先寫代理端的驅動，會照著實作方便的形狀長出來，
之後要重做——這正是待決點 5 原本寫著「在決定之前不要先寫」的理由。

**B4-d 是這批裡最有價值的一項**，理由與 B2 的等價測試相同：搬家不是改寫，
唯一的驗收標準是「新舊輸出完全相同」。而**兩份實作同時存在的這段期間，
正是唯一能做這個比對的窗口**——地面站那份刪掉之後就沒有對照組了。
（這也是保留後備的第二個好處。）

### 9.4 已經是既成事實的部分

搬家不是從零開始。意圖協定的 `state` 訊息**現在就在送正規化的東西**：
`state`（`FLYING_MISSION`／`HOLDING`／`PILOT_CONTROL`…）、`derived`、
`rc_link`、`mission_seq`。原始 MAVLink 流照舊進 backend 入庫給
[014](../issues/014-two-tier-collection.md) 的原始層——**那正是待決點 5 當初
猜的「原始流照舊送，另加一路正規化摘要」的形狀**。

所以 B4-a 是把已經在跑的那條路**正名並補齊**，缺的是差異點 2、7、8
（模式名、就緒判定、EKF 健康）——它們目前仍在地面站解讀。

## 8. 不做什麼（範圍邊界）

- **不做外掛式動態載入**：驅動是編譯期已知的少數幾個，動態載入只增加除錯難度。
- **不在這一層做重試／逾時策略**：那是傳輸層（router）的職責，驅動只負責「這個
  廠牌該送什麼、怎麼判定成功」。
- **不把 capabilities 的四態語意改掉**：那是使用者定案，本提案只改「值從哪裡來」
  （人工判斷 → 測試結果＋執行期檢查），不改語意本身。
