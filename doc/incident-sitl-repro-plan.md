# 事故序列 SITL 重現劇本

- 日期：2026-08-13（PM 核可，純文件，尚未執行）
- 目的：重現部署環境事故的操作者序列，**判定「凍結」與「墜落」各自的成因**
- 對象：SITL 機隊（非主機 sysid），**不涉及真機**

## 事故時序（使用者更正後）

    載任務起飛 → 爬升中突然不動 → 操作者重載任務並執行 → 直直墜落

分成兩段，**成因可能完全獨立**：

- **前段「不動」**——三種可能，見 §1
- **後段「墜落」**——與任務重啟時間相關，見 §3

---

## §0 執行紀律（每個分支都適用）

1. **只飛 SITL**，用非主機 sysid；飛前在群裡預告、飛後回報。
2. 每個分支**跑前先記錄基線**（機隊狀態、服務啟動時間、DB 筆數），
   跑後逐項對帳——沒有基線的「有變化」不算觀察。
3. **每個分支獨立跑一次**，不要在同一趟飛行裡連續製造多個異常：
   兩個異常疊在一起，因果就分不出來了。
4. 收尾一律 RTL 並**等到 disarmed 才算結束**。

## §1 前段：「不動」的三個分支

**三者對操作者的外觀完全相同**（畫面不更新／機看起來停住），這正是它需要
分支實驗的理由。**遙測是獨立判官**：

| 分支 | 遙測呈現 | 誰負責 |
|---|---|---|
| A 純畫面卡 | 位置高度**持續變化**，但畫面不動 | 前端（注入式，**不需飛**） |
| B 我方序列安全停 | 位置高度**靜止、資料連續** | 後端（SITL 飛） |
| C 鏈路斷 | 資料**整段缺口** | 後端（SITL 飛） |

> ⚠️ **第三列要讀得比字面小心**（設計師 2026-08-13 指正，本文件據此修正）：
> 資料缺口**只證明「我們看不到」，不證明「機停了」**。缺口期間機體實際在做
> 什麼，我方資料**無法回答**——那是 ulog 才答得出來的。
>
> 我原本的寫法讓「缺口」隱含了「機進 failsafe」的結論；那是從 PX4 行為推論
> 出來的**預期**，不是觀察到的**事實**。**判讀時不得讓資料缺口冒充機體狀態。**

> **C 最可能，而且它不是「另一個選項」**：鏈路一斷，畫面凍結與機體停下是
> 同一件事的兩個面向。若真相是 C，A 與 B 都不成立，但**設計師要求的「畫面
> 活性證據」仍然成立**——操作者當時無從分辨自己看到的是哪一種。

### 分支 A：純畫面卡（前端，注入式）

- **做法**：注入正常變動的 WS 遙測，但令前端某條路徑停止更新（覆蓋缺陷／
  例外吞掉／重繪失敗），觀察畫面是否「看起來正常但不動」。
- **不需要飛。** 歸 `uav-system-07`。
- **推翻條件**：若無論如何都會出現可見異常（紅字／錯誤 toast），
  則「畫面卡但看起來正常」不成立，A 出局。

### 分支 B：我方序列自己的安全停

`mission_fly` 在「起飛後未達目標高度 80%」時會逾時並**停在懸停**
（`alt_timeout_s`，預設 60s）。外觀正是「爬升到一半不動」。

- **做法**：給一個**高於機體實際爬升能力或超過逾時**的 `takeoff_alt`，
  讓高度檢查逾時。
- **預期**：序列回 504、機停在懸停、`flight_mode` 進 HOLD。
- **要記錄**：逾時當下的 `alt_rel`、序列回應的 hint 文字
  （**當時的 hint 寫「可重試」，操作者照做了**——這句要原文記下）。
- **推翻條件**：若逾時後機**不是**懸停而是繼續爬或自行返航，B 的外觀就與
  事故描述不符，出局。

### 分支 C：鏈路斷（心跳中斷）

- **做法**：飛行中令 command 服務停止送 GCS 心跳（停容器／中斷 fanout 的
  command 腿），持續 >10s。
- **預期分層**（三個門檻各自宣告不同的事，見 `doc/032-rb5-manual-control-analysis.md`）：

      0.5s  COM_RC_LOSS_T   飛控判手動輸入沒了
      4.5s  gcs_timeout_s   機上 router 判 GCS 斷了（真機才有，SITL 無此層）
      10s   COM_DL_LOSS_T   飛控判資料鏈斷 → NAV_DLL_ACT

- **要記錄**：機在各時刻的 `flight_mode`、事件流有無 failsafe 宣告、
  **恢復心跳後機會不會自己回任務**。
- **推翻條件**：若中斷 10s 以上機仍照常執行任務，則 datalink failsafe 未生效，
  C 的機制不成立（要回頭查 `NAV_DLL_ACT` 設定）。

#### C 的前端側驗收條件（設計師指定）

即時頁的三分告警在 **08-11 15:38（`001f9b7`）就已具備且優先序正確**：
`!wsConnected`（「與系統失去連線」）→ `droneLost` → `link_age_s > 5`。

**所以部署 build 若 ≥ 該時點，C 分支下操作者應該看得到誠實告警**——
「呈現誤導」的範圍因此縮小到**地圖層**（橫幅說「最後已知位置」，但地圖上
看不到那個位置）。

**驗收條件是「三條告警在對應情境各自出現且不互相冒充」，不是「有沒有告警」。**
三條都亮等於沒測——那只證明程式會亮燈，不證明它分得出是哪一種故障。

**順帶一個既有正例**（033 可引用）：`link_age_s` 凍住時 `!wsConnected` 會接手
——這正是「**故障的偵測不得依賴故障的那條路徑**」在本專案已經做對的地方。

## §2 中段：對「空中、已 armed」的機重跑 mission/fly

**這條路徑從未測試過**——所有 SITL 驗證都是從地面起飛。

照現行程式碼，對空中機重跑會發生：

1. `upload`：**在飛行中替換機上任務**（機可能正在執行舊任務）
2. `arm`：已 armed → **跳過**
3. `NAV_TAKEOFF`：送出，**接受與否未檢查**（空中大概率被拒，序列不看）
4. 等高度：已高於 80% → **秒過**
5. 切 `AUTO.MISSION`

**要觀察的**：

- 步驟 1 當下機的行為（是否中斷舊任務、是否跳到新任務首項）
- **新任務首項是 NAV_TAKEOFF，而機已在空中**——PX4 怎麼處理？
  若新任務的起飛高度**低於**當前高度，機會不會下降？
- 步驟 3 的 ACK 實際是什麼（我方不看，但我們要知道）
- 全程 `armed` 有沒有變成 false（**這是墜落的唯一機制**）

**推翻條件**：若全程 `armed` 始終為 true 且無異常下降，則「我方序列直接造成
墜落」不成立——與 PM 的讀碼結論一致，墜落成因要往 §3 找。

## §3 後段：「墜落」的候選（獨立實驗）

墜落＝馬達停轉＝**disarm**。四個候選，按可檢驗性排序：

### 3a 搖桿值構成 disarm 手勢（SITL 可安全驗，**優先**）

`MAN_ARM_GESTURE` 預設 1：左搖桿**左下**（油門最低＋偏航全左）disarm。
我方編碼在前端送 `z=-1, r=-1` 時，線上是 `z=0, r=-1000`——**正是那個手勢**，
而 `_tick_manual` 無任何過濾（見 `issues/031`）。

- **做法**：SITL 起飛至安全高度 → `manual/start` → 持續送 `z=-1, r=-1`。
- **預期（若假設成立）**：機 disarm、直直落。
- **同時要驗的前置條件**：PX4 對**空中**的手勢 disarm 是否有前置條件
  （是否檢查 land-detected 或限特定模式）。**若有前置條件，這條與 3c
  就是串聯而非獨立的兩個候選。**
- **推翻條件**：空中送該組合 30s 仍不 disarm → 這條出局（或需與 3c 併發）。
- ⚠ **這個實驗會讓機掉下來**，是刻意的。用非主機、確認場地無其他測試在跑。

### 3b 電池電壓在任務啟動推力上升瞬間崩潰

時間相關性有力學解釋（重載任務→推力需求上升→老化電池電壓崩）。
**SITL 難以忠實重現**（電池模型不同），列為**只能真機／ulog 驗證**。

### 3c 空中誤判著陸 → 自動上鎖

`COM_DISARM_LAND` 預設 **2.0s**：偵測到著陸情境後 2 秒自動 disarm。
任務重啟時的推力變化若讓著陸偵測誤判，2 秒後就 disarm。

- **SITL 可嘗試**：觀察 §2 實驗中 `vehicle_land_detected` 有無在空中觸發。
- **推翻條件**：整段飛行 land-detected 從未在空中為真 → 出局。

### 3d RC kill switch（ch6/7）／voxl-px4 程序死

**只能真機驗證**。RB5 官方設定把馬達切斷掛在 RC 通道
（`reference/rb5/...pre-flight-setup.html`）。

## §4 ulog 是最終判官（四項）

SITL 重現只能證明「這個機制存在且會產生該症狀」，**不能證明事故當時就是它**。
最終判定要看機上 ulog：

1. **disarm 事件的時間與原因**（PX4 記 disarm reason）
2. 該時刻前後的 **`manual_control_setpoint`**（z、r 的值 → 是否來自我方）
3. **`vehicle_land_detected`** 有無在空中觸發
4. **電池電壓曲線**在任務啟動瞬間

> 第 1、2 項會**同時裁決 032**：若 disarm reason ＝手勢且 `manual_control_setpoint`
> 來自我方，就證明我方搖桿流確實有進到飛控——那麼 032 的「搖桿控不了」
> 就不是「被忽略」，而是別的環節（見 `issues/032` 的耦合說明）。

## §5 這份劇本的誠實邊界

- **SITL ≠ 真機**：SITL 沒有 voxl-mavlink-server 那一層、沒有實體 RC、
  電池模型不同、`COM_RC_IN_MODE` 我方設 1 而真機可能是 3。
  **凡是依賴這些差異的候選，SITL 跑過也不算結案**（3b、3d，以及 032 主嫌）。
- **重現成功 ≠ 找到成因**：能造出同樣症狀的機制可能不只一個。
  結論要等 ulog。
- 每個分支都寫了**推翻條件**——沒有推翻條件的實驗，跑完只會看到想看的。
