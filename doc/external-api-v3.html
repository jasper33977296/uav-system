00這一版改了什麼

v2（2026-09-16）之後改了三件事，三件都是契約變更——照 v2 寫的程式有兩處會遇到新的行為。

項目v2v3狀態
重複執行同一條路徑 帶同一個 mission_id 就掛進那個任務 每一次執行都是新的任務。mission_id 用過就 409 mission_id_used（進行中、已結束都一樣）；沒帶 mission_id 而這台機還在別的任務裡，會建立新任務並把舊的結束掉，被結束的列在 replaced 裡（§6.1） 已上線
任務與路徑的關係 沒有明說 一個任務綁定一條路徑。同一條路徑飛三趟是三件事，不是一件事飛三次——這正是「比較兩趟訊號」要成立的前提（§6.1） 已上線
即時畫面 v2 §17 明寫不送影像 改成給了：走 RTSP，由地面站轉發，網址在 GET /api/v1/ext/drones 每台機的 video 欄位（§3） 已上線
任務歷史：停留 沒有 每一趟多一組 holds：規劃的停留點實際站了多久是量出來的，不是照抄規劃值；樣本多一個 hold_seq，分得出「在停留點量的」與「飛行中量的」（§14） 已上線
/api/ext/live 標為「實飛驗收後移除」 仍在，仍然標為要移除。新的程式請用綁任務的 §8——它與串流是同一份訊息 待移除

照 v2 寫的程式要檢查的兩處：① 有沒有重用 mission_id（以前會被接受，現在 409）；② 有沒有假設「同一台機連續兩次起飛會在同一個任務底下」（現在是兩個任務，第二次的回應會帶 replaced）。其餘端點的形狀沒有變。

畫面由地面站轉發，走 RTSP。 rtsp 的主機名取自你這次請求的 Host——你連得到這支端點，就連得到那條串流。

state意思有 rtsp 嗎

ready 不保證此刻拉得到。地面站知道的是「來源設好了」與 「MAVLink 還在通」；機上的相機服務有沒有在跑，在真的去拉之前無從得知——串流是 on-demand 的，沒人看的時候機上根本不開相機。所以請把「拉不到」當成正常的可能結果。

只要有人在看就會一直送。你和我方前端讀的是同一條來源， 所以機上只會被拉一次、兩邊共用同一條上行——你接進來不會讓上行變兩倍。 最後一個讀者離開之後機上才停止送畫面。

影像與 5G 量測共用同一條上行，所以拉著不放會影響那段時間量到的鏈路品質。 這件事不擋、也不記錄（2026-09-23 裁定）——寫在這裡是讓你知道代價，不是限制你。

任務相關的錯誤

HTTPcode什麼時候msg 說明什麼
422mission_id_invalidmission_id 不是 UUID收到的值、要的格式（例如 crypto.randomUUID() 產生的）
409mission_id_used這個 mission_id 已經用過——不管那個任務是進行中還是已結束（v3 起兩種情況同一個代碼）說明它是進行中還是已結束；要再飛就產生新的 UUID
409mission_busy只剩競態：兩個請求同時替同一台機建任務那個任務的名稱與編號；重試即可

v3 起：每一次執行都是新的任務，不再掛進既有的任務——見下面的 §6.1。

·§6.1　一次執行＝一個任務已上線

2026-09-23 的契約變更。同一條路徑飛三趟是三件事，不是一件事飛三次。

系統裡路徑（plan）／任務（mission）／架次（session）是三個不同的東西（§1）。本系統的主要用途是「同一條路徑飛多趟、比較訊號」——三趟若共用一個任務編號，資料就疊在同一個任務底下，§14 的比較功能拿不出「這趟 vs 那趟」。所以：

你送的v2v3
mission_id 對到進行中的任務掛進去409 mission_id_used
mission_id 對到已結束的任務409 mission_ended409 mission_id_used（同一個代碼）
沒帶 mission_id，而這台機還在別的任務裡沿用那個任務建立新任務，把舊的結束掉，並在回應的 replaced 裡說出來
mission_id 是沒用過的 UUID採用採用（讓你對得上自己的請求）
沒帶 mission_id，這台機也不在任何任務裡自動建立自動建立

replaced 一定會說出來。資料庫的不變式是「一台機一次只能在一個任務」，所以新任務成立就代表舊的被結束了——默默結束別人的任務是不行的：

200
{
  "mission_id": "8f0c…",              // 這一趟的任務（你給的，或自動產生的）
  "name": "0914-square-test-v5 09-23 15:41",
  "replaced": [                       // 為了建立這個任務而被結束掉的任務
    {"id": "2b71…", "name": "0914-square-test-v5 09-23 15:12", "drone": "pi5-…"}
  ],
  "plan_id": "e961b301-…",
  "steps": [ … ]
}

任務名稱不必你想。不給 mission_name 時自動產生「<路徑名> MM-DD HH:MM」（地面站時鐘）；同一分鐘撞名加秒數，再撞加 #2。

一個任務綁定一條路徑。設計上一個任務可以含多條路徑，但目前不管從我們的畫面還是從外部控制，都是一個任務一條路徑。任務一旦綁了路徑就不會被改掉——不讓第二趟不同路徑的架次悄悄改掉任務的路徑。

08即時資料：兩種傳法

控制端自己產生一組 UUID 當任務編號，用它連上地面站，再帶著同一組編號起飛。 從起飛流程開始每 0.5 秒收到任務裡每一台機的狀態，外加預計航線、已飛過的軌跡與重要事件，拿來在自己的 OSM 地圖上畫。只讀，不收指令。

拿的方式有兩種，送的是同一份訊息：地面站推的 WebSocket 串流，與控制端拉的 HTTP 輪詢。 messages 裡的每一則與串流送出去的逐字相同（§9）， 所以兩種可以混用——WebSocket 斷線的那段先用輪詢頂著，接回來再換回去。

尚未實飛驗收。兩種傳法的連線、等待、結束、重連補送、錯誤都已經對正在跑的地面站測過（含「同一個任務同時開串流與輪詢，訊息逐欄相同」）；解鎖、離地、著地、上鎖事件的時序與墜機判定，要真的飛一趟才算數。

  "poll_after_s": 0.5,           // 地面站的節拍。拉得比它快只會拿到空的 messages
  "messages": [ … ]              // 與串流逐字相同的 state／event／route／track／ended
}

外層那幾個欄位就是串流 hello 的內容，而且每一次都給——輪詢沒有「連上的那一刻」，所以不另外分出一則 hello。

輪詢要注意兩件事。

  • 快照的 state 沒有 seq：它與 route、track 一樣是「只屬於這一次呼叫」的訊息。要接續請用外層的 seq，不要從 messages 裡挑。這一則是現算的，不是緩衝裡最後一則——剛掛上來的任務要到下一拍才有 state，而快照的用途正是「不必等下一拍」。
  • 緩衝一樣只有 60 秒：拉得太慢會掉東西，replay.gap 會說缺了哪一段（§12 同一套）。不想漏就照 poll_after_s 的節拍拉。

該選哪一個

串流（WS）輪詢（GET）
延遲事情發生就送到最多差一個輪詢間隔
斷線要自己做 3 秒看門狗（§11）——TCP 可能幾十秒才發現對方不在一次呼叫失敗就是失敗，下一次重試即可
連線要維持長連線無狀態，過 proxy 不必特別設定
流量只送變化每次都帶外層欄位（約 0.5 KB）＋那段期間的訊息
其餘完全一樣：進場（沒見過的編號是開場不是錯誤）、結束條件（最後一台上鎖 3 秒後）、過期分級、錯誤的 code／msg／how_to。輪詢不會讓任務活得比較久，也不會讓它提早結束

流程

1控制端產生一組 UUID，當任務編號
2控制端→地面站連 /ws/v1/missions/{UUID}。回 hello（waiting），之後每 0.5 秒一則保持連線
3控制端→地面站30 秒內呼叫 POST :38001/api/v1/start，帶 {"plan_id": …, "mission_id": UUID}。地面站用這個 UUID 建立任務
4地面站→控制端route（預計航線）、每 0.5 秒 state、event——上傳、解鎖、爬升都看得到
5地面站→控制端最後一台上鎖 3 秒後：自動結束任務、送 ended、關閉連線
  • 第 2 步換成輪詢也一樣：改拉 GET :38000/api/v1/ext/missions/{UUID}/live，其餘每一步都不變。
  • 先連再起飛。/api/v1/start 要等飛機爬到起飛高度才回應，先連上（輪詢的話先拉一次），上傳、解鎖、起飛那一段才看得到。
  • 群飛：POST :38001/api/v1/command/group/{group_id}/execute 同樣帶 {"mission_id": UUID}。不帶 mission_id 也不帶 mission_name 時照舊不建任務（畫面按的群飛就是這樣）。
  • 看從我們畫面啟動的任務：GET :38000/api/v1/missions/active 拿到任務編號，連同一個網址。這種任務由操作員在畫面上結束。

10任務何時結束

3秒

用 /api/v1/start 建立的任務：每一台都已上鎖，最後一台上鎖 3 秒後自動結束任務、送 ended、以 1000 關閉。這 3 秒內任何一台又解鎖，就不結束。

  • 要換電池再飛：開一個新任務（新的 UUID）。
  • 從我們畫面建立的任務：由操作員在畫面上結束時才送 ended，兩趟之間照常每 0.5 秒送狀態。
  • 3 秒夠用是實測過的：這台 ArduCopter 4.7 用路徑的降落項或 LAND 模式降落，著地後 0.4–0.8 秒就自動上鎖（2026-09-14 五次降落）。手飛直接落地、RTL 降落還沒有樣本。

每一台的結束原因 reason

reason意思
landed著地後上鎖：著地狀態先到 on_ground，接著上鎖
crash飛控判定墜機而切斷馬達。控制端必須分得出落地與摔機
disarmed_in_air上鎖時沒有著地訊號，例如飛控其他保護機制上鎖
telemetry_lost解鎖中連續 90 秒沒有遙測，地面站收掉這一趟。不代表飛行結束，只代表資料在那裡斷了
start_failed起飛流程被拒（上傳、解鎖、起飛任一步）
aborted群飛全撤

不會結束的情況

  • 著地了但一直沒上鎖（例如手飛落地、油門沒拉到底）：繼續送，該機 landed: "on_ground"、armed: true。
  • 路徑最後沒有降落項（例如從 QGC 匯入的）：飛機會在最後一點懸停，串流一直開著，直到有人讓它降落。本系統規劃頁產生的路徑一定帶降落項。
  • 控制端斷線：不影響飛行，也不影響任務何時結束。

113 秒斷線規則

3秒

超過 3 秒沒有收到任何一則訊息，就當成連線斷了：關掉這條連線，帶著最後收到的 seq 重連。

地面站保證每 0.5 秒一定送一則——waiting 時送保持連線用的 state，起飛後送真正的 state。3 秒是正常間隔的 6 倍，一般的網路抖動不會誤判。

為什麼不能等 WebSocket 自己報錯：網路半路斷掉時（5G 或跨網段的路由掉包），TCP 可能要好幾十秒才發現對方不在了。那段時間連線看起來還開著，地圖上的飛機卻停在原地——看起來像懸停，其實是資料沒有進來。

判斷斷線後，把地圖上的機體標成「資料中斷」，不要讓它停在最後的位置看起來正常。範例見 §16。

這裡的「連線斷了」與 §13 的「資料舊了」是兩件事：連線好好的，飛機的遙測也可能斷了。

地面站為每個任務保留最近 60 秒的訊息。重連時帶上最後收到的序號：

訊號欄位與即時串流的 state.link 逐字相同（§9 的下表）：即時看到的與事後拿到的是同一個東西。量不到的是 null，不補假值。

兩趟怎麼對齊

時間對不齊：兩趟的速度不同，用時間當 X 軸會把「同一個地點」錯位。每一筆樣本都投影到那一趟自己的預計航線上，給出 along_m（走了多遠）與 offset_m（偏離多少），控制端拿 along_m 當共同的 X 軸。

  • 基準是計畫航點，不是任一趟的實飛軌跡——拿其中一趟當基準，那一趟的偏航就變成零誤差。所以那一趟沒有綁路徑時 reference 是 null、along_m 全給 null，不退回用軌跡。
  • 偏離超過 max_offset_m（60 m）的樣本 along_m 給 null，offset_m 照給。硬塞進某個里程的數字看起來完全正常，而且沒有線索說它是垃圾。這個門檻不給外部調——可調的話同一趟資料在不同呼叫下會給出不同的 along_m；用了哪個值寫在 method.max_offset_m 裡。
  • along_m 只在同一份路徑之間可比。每一趟都帶 plan_id，比較前先確認相同。
  • sample_interval_s 是量出來的，不是設定值：那一趟相鄰樣本時間差的中位數。取樣率由機上的旗標決定，地面站沒有管道知道它設成多少（2026-09-07 實測過設定 1.0 s、實際 2.61 s），所以只回報量到的。不足兩筆時是 null。
  • gaps 與 sample_gaps 是兩件事。gaps ＝遙測失明（那段地面站看不到飛機，超過 10 秒沒遙測）；sample_gaps ＝那段沒有訊號樣本（相鄰樣本差超過取樣間隔的 sample_gap_factor 倍）。真機上樣本走機上代理、每 10 秒一批而且允許補傳，與遙測是兩條路——遙測斷了樣本可能是齊的，樣本斷了遙測可能照常。畫訊號圖要留白的是 sample_gaps，不要把兩端連成一條線；gaps 另外標成「失聯」。算不出取樣間隔時 sample_gaps 是 null 而不是 []——空陣列的意思是「沒有缺口」，而那時我們其實是「不知道」。
  • holds：停留點站了多久是量出來的，不是照抄規劃值（v3 新增）。一條航線上規劃了停留的點各一筆：planned_s 是規劃值，seconds 是從地速實際量到的靜止時長，observed 說這一筆到底有沒有量到。observed: false 時 seconds 是 null 而不是 0——「沒量到」與「站了 0 秒」是兩件事，理由寫在 note。怎麼量的寫在 method.hold_stop_ms（地速門檻）與 method.hold_near_s（抵達事件附近的時間窗），與 max_offset_m 一樣不給外部調。
  • phase 與 hold_seq（v3 新增）：phase 是 route（在航線上）或 transit（飛往任務起始點那一段）——里程只對 route 有意義。hold_seq 有值代表這一筆是在那個停留點站著時量的，分得出「站著量的」與「飛行中量的」：比較兩趟訊號時，停留點的樣本是同一個地點的重複量測，飛行中的不是。
  • 任務是哪一態看 state：planned（建了還沒飛）／flying（進行中）／ended。不要自己從時間戳推——started_at 在還沒飛時是 null，而舊的「ended_at 是 null ＝進行中」會把從沒飛過的任務判成正在飛。

只有掛在任務底下的架次拿得到。用 /api/v1/start 帶 mission_id 起飛的一定有；更早以前的飛行多半沒掛任務，要先在畫面的資訊頁補歸。

15錯誤格式與狀態碼

失敗一律回 4xx／5xx。每一個錯誤都同時帶機器讀的 code 與人讀的 msg，呼叫端自己排除得了的再附 how_to。msg 可以直接顯示給人看。

409
{"detail": {
  "code": "mission_busy",
  "msg": "這台機（sysid 1）已經在進行中的任務「0914 巡檢」（8f0c…）裡，一台機同一時間只能在一個任務",
  "how_to": ["等那個任務結束再起飛", "或改用 mission_id 8f0c… 起飛，把這一趟掛進那個任務"]}}

/api/v1/start 與群飛執行的錯誤一律是物件、一定有 code 與 msg；沒有專屬代碼的依 HTTP 狀態給通用代碼（forbidden、not_found、conflict、vehicle_rejected、timeout…），起飛後判定不到離地是 not_airborne。其他端點（上傳、切模式）形狀照舊：detail 是字串就直接顯示，是物件就顯示 detail.msg。

狀態常見 code意思怎麼辦
403not_admitted這台機不接受指揮（例如沒有機上代理），或地面站的指令功能沒開先查 §3 的 controllable 與 reason
404—找不到這份路徑／航線檔用 §4 重新取清單
409guard_refused、unverified、mission_busy…當下狀態不允許（例如飛行中上傳、機在地面卻叫它開始路徑），或做了但沒能讀回確認照 msg 與 how_to 換做法
422mission_id_invalid…payload 欄位缺漏或型別不對對照該端點的 payload 表
501—這個機型的這個動作尚未支援換動作或換機
502—飛控拒絕，或沒有回 ACK看 msg；沒有 ACK 可重試
504link_timeout指令送出去了，但 30 秒內沒有回應——送往飛機的方向不通可重試；連續失敗代表通訊中斷
503—沒有任何無人機在線查 §3

16範例程式

最小的控制端（Leaflet）：先連上、再起飛；畫預計航線、實際軌跡與機體位置；3 秒沒收到訊息就標成資料中斷並重連。

畫圖的 draw(m) 與傳法無關——下面輪詢版用的是同一個函式，因為兩種傳法送的是同一份訊息。

javascript
const GS = "10.141.2.21";
const missionId = crypto.randomUUID();
let lastSeq = null, ws = null, watchdog = null;
const markers = {}, tracks = {};

function connect() {
  const q = lastSeq == null ? "" : `?after_seq=${lastSeq}`;
  ws = new WebSocket(`ws://${GS}:38000/ws/v1/missions/${missionId}${q}`);
  ws.onmessage = (e) => {
    const m = JSON.parse(e.data);
    if (m.seq != null) lastSeq = m.seq;
    resetWatchdog();
    draw(m);
    if (m.type === "ended") { clearTimeout(watchdog); ws.onclose = null; }
  };
  ws.onclose = () => setTimeout(connect, 1000);
}

// 與傳法無關：串流與輪詢送的是同一份訊息
function draw(m) {
  if (m.type === "route") L.geoJSON(m.geojson).addTo(map);                // GeoJSON：[經度, 緯度]
  if (m.type === "track") {
    tracks[m.drone_id]?.remove();
    tracks[m.drone_id] = L.geoJSON(m.geojson, {style: {color: "red"}}).addTo(map);
  }
  if (m.type === "state") for (const d of m.drones) {
    const p = d.position ?? d.last_known;                                  // old 時位置在 last_known
    if (!p) continue;
    markers[d.drone_id] ??= L.marker([p.lat, p.lon]).addTo(map);          // Leaflet：[緯度, 經度]
    markers[d.drone_id].setLatLng([p.lat, p.lon])
      .setOpacity(d.freshness === "live" ? 1 : 0.4);
  }
  if (m.type === "error") console.warn(m.code, m.msg);
}

// §11：3 秒沒收到任何訊息＝連線斷了，不等 WebSocket 自己發現
function resetWatchdog() {
  clearTimeout(watchdog);
  watchdog = setTimeout(() => {
    for (const mk of Object.values(markers)) mk.setOpacity(0.2);          // 標成「資料中斷」
    ws.close();                                                            // onclose 會帶 after_seq 重連
  }, 3000);
}

connect();
const r = await fetch(`http://${GS}:38001/api/v1/start`, {method: "POST",
  headers: {"Content-Type": "application/json", "X-Client": "my-controller"},
  body: JSON.stringify({plan_id: "0914-square-test-v5", mission_id: missionId})});
if (!r.ok) { const {detail} = await r.json(); alert(`${detail.code}：${detail.msg}`); }

同一個控制端，改用輪詢

把 connect() 換成下面這個迴圈就好，draw(m) 一行都不用改。 沒有看門狗——一次呼叫失敗就是失敗，下一次重試即可。

javascript
let seq = null, timer = null;

async function poll() {
  const q = seq == null ? "" : `?after_seq=${seq}`;                        // 不帶＝快照
  const r = await fetch(`http://${GS}:38000/api/v1/ext/missions/${missionId}/live${q}`);
  if (r.status === 410) return stop();                                     // 結束且補送過期
  if (!r.ok) { timer = setTimeout(poll, 1000); return; }                   // 失敗就下一次再試
  const d = await r.json();
  seq = d.seq;                                                             // 接續用外層的 seq
  if (d.replay.gap) markGap(d.replay.gap);                                 // 缺了就照實標，不連成一條線
  for (const m of d.messages) draw(m);                                     // 與串流版同一個函式
  if (d.messages.some((m) => m.type === "ended")) return stop();
  timer = setTimeout(poll, d.poll_after_s * 1000);                         // 照地面站的節拍
}
function stop() { clearTimeout(timer); }

17不提供的東西

  • 沒有認證。任何連得到地面站的人都能看任何一個任務的即時狀態，也能指揮飛機。安全靠網段隔離——這件事要寫在這裡，不能靠「大家都知道」。
  • 兩種傳法都不收指令。暫停、返航、改航線照舊走 :38001。
  • 不送圍欄。控制端只拿預計航線與實際軌跡。
  • 歷史不做伺服器端的比較結論（勝負、改善多少）：地面站給樣本與共同的 X 軸，怎麼比是控制端的事。也不做 CSV、不降採樣。
  • 不再提供全機隊的輪詢快照 /api/ext/live（v1 §5 的那一支，實飛驗收後移除）：要輪詢即時資料請用綁任務的 /api/v1/ext/missions/{id}/live（§8），它與串流是同一份訊息。不是不給輪詢，是輪詢也要綁任務。
  • 影像改成給了（2026-09-23）：走 RTSP，網址在 GET :38001/api/v1/ext/drones 每台機的 video 欄位裡（§3）。不在即時串流的訊息裡——那份訊息是 WS 與輪詢共用、逐字相同的，而網址的主機名要看呼叫端自己連進來的位址。
  • 仍然不送原始 MAVLink、不送 IMU 或驅動診斷這類內部欄位。
  • 逐則訊息只補送 60 秒；更早的完整資料走 GET :38000/api/v1/sessions/{session_id}/export。
