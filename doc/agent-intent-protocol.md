## 0. 一句話

**地面站說「我要什麼」，代理回「我打算怎麼做」，人確認，代理執行並持續回報。**
權威狀態機**只有一份，在代理上**；地面站是鏡像與意圖來源。

## 1. 為什麼是這個形狀

| 決定 | 理由 |
|---|---|
| **狀態機只有一份、在代理** | 兩份會有兩個事實來源。代理直接讀飛控（微秒級），地面站的位置經 5G 回來已是過期資料——10 m/s 巡航下一次鏈路抖動就是數十公尺誤差，而「離當前位置最近的航點」正是對位置敏感的判斷 |
| **傳意圖，不傳步驟** | 步驟層指令在斷線時會把飛機卡在半途（送了「暫停」還沒送「續飛」就斷了）。意圖層可以在斷線後由代理自己跑完——這是「失聯照代理跑完」唯一成立的方式 |
| **代理主動撥出** | 今天地面站**能**連進 Pi（同一個私有 5G 網段，實測 SSH 通、ping 40ms），但換到電信商 APN 後飛機就在 carrier NAT 後面。**不要依賴今天的拓撲。** 代理撥出在兩種拓撲都成立 |
| **提案要人確認** | 「離最近航點續飛」是系統替人做的判斷，必須攤開給人看過（issues/039 §6.3） |

## 2. 傳輸

**WebSocket，代理主動連向地面站**：`ws://<地面站>:38000/ws/agent`

* 一條連線雙向：地面站可即時推 intent，代理推 state/proposal/event。
* **連線斷掉＝失聯**，語意乾淨，不需要另外的心跳判定
  （仍保留 §5 的靜默逾時，因為 TCP 可能在斷線後長時間不 FIN）。
* 訊息＝一行 JSON。

**已實作的行為**（2026-08-25）：第一則必須是 `hello`，否則 `state` 會被擋下
——沒有 `board_uid` 就不知道這條連線是哪一台機的，之後的狀態只能記成無主資料。
`hello` 的回應是 `ack`，帶 `drone_id` 與 `accepts`（本站目前收哪些型別）。
**斷線時保留最後已知狀態**並標成不新鮮：清成空白等於宣告「不知道」，
而「最後看到它在 FLYING_MISSION」是有用的資訊。

> **為什麼不用 MAVLink 自訂訊息**：飛控鏈路是 57600 序列埠，那條頻寬要留給遙測；
> 而意圖只在人操作時才發生，量極小。混進去只會排擠遙測。

## 3. 共同信封

```json
{ "v": 1, "type": "...", "ts": "2026-08-25T09:12:33.412Z", "sysid": 1 }
```

`v` 是**協定版本**，不是軟體版本。收到不認得的 `v`：**拒絕並回報**，不要盡力解讀
——半懂的指令比不懂的危險。

## 4. 訊息

### 4.1 `hello`（代理 → 地面站，連上第一則）

```json
{ "type": "hello", "agent_version": "…", "board_uid": "2a00…",
  "autopilot": "ardupilot", "fw": "4.7.0 (official)",
  "inputs": ["telemetry"],
  "protocol": [1] }
```

**`inputs` 是判斷依據的清單，也是感測擴充的接點。** 目前只有 `telemetry`；
機上加裝攝影機後會變成 `["telemetry", "perception"]`。地面站據此知道
**這台機的判斷是基於什麼**，而不是假設所有機都一樣聰明。

> 現在**不做**任何 perception 的機制，只把欄位留著。預先蓋一套用不到的抽象，
> 會在真的接上相機時發現形狀不對——那時要拆的東西比重寫還多。

### 4.2 `state`（代理 → 地面站；狀態變化時立即送，另 1 Hz 保活）

```json
{ "type": "state", "state": "FLYING_MISSION", "since": "…",
  "intent_id": "…", "seq_step": null,
  "mission_id": "…", "wp_current": 3,
  "derived": { "armed": true, "landed": "in_air", "mode_verb": "mission",
               "alt_rel": 25.1, "lat": 25.0554, "lon": 121.5065,
               "battery_pct": 74, "gps_fix": 3 } }
```

`derived` 是代理**從飛控遙測算出來**的，地面站可以自己驗算（它收得到同一份
遙測）。**不一致就是要報警的事實**，不是拿來選一邊的——見狀態機文件 §6.4。

### 4.3 `intent`（地面站 → 代理）

```json
{ "type": "intent", "intent_id": "uuid", "action": "change_route",
  "mission_id": "…", "params": { "hold_alt": 25.0 } }
```

| `action` | 語意 |
|---|---|
| `start_mission` | 起飛並執行任務（地面才可用） |
| `change_route` | **飛行中改航線**（暫停→換→續飛，由代理自己跑完序列） |
| `pause` | 暫停懸停，可帶 `hold_alt` |
| `resume` | 續飛 |
| `rtl` / `land` | 返航／降落 |
| `abort` | 中止當前 intent，停在安全狀態（懸停） |

### 4.3b 執行者分工（**丙案**，2026-08-25 裁定）

切分依據是**「失聯時還需不需要它」**：

| 意圖 | 執行者 | 理由 |
|---|---|---|
| `rtl`／`land`／`abort` | **代理** | 失聯時唯一還需要動作的東西，而且只要 `DO_SET_MODE`，不碰任務協定 |
| `pause`／`resume`／`change_route`／`start_mission` | **地面站** | 需要任務上傳與索引換算＝整套廠牌方言（`libs/autopilot`）。在樹莓派上重寫一份等於複製一個會漂移的事實來源；而這些動作**失聯時本來就不該發生**——沒有人在下意圖 |

**不論誰執行，守門一律先過代理。**

### 4.4b 提案只在代理上算（2026-08-25 裁定）

續飛航點是**對位置最敏感的判斷**，而地面站看到的位置經 5G 回來已經是過期
資料——10 m/s 巡航下一次鏈路抖動就是數十公尺誤差（本場域實測一次斷 98 秒）。
過期檢查同理：它問的是「機體從你確認到現在飄了多少」。

**地面站沒有備援副本。** 曾經有過一份，一天之內就決定拿掉——兩份相同實作的
症狀特別陰險：同一台機，有代理時飛去 A 點、代理掉線時飛去 B 點，沒有錯誤
訊息，只有事後看軌跡覺得哪裡怪怪的。等價測試能釘住它，但那是在管理一個
本來就不必存在的風險。

代價：**沒有代理的機做不了飛行中改航線**。那時候地面站回 409 `no_agent` 並
說明原因——不能算的時候說不能算，不要拿次一等的資料算一個看起來很正常的答案。 代理在 `hello` 裡宣告 `executes`（自己執行
哪些）與 `vets`（守哪些）——**能力用問的，不要用試的**：舊版代理不回 event，
不先問清楚就送過去只會等到逾時，然後「不知道＝不行」把所有飛行操作擋死。

守門的三種判決，**「不知道」歸到「不行」那一側**：

| 判決 | 意思 |
|---|---|
| `cleared`／`done` | 放行（或代理已執行） |
| `refused` | 擋下，理由原樣轉給操作員，並寫進事件流 |
| `no_agent` | 這台機沒有代理（或代理版本不守這個意圖）→ 沿用呼叫端原本的檢查。**守門是額外一層，不是唯一一層** |
| `unknown` | 逾時／斷線 → **擋下**。不知道守門怎麼說，在飛安路徑上就是不行 |

> **守門問在指令服務，不是問在前端。** 只在前端問的話它就不是守門——前端可以
> 不問，而且還有別的呼叫端（驗收 rig、MCP、curl）。要擋得住，就得擋在真的會
> 動到飛機的那條路上。

**同一個 `intent_id` 重送＝冪等**，不是再做一次。斷線重連後地面站可以安全重送。

### 4.4 `proposal`（代理 → 地面站，需要人確認時）

```json
{ "type": "proposal", "intent_id": "…", "expires_at": "…",
  "hold": { "alt": 25.0, "alt_delta_m": 4.9 },
  "resume_wp": { "seq": 5, "lat": …, "lon": …, "alt": 30.0,
                 "distance_m": 42.3, "bearing_deg": 48, "alt_delta_m": -3.0 },
  "steps": ["爬升至 25m 懸停", "上傳航線 B", "從第 5 點續飛"],
  "inputs_used": ["telemetry"],
  "warnings": ["續飛航點在目前航向後方 130°"] }
```

這份就是 UI 確認畫面要顯示的內容（狀態機文件 §6.3 逐項對應）。
`inputs_used` 讓人知道**這個判斷是根據什麼做的**——日後有 perception 時，
「有沒有用到影像」會直接影響人要不要相信它。

### 4.5 `decision`（地面站 → 代理）

```json
{ "type": "decision", "intent_id": "…", "approved": true }
```

**提案留在機上，地面站只回一個 id。** 把提案送回去等於讓執行端相信一份無法
驗證的東西——送回來的那份與人真正看到的是不是同一個，沒有辦法證明。留在機上
就沒有這個空間。

收到確認時代理做三件事，**順序有意義**：

1. **守門再過一次**（§5.2）。狀態可能在人看提案的時候變了——例如飛手拿起
   遙控器接管。人確認的位階低於守門。
2. **用最新位置重算並比對過期**（§5.1）。續飛航點換了就中止並附上新提案，
   要人重看，**不自作主張用新的執行**。
3. 兩關都過才標記序列開始。

### 4.5b `progress`（地面站 → 代理，序列逐步回報）

```json
{ "type": "progress", "intent_id": "…", "step": "hold", "ok": true }
```

丙案裡三步序列由地面站執行，但**代理必須知道序列跑到哪一步**——不是為了記帳，
而是 §7 規定「改航線序列中失聯 → 立刻 RTL」：序列跑到一半失聯，飛機停在一個
**沒有人確認過的中間狀態**（可能已經 hold、可能已經上傳但還沒續飛），
而接下來每一步都需要地面站，它已經不在了。

序列旗標有**死線**（`SEQ_TIMEOUT_S`，預設 120 s）。地面站中途掛掉時旗標會
留著，讓失聯處置一直以為序列在跑——**旗標卡住造成的誤判比沒有旗標更難查**。

### 4.6 `event`（代理 → 地面站）

序列每步完成、被守門擋下、失聯處置觸發，都送一則。**被擋下必須有具體理由**：

```json
{ "type": "event", "intent_id": "…", "event": "guard_refused",
  "reason": "續飛航點是 NAV_LAND——續飛過去會當場降落" }
```

## 5. 幾條不可省的語意

### 5.1 提案會過期，執行前一定重算

代理在**執行的那一刻**重新計算。若答案與提案有實質差異（續飛航點換了、
距離變化超過門檻、狀態變了），**中止並重新提案**，不照過期的提案做。

人確認的是**那一份提案**，不是「授權代理之後隨便怎麼飛」。

### 5.2 人的確認不能覆蓋守門

守門在代理上，且**位階高於 `approved`**。人按了確認，代理仍然可以拒絕並回
`guard_refused`。理由：人是在看提案時確認的，而守門檢查的是**執行當下**的事實。

### 5.3 代理不等地面站做安全決定

任何需要立即處置的情況（失聯、電量、飛控 failsafe），代理**自己決定**。
它不會為了等一個確認而讓飛機停在危險狀態。

### 5.4 `PILOT_CONTROL` 期間不下任何指令

飛手用遙控器接管時，代理只觀察、只回報。**收到的 intent 一律拒絕**並說明原因。

## 6. 失聯處置（2026-08-25 裁定：選項 C）

**判定**：WebSocket 斷開，或超過 `LINK_WARN_S`（預設 5s）沒有任何地面站訊息。

| 當下狀態 | 處置 |
|---|---|
| `FLYING_MISSION` | **繼續執行任務到結束，然後自動 RTL** |
| `HOLDING`／改航線序列進行中 | 立刻 RTL（沒有「任務」可以跑完，停在空中等一個回不來的確認毫無意義） |
| `TAKING_OFF` | 立刻 RTL |
| `ARMED_GROUND` | **只告警不動作**（見下方「實作時改掉的一格」） |
| `RETURNING`／`LANDING` | 不介入（已經在回家） |
| `PILOT_CONTROL` | **永不介入**（人拿著） |
| 未 armed | 只告警不動作 |

**兩個上限，任一命中就立刻 RTL 而不是跑完**：

1. **失聯後的單飛時間 > `LINK_LOSS_MAX_SOLO_S`**（暫定 120s）——「跑完」在
   3 分鐘的任務與 40 分鐘的測繪任務上，風險完全不是一回事。無人監看的長時間
   飛行不該因為「規則說跑完」就發生。
   > **實作時把「剩餘任務時間」換成「已經單飛多久」**：剩餘時間要靠航點距離
   > 與速度模型去估，而代理手上沒有任務內容，估出來的數字沒有可信度。單飛時間
   > 是碼錶讀數，而且它正好就是這條規則真正想限制的東西——沒人看著的飛行時長。
2. **電量 < `LINK_LOSS_MIN_BATT_PCT`**（暫定 40%）——電量餘裕要留給返航，
   不是留給把任務跑完。

> **兩個預設值都是暫定的**，要由實機續航測試定案：續航多久、返航要留多少電量
> 餘裕，是這台機的物理性質，不是可以在鍵盤上想出來的數字。在有實測之前取保守
> 值——保守的代價是任務被打斷，不保守的代價是掉機。

### 實作時改掉的一格：`ARMED_GROUND`（2026-08-25）

規格原本寫「立刻 RTL」，實作**刻意沒有照做**。機在地上時 RTL 會先爬到
`RTL_ALT`——那是一次沒有人按下的起飛，而且發生在「地面站看不到」的當下。
同一時間遙控器就在旁邊待命（這是本系統的操作前提），人處理比飛機自己起飛安全
得多。所以這格只告警留痕。**要改回規格行為必須是明確裁定，不是預設值。**

### 狀態怎麼判出來的（協定接上之前的近似）

意圖協定還沒實作，所以代理現在**沒有**那台權威狀態機可讀，只能用 MAVLink
看得到的東西近似：模式、armed、相對高度、地速、`MISSION_CURRENT`。每一格都往
「不要亂動」的方向偏——分不出來就當飛手拿著。

| 觀察到的 | 判成 |
|---|---|
| 未 armed | `DISARMED` |
| RTL／LAND／SMART_RTL／AUTO_RTL | `RETURNING` |
| 高度 < 1m 且地速 < 0.5m/s | `ARMED_GROUND` |
| AUTO 且 `mission_state` ≠ COMPLETE | `FLYING_MISSION` |
| GUIDED、或 AUTO 但任務已完成 | `HOLDING` |
| LOITER **且是我方要求的** | `HOLDING` |
| 其餘（含溯源不明的 LOITER） | `PILOT_CONTROL` |

**LOITER 為什麼要溯源**：它既是地面站的「暫停」（`libs/autopilot/ardupilot.py`
的 `hold` 就是 5），也是飛手最常用的手飛模式。兩者的處置完全相反——前者要 RTL，
後者永不介入。代理是地面站指令送到飛控的必經之地，所以只要看一眼經過的
`SET_MODE`／`DO_SET_MODE` 就知道是不是我方要求的，不必另開通道問。

判定只在**模式變化的當下**做一次：若每拍都拿「我方曾經要求過 LOITER」去比對，
飛手把 LOITER 切走再切回來就會被誤認成我方的暫停，然後在他手上飛的時候送 RTL
——那正是這套規則最該避免的操作。

接上協定之後，這張近似表換成讀權威狀態即可，處置規則不用動。

鏈路恢復後**不自動改變當下行為**（例如不會把已經開始的 RTL 取消）——恢復只
解除警戒並留痕，要不要繼續是人的決定。

## 6b. 續飛的機制（2026-08-25 兩家 SITL 實測定案）

### 為什麼「續飛」是必要動作而不是優化

飛行中上傳新任務後，**兩家都不會把 `MISSION_CURRENT` 歸零**，而是把舊任務的
索引原封沿用到新任務上：

| | 上傳前 | 上傳後 | 結果 |
|---|---|---|---|
| PX4 1.14.3 | seq 2（A 的第 3 點） | **seq 仍是 2** | 直奔 B 的第 3 點 |
| ArduPilot 4.0.3 | seq 3 | **seq 仍是 4** | 直奔 B 的對應點 |

舊任務的第 N 點與新任務的第 N 點**毫無關係**。不主動指定的話，飛機會飛到一個
純粹由「上一份任務碰巧進行到第幾點」決定的位置——**那不是次佳解，是未定義行為**。

### 用訊息 41，不是指令 224

| 機制 | PX4 1.14.3 | ArduPilot 4.0.3 |
|---|---|---|
| `MAV_CMD_DO_SET_MISSION_CURRENT`（指令 224） | ❌ `MAV_RESULT_UNSUPPORTED` | ❌ 同左 |
| **`MISSION_SET_CURRENT`（訊息 41）** | ✅ **生效** | ✅ **生效** |

224 是後來才加進 MAVLink 的指令形式；41 是任務協定的原生做法（QGC 一直用它）。

> **這件事差點把設計帶偏。** 只試 224 就會得到「兩家都不支援」，然後被迫走
> 備案——上傳前重排航線讓最近點變成索引 0。那條路能動，但代價是**機上任務與
> 任務庫的順序不同**，回放與前後比對會對不起來，還要額外存一份「這趟實際飛的
> 順序」才不會讓資料說謊。**能不引入這個複雜度就不要引入。**

### 41 沒有 ACK——驗證只能看效果

送出後**讀回 `MISSION_CURRENT` 確認機端真的跳過去**，3 秒內沒跳就報錯。
這符合本專案既有的紀律：ACK 是「我收到了」，不是「我做到了」。

實測證據無歧義：兩家都**掉頭往回飛**到指定的航點——自然前進永遠不會倒退，
所以沒有第二種解釋。

### 索引換算走驅動

API 收的是**我方航點索引**，機端 seq 由 `Driver.wire_seq()` 換算：

    我方索引 0  →  PX4 送 seq 0 ／ ArduPilot 送 seq 1（home 佔 0）

同一個 API 呼叫，兩家送出不同數字，呼叫端不需要知道差別。
**少了這層換算會差一個航點，而且沒有任何錯誤訊息**——飛機安靜地飛到隔壁那點。

### ⚠ 版本限定

以上是 **PX4 1.14.3** 與 **ArduPilot 4.0.3** 的行為。機上實機是 **4.7.0**，
差 7 個 minor 版本。**首飛前必須在真機上覆核**——機體上鎖時送這則訊息是零風險
的查詢，它只會回報機端怎麼處理。

## 7. 尚未定

1. 兩個上限的**實際數值**（`LINK_LOSS_MAX_SOLO_S`、`LINK_LOSS_MIN_BATT_PCT`）。
   建議由一次真機續航實測反推，而不是拍腦袋。
2. 「續飛航點」的目標函數細節：目前是**水平最近的導航航點**（機制見 §6b）。
   是否要加入「不選在航向後方」「不選需要大幅下降」等權重，需要定義清楚——
   **沒寫明的目標就是意外行為的來源**。實測時看到兩家都會為了回到指定航點而
   **掉頭往回飛**，所以「在航向後方」是真的會發生、而不是理論情況。
3. `proposal` 的「實質差異」門檻（距離變化多少算實質）。
4. ~~多機時一個代理對一台機~~ → **一對一定案**（2026-08-25）。同一個
   `board_uid` 出現第二條意圖通道時**新的贏、舊的關掉**：最常見的情況是
   半開的 TCP（舊連線其實已經死了、只是還沒 FIN），讓舊的贏會讓真正活著的
   代理永遠連不上，而畫面上看起來一切正常——有連線、有狀態，只是狀態永遠
   停在斷線前那一刻。舊連線**還新鮮**時會記一筆警告：那代表真的有兩個代理
   指向同一台機（例如 Pi 被複製、`board_uid` 跟著複製），兩個代理各自守門、
   各自算提案，飛機會收到互相矛盾的指令。
