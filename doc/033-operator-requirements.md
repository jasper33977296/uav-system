# 033 · 操作者視角需求（UI/UX 供稿，待併入分層防線設計文件）

供 033 設計文件第 4 層（地面站防呆）與跨層呈現使用。**本文只寫需求與判準，
不動 `doc/ui-spec.md`**；核可後再回寫規格。

前提：使用者是**新手操作者**，介面走簡約風（除事件與 log 外不放解釋性文字）。
緊急態是**唯一容許畫面變吵的時刻**——但吵的內容必須全部可行動。

---

## 一、緊急狀態下，操作者要一眼看到什麼

緊急時操作者只有一個決策要下：**我現在還能不能控制它，不能的話它自己會做什麼。**
畫面要按這個順序回答，不是按資料結構的順序。

| 序 | 問題 | 呈現要求 |
|---|---|---|
| 1 | **哪一台** | 色點**必配文字標籤**（既有硬規則）——緊急時色盤記憶最先失效 |
| 2 | **故障在哪一段** | **機／鏈路／地面站三分**，見第三節。這是最重要的一項 |
| 3 | **多久了** | **絕對秒數**（「已 12 秒」），不得用「剛剛／稍早」——failsafe 是時間驅動的 |
| 4 | **機自己正在做什麼** | failsafe 階段：尚未觸發／已觸發（RTL／降落／懸停）／已完成 |
| 5 | **我還能做什麼** | 當下可用與不可用的指令，**不可用要附原因**（第二節） |

**倒數優於狀態名。**「失聯」是狀態，「**距 datalink failsafe 觸發約 8 秒**」才可行動。
但**倒數只有在門檻已知時才准顯示**——門檻來自機上參數（021 Phase 2 參數快照）。
**參數未知時顯示已失聯秒數即可，不得推測門檻**（不猜不硬翻，同 §0.2d 既有立場）。

**版面要求**：緊急態的呈現**必須非 hover、非收合、無需捲動即可見**。
理由是本次事故調查的教訓——**收合區裡的告示與沒有告示，在量測與使用上完全同形**。
正常態則完全不出現（簡約風不因緊急需求而在平時付出版面代價）。

**顏色不得單獨承載語意**：紅色必須同時有文字與形狀差異（既有全站規則）。

## 二、緊急操作的 UI 原則

**1. 隔離靠空間與尺寸，不靠確認步驟。**
「緊急操作單擊即發」是既有的刻意安全設計，**不得為了防誤觸而加確認對話框**——
那會在最需要速度的時刻增加步驟。防誤觸改用**分區＋間距＋尺寸**達成：
緊急鈕不與一般操作同區、不相鄰、不共用樣式。

**2. 不可用的指令不得只是變灰。**
灰按鈕在緊急時是最糟的呈現：操作者**既不知道為什麼、也不知道能否補救**。
要求：**拒絕原因就地顯示**，且原因必須可行動——
「未驗證機型，指令已鎖定」（我方保護，可解）與
「鏈路中斷 8 秒，指令送不出去」（環境問題，等或換通道）是**完全不同的處置**。

**3. 事前可查證的前提，不要讓使用者用失敗去發現**（§0.2c 既有）。
能事前判定不可用的，**在按鈕上就標明原因摘要**，而不是按下去才說。

**4.「不可用」與「不知道能不能用」必須分開。**
鏈路中斷時，正確答案不是「指令不可用」，而是
**「送得出去，但無法確認會不會執行」**。把後者顯示成前者，
會讓操作者放棄一個其實可能成功的動作。

**5. 送出 ≠ 生效，收到確認前不得顯示成功。**
緊急指令（RTL／降落／切手動）**必須等到觀測到機體實際狀態改變才算數**。
在確認前顯示「已送出」，**不得顯示「已返航」**。
理由：緊急時操作者會據此停止其他補救動作——**假的成功比明確的失敗更危險**。

## 三、「系統自己就是風險源」的呈現

本節是本次事故的直接產物，也是 §0.2e（失效不得冒充合法狀態）的正面應用。

**1. 三種故障絕對不得互相冒充**（既有三分的緊急版）：

| 實際故障 | 意義 | 操作者該做的事 |
|---|---|---|
| `link_state` 劣化 | 訊號差，**機還在飛** | 等待／機自己會 failsafe |
| `link_age_s` 過大 | 量測送不回，**我們瞎了**，機可能正常 | 換通道確認，勿貿然處置 |
| **地面站自身斷線**（`wsConnected=false`） | **機與鏈路可能都正常，是我們的問題** | **不要對飛機做任何事**；修地面站 |

**第三種顯示成前兩種是最嚴重的呈現錯誤**：操作者會對**一台完全正常的飛機**
執行失聯處置。這是「誤判方向相反的錯誤比不顯示更糟」的最強實例。

**2. 故障的偵測不得依賴故障的那條路徑。**
「多久沒收到資料」必須由**前端本地時戳**計算（比照 deadman 既有決定），
**不得等後端告訴我們**——**依賴故障源去報告故障，等於沒有報告**。

**3. 畫面必須能證明自己還活著。**
最陰險的失效是 **UI 停止更新但看起來完全正常**（數字都在，只是不動了）。
要求：畫面上**必須有一個由本地時鐘驅動、持續變化的元素**
（如「最後更新於 N 秒前」）。**一個會自己變的數字，是畫面還活著的唯一證明**；
靜態畫面無法與凍結畫面區分。

**4. deploy guard 擋下操作時，操作者要知道。**
靜默擋下等於操作者不知道剛剛差點中斷連線。要求：
**記入事件流一條**（可事後追），**不用 toast 搶飛行中的注意力**。
反之若 guard **未能**擋下（例如偵測不到 armed 狀態），
**必須明說「無法確認機體狀態，未執行防護」**——不得靜默放行。

**5. 版本身分在事故當下就要可見**（§0.2f 已實作）：
未知版本必須非 hover 可見。本次事故的還原成本，
有相當部分來自「系統說不出自己是哪一版」。

## 四、對後端／command 的資料需求

呈現要成立，需要下列欄位；**缺哪一項，對應的呈現一律走「不知道」而非略過**：

1. **failsafe 門檻**（datalink loss／RC loss／低電量的行為與延遲）——來自參數快照。
   有值才准顯示倒數。
2. **failsafe 當前階段**（尚未觸發／已觸發何種行為／已完成）——
   若只能從模式推測，**必須標為推測，不得當事實**。
3. **指令可用性與拒絕原因**（比照既有 `not_ready_reasons` 形狀，逐條可讀），
   且要能區分「明確不可用」與「狀態未知」。
4. **地面站自身連線狀態**與**最後收到資料的本地時戳**（前端可自算，
   但需後端不覆蓋、不偽造心跳）。
5. **deploy guard 的判定依據與結果**（含「無法判定」這一態）。

---

## 五、明確不做

- **不加緊急操作的確認對話框**（見二·1）。
- **不在正常態顯示任何緊急相關版面**（簡約風不預付代價）。
- **不推測未知的門檻與階段**——寧可顯示「已失聯 N 秒」而不給倒數。
- **不把地面站問題包裝成機體問題**，即使那樣的文案比較簡短。
