# GCS 取代計畫：自製功能取代 QGC（含群組任務）

2026-08-10 討論定案。目標：**作業流程取代**——例行量測飛行完全不開 QGC；
QGC 降級為板凳工具（校準/參數/韌體）與場域緊急備援。

## 0. 不變的底線

- **手動控制＝實體遙控器，系統不做連續操縱**（2026-08-24 使用者定案）。
  系統範圍收斂為「載入／執行／中斷／中途更改飛行路徑，並絕對確保飛行過程的
  安全操作」，虛擬搖桿已整塊移除（[issue 035](../issues/035-remove-manual-control.md)）。
  **RC 實體遙控在自駕儀端永遠優先，可隨時接管——這是法規上操作員在場的底線，
  不變**；也正因為它現在是唯一的手動接管路徑，**不得為了方便而關閉飛控預檢的
  RC 檢查**。

  > 沿革：2026-08-11 曾定案「帶安全鐔的監督式虛擬搖桿」（理由是實機須先手動
  > 飛到高度才能執行任務），推翻更早的「不做虛擬搖桿」；2026-08-24 再次推翻，
  > 回到不做。三次轉向都記在這裡，因為**「為什麼又改回去」比「現在是什麼」
  > 更容易被後人問到**。
- **Failsafe 留在 PX4**。地面站負責觸發與顯示，不接管安全邏輯。
- **ingest 維持唯讀**。「backend 對 MAVLink 唯讀」從全系統規則改為
  模組邊界：指令能力放在獨立 command 服務，這是刻意決策（見 §1）。

## 1. 架構：獨立 command 服務

```
                    ┌──────────────────────── 地面站 ────────────────────────┐
  機上 mavlink-router│  backend（ingest，唯讀）      command 服務（新）        │
   ├─ udp 14540 ────┼─▶ 遙測入庫/廣播               ├─ MAVLink 雙向連線池     │
   ├─ udp 14541 ────┼──────────────────────────────▶│   （依 drones 表逐台）  │
   └─ tcp 5760（動態│                                ├─ 指令佇列＋ACK 追蹤    │
      QGC 緊急接入） │   PostgreSQL ◀── 指令留痕 ────┤─ 1Hz GCS 心跳（逐台）  │
                    │   前端 ◀────── REST/WS ───────┘                        │
                    └────────────────────────────────────────────────────────┘
```

- **常設端點兩個**：ingest（14540 唯讀）＋ command（**生產 14541** 雙向）。
  QGC 緊急接入走 router 動態 TCP 口（5760），不設常設第三端點。
  > **埠的環境分歧（實測，勿混淆）**：上面 14541 是**生產**——機上
  > mavlink-router 主動把指令通道打到 GS:14541。**SITL 開發環境不同**：
  > PX4 SITL 沒有 onboard router 拆通道、只會廣播到 **14550**（QGC 慣用埠），
  > 所以 SITL 的 command 服務改聽 **14550**（`COMMAND_MAVLINK_URL=udpin://0.0.0.0:14550`，
  > 見 `.env.example`、`config.py` 註解）。config 預設值是 14541（生產）；
  > SITL 靠本機 `.env` 覆寫成 14550（`.env` 為 gitignore、不入庫）。
  > **後果**：SITL 下 command 與 QGC **同搶 14550**，同機不能並存（互斥；
  > 見 issues/016）。生產 command 在 14541、與 QGC 的 14550 分開，無此問題。
- **單埠多機（2026-08-10 定案）**：所有機都打同一組埠，逐框架以
  MAVLink `sysid` 區分（QGC 同款拓撲）。機上設定全隊相同（只差
  `MAV_SYS_ID` 參數）、防火牆單規則、加機零地面站設定。
  capture tee 升級為 sysid demux（per-sysid 內部埠＋mavsdk 實例，
  回程依來源位址原路送回）；`drones.mav_sysid` 承擔身分對應，
  「主機」概念退役。防呆：同 sysid 異位址 → 告警（撞號＝靜默混料）。
- **sysid 254**（QGC 慣用 255）：板凳期並存可辨識；偵測到 255 心跳時
  UI 顯示「QGC 連線中」（單一指揮權可視化）。
- **心跳即安全鏈**：QGC 退場後 command 服務是 PX4 唯一的 GCS，
  `COM_DL_LOSS_T` 逾時沒收到心跳→PX4 執行 `NAV_DCL_ACT`（設 RTL）。
  服務存活屬飛安相關：Restart=always、健康端點、飛行中斷線前端大聲警告。
- **從第一天就是多機架構**：連線池依 `drones` 表的 connection_url 逐台
  建立（與 issue 011 的 ingest 多實例化同一份註冊表）；所有 API 帶
  drone_id，不做單機假設——群組任務（§3）建立在這之上。
- 指令佇列：`COMMAND_LONG/INT` → 等 ACK → 重送 → 逾時明示失敗。
  **無 ACK 不得顯示成功**。緊急指令（RTL/Hold/Land）走獨立路徑、前端常駐。
- 任務上傳：MAVLink 2 `MISSION_ITEM_INT` 完整握手，上傳後**下載回讀
  比對**才顯示「已上傳」。
- 指令留痕入庫（誰、何時、參數、ACK 結果）——同時是實驗記錄。
- `ENABLE_COMMANDS` 預設關，部署時顯式開啟。

## 2. 監看補齊（階段 1，backend，仍唯讀）＝兩層收集

原則（2026-08-10 定案）：**任何無人機傳出的資訊都要收集到**。不逐種訊息
挑選，分兩層：

### 2a. 原始層（已實作，`app/capture.py`）

MAVLink 每一個框架**先無損落盤再轉發**（透明 tee：backend 綁 14540，
ingest 的 mavsdk 改聽內部埠 14549，回程原路轉回）。tlog 格式
（QGC 回放／pymavlink 工具鏈相容），UTC 日切檔於 `mavcap` volume，
`CAPTURE_KEEP_DAYS`（30）滾動清理。實測待機 ~16.5 KB/s（61 MB/hr）。

價值：今天沒解析的訊息（ESC/震動/EKF/⋯）明天要研究時歷史還在，
重放解析即可——與 modem 端保留 `at_qeng` raw 同一哲學。錄製失敗
不拖垮資料路徑；啟動失敗自動退回 ingest 直連。

盤點（實測）：待機 27 種週期訊息 ~368 則/s；另有事件/回應型 ~12 種
（STATUSTEXT、COMMAND_ACK、MISSION_ACK 等——**量小值高，任務上傳
失敗的原因碼就在 MISSION_ACK**）；ulog（機上全速率日誌，100+ topic）
屬事後回收，列階段 2+ 待辦。

### 2b. 結構層（UI 與分析用，逐步擴充）

- STATUSTEXT 入事件流（PX4 警告與拒絕解鎖原因；沒有它操作員是瞎的）
- `MISSION_CURRENT`（任務進度）、`SYS_STATUS`（感測器健康）、RC 訊號狀態
- `COMMAND_ACK`／`MISSION_ACK`（指令與上傳結果，含原因碼）
- 完成判準：例行飛行中 QGC 可最小化，只在下指令時打開

## 3. 群組任務（群飛同時配置飛行路徑）

> **完整設計定案見 [group-missions-design.md](group-missions-design.md)**
> （2026-08-11 三方討論＋PM 裁決：地面展開 per-drone 實體任務、mission_groups
> 資料模型、兩階段狀態機、嚴格 execute gate、check_group、切批 011→013）。
> 本節為原始草案，細節以該文件為準。

QGC 多機支援弱（能看不能派），這是自製 GCS 超越它的部分；研究價值：
**N 台同測＝一次飛行取得鏈路品質空間分布**（垂直剖面／平面分割掃描）。

### 資料模型

- `groups`（群組）＋ `group_assignments`（group × drone × mission 指派）。
- 任務庫「路徑不綁機」原則不變（issue 010）：group 是配置單位不是擁有者。

### 指派方式（三種都要，分版實作）

| 版本 | 方式 | 說明 |
|---|---|---|
| V1 | 手動逐台指派 | 群組裡每台從任務庫挑一條，最通用 |
| V2 | 基準路徑＋自動偏移 | 一條軌跡生成同軌不同高／橫向編隊副本；高度分層同時就是去衝突手段（研究首選：垂直剖面） |
| V3 | 區域自動分割 | 畫掃描區切給 N 台；實作最重（路徑生成演算法），架構驗證後再做 |

### 起飛時序：嚴格同時（兩階段提交）

PX4 無跨機同步，「同時」＝地面站並行廣播 start（誤差數十 ms，量測對齊足夠；
回放已有相對時間對齊）。失敗處理是設計核心：

1. **階段一（地面，可逆）**：逐台上傳＋回讀比對 → 全部 arm。
   任一台 prearm 失敗 → **全組地面撤銷**（disarm all），零風險中止。
2. **階段二（提交）**：全部 arm 成功才並行廣播 mission start。
3. **空中失敗政策**：起飛後單台異常＝該台自動 failsafe（RTL），
   **其他台繼續**——量測任務少一台是資料缺片，不是安全事件；
   全體中止另有 RTL-all 緊急鈕。

### 去衝突（規劃期責任，PX4 之間不會互相避讓）

- 派發前檢查：同時飛的路徑需高度分層（≥N m）或橫向分離（≥M m），
  不過檢查不開放上傳。規模 >6 台時升級為時空檢查（同時刻位置對）。
- **RTL 高度逐台錯開**：全組同高返航會在 home 上空匯合；派發時自動
  設定分層 RTL 高度，大規模時加橫向返航走廊。

### 規模：研究願景為大於 6 台，驗證路徑由小到大

2–3 台（高度分層即可）→ 4–6 台（高度＋橫向組合）→ 更多（時空檢查）。
UI 狀態矩陣從第一版就設計成可滾動的逐台列表，不做固定欄位。

### 方法學注記（多 UE 互測干擾）

N 個 UE 掛同一 cell 會互相影響鏈路品質——多機同測時「其他機的流量」
本身是量測變因：量測期壓低影像碼率（控制），樣本含 cell_id/PCI 可
事後歸因（記錄）。這對研究可能是題目而非只是干擾。

## 4. 階段總表與驗收

| 階段 | 內容 | 驗收（先 SITL 後真機） |
|---|---|---|
| 0 | 機上 mavlink-router 兩常設端點 | QGC 關閉後遙測不中斷 |
| 1 | 監看補齊（仍唯讀） | 例行飛行 QGC 可最小化 |
| 2 | command 服務：單埠路由/心跳/指令佇列/任務上傳/RTL ✅（2026-08-10 SITL 驗收：上傳回讀比對→arm→start→空中 RTL→自動上鎖，留痕完整） | 拔心跳→PX4 依 `COM_DL_LOSS_T` 執行 RTL（真機設定時實測）；ACK 遺失注入→UI 顯示失敗 |
| 3 | 解鎖/起飛入 UI（滑動確認；拒絕原因就地顯示） | 全流程不開 QGC 完成一次量測飛行 |
| 4 | 群組任務 V1→V2→V3 | 兩階段提交中止測試（單台 prearm 失敗→全組地面撤銷）；SITL 多機同時起飛；RTL 分層實測 |
