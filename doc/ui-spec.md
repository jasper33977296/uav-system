### 0.2b 三種「非正常」不得互相冒充（2026-08-12 裁定，混機情境）

混機時同一畫面會同時出現三種非正常狀態，**視覺與語意必須三分，不得
共用樣式**——它們對操作者的意義完全不同：

| 狀態 | 意義 | 視覺 | 文案 |
|---|---|---|---|
| **未就緒** | 知道不行（有明確原因） | 黃點 `--status-warn` ＋原因行 | 「未就緒」＋ not_ready_reasons 逐條 |
| **遙測不足** | **不知道**（判斷依據本身缺席） | **灰空心點**（`--muted`、空心＝無斷言）| 「**尚無足夠遙測**」——不寫「就緒」也不寫「不可飛」 |
| **未驗證鎖定** | 協定未驗過，刻意保護 | warn 黃底橫幅＋機型徽章 | 「此機型控制尚未驗證，指令已鎖定」（既有 §2.5）|
| （對照）故障 | 壞了 | 紅 `--status-danger` | 錯誤原文 |

**判定規則**：`ready=true` **但其依據欄位（prearm_ok／ekf_ok）皆為 null**
時，**不得顯示綠燈「就緒」**——那是**沒有依據的布林值蓋過一整排空白**，
屬「空值繞過」的變體（前例：§0.1 徽章顯「—」等於形同移除）。此時一律
走「遙測不足」灰空心態，直到依據欄位有值。

**為什麼不能沿用紅色**：「不知道」與「壞了」若同色，操作者會把一台
剛連上、還沒送齊遙測的正常機當成故障機處置——**誤判方向相反的錯誤，
比不顯示更糟**。同理「未驗證」是我方刻意保護、非機體異常，用 warn 不
用 danger。

### 0.2e 兩種「灰」不得同形：沒量到 vs 有量測但沒有這個欄位（2026-08-13）

分級軌跡在無 SINR 時退回灰線。但**灰線目前同時承載兩種完全不同的
狀況**，而它們在畫面上一模一樣（實測：欄位名由 `sinr` 改為 `snr`，
灰線像素數與「真的沒量到」完全相同）：

| 情況 | 成因 | 目前呈現 | 應有呈現 |
|---|---|---|---|
| 完全沒有 link 樣本 | 這趟沒收訊號資料 | 灰線 | 灰線＋「這趟沒有訊號量測」 |
| **有 link 樣本，但 SINR 全為 null** | **上游改欄位／我方對映失效** | 灰線（同上，無從分辨） | 灰線＋「**有 N 筆量測，但沒有 SINR 值**」 |
| 部分樣本無 SINR | 量測斷續 | 該段灰 | 該段灰（不補值，維持現況） |

**判定極廉價且確定**：`link.length > 0 && sinr 非 null 數 === 0`。
一個布林運算就把**看不見的失效換成看得見的陳述**。

**為何必須分**：第二種幾乎一定是缺陷（有人送了量測卻沒有這個欄位），
但它偽裝成第一種——**一個合法、常見、不會有人追問的狀態**。使用者
只會記下「這趟沒訊號資料」而繼續研究，**上游欄位改名可以就這樣活過
整個實驗**。這是 §0.2b 的同族：**失效不得穿上合法狀態的外衣**；
差別只在這裡冒充的不是另一種非正常，而是**一種正常**——更難察覺。

**通則**：凡「缺值即退回中性呈現」的地方，都要能回答
**「是沒有這筆資料，還是這筆資料裡沒有這個欄位？」**——答不出來，
該處就存在一個永遠不會被回報的失效。

**同族第三種：我方取得失敗被說成「沒有資料」。** `fetch` **不會**因
HTTP 5xx 而 reject，而錯誤回應的 body（`{"detail": …}`）是合法 JSON——
`d.link ?? []` 於是得到空陣列、流程視為成功，畫面說出「這趟沒有訊號
量測」。**後端掛掉時，即時頁會宣告飛機一切正常。** 取用點一律先看
`r.ok` 再 `json()`，失敗說「無法取得…」而非「沒有…」。

**「兩種狀態塞進同一句括號，等於兩個都沒宣告」**（回放頁實例：
「載入軌跡中…（若架次無樣本則無可回放）」——載入卡住時看起來像沒
樣本，沒樣本時看起來像還在載）。**每個狀態各自有話，才叫有宣告。**

**這類缺陷與注意力無關**：§0.2e 的修正在同一個 commit 裡就犯了 §0.2e
要防的錯（`.catch()` 接不到 5xx）。**防線只能是被測試釘住的陳述，
不能是「記得要注意」。**

**兩道防線分工不同，缺一不可**：**型別/介面防初次犯**（呼叫端根本拿
不到「靜默變成空陣列」這個選項），**測試防回歸**（有人改回去就紅）。
測試只覆蓋想得到的失敗，所以不能當唯一防線；反之沒有測試釘住，
介面日後會被繞過。

**同句混態實測清單（2026-08-13 掃全庫）**：已修——回放頁「載入軌跡中…
（若架次無樣本則無可回放）」、比對回放頁「載入中，或此路徑尚無已完成
的航線」、比較頁「載入兩趟軌跡中…」；**未修——機隊頁
`app/drones/page.tsx:309`「讀取中，或 backend 未連線」**（同一形狀第四
例）。**此形狀比 `r.ok` 更常見**，因為它不需要任何錯誤發生就已經是
錯的：句子本身就拒絕宣告。

### 0.2f 系統必須能陳述自己是哪個版本（2026-08-13，事故調查暴露）

**現況（已查證）**：`apps/frontend/Dockerfile` 是 `COPY . . && npm run build`，
**全 repo 的 Dockerfile 與 compose 皆無任何版本注入**（無 git sha、無 build id、
無 LABEL）。部署環境**無法回答「我是哪個 commit」**。

**後果**：2026-08-13 真機事故調查中，「事故環境帶有哪些已知缺陷」只能靠
**bundle 內容指紋考古**（UI 字串出現/消失夾區間；連字串都沒變的修正還得比
minify 後的語句順序）。**每一次事故都要重做一次考古**，而考古的每一步都可能
把判準套錯對象——本輪已實際發生兩次（見 §0.2e 註）。

**要求**：
1. **建置時注入 git sha**（build arg → 環境變數），**工作區不乾淨時標記 `-dirty`**。
2. **UI 可見**：設定／關於處顯示 build id；不佔用飛行畫面版面。
3. **端點可讀**：提供版本端點，讓調查與自動檢查不必開瀏覽器。
4. **`-dirty` 或缺版本一律顯示為「未知版本」**，不得留空——
   §0.2e 同一條：**「不知道」要說出來，不能靠畫面上沒東西表達**。

**為何這屬 UI/UX 而非只是維運**：操作者與調查者是**同一群人**，而
**一個無法陳述自身狀態的系統，等於要求使用者用考古來取得本該直接顯示的事實**。
這與我們整輪在修的是同一件事——**把看不見的事實換成看得見的陳述**。

### 0.2d `mode_verb`：跨廠牌模式語意的用法（2026-08-12）

後端提供 `mode_verb`（`hold`／`mission`／`rtl`／`land`／`position`，
未知或解不出＝`null`）作為**廠牌無關的模式語意**，與顯示用的
`flight_mode` 並存。實測：PX4 `HOLD`→`hold`、ArduPilot `LOITER`→`hold`。

**用法三條（顯示與判斷分離）**：

1. **顯示層永遠用 `flight_mode` 原廠模式名**——那是機端真的在跑的模式，
   照「機上原文不翻譯」原則。**`mode_verb` 不得取代顯示**。
2. **判斷層一律用 `mode_verb`**：狀態判定、事件摺疊、跨機一致性檢查、
   任何「這台機在做什麼」的程式判斷。**禁止比對 `flight_mode` 字串**
   ——PX4 `HOLD` 與 ArduPilot `LOITER` 是同一件事，比字串必在混機時錯。
3. **混機時的人話註記**：≥2 種 autopilot 同時在線時，模式名旁加語意
   括注（`LOITER（定點停懸）`）——**單一廠牌時不加**（無歧義就不加字，
   簡約優先）。`mode_verb=null` 時**不加註記也不猜**。
   **顯示位置僅兩處：任務控制狀態列、事件流 mode_change 句。**
   （**IMU 卡無模式列**——§2.6 定案時已將「就緒／模式／GPS」自抽屜刪除，
   理由是與面板狀態列重複；本節初稿誤列第三處，2026-08-12 更正。
   **記取**：規格引用其他章節的既有元素時須查證其現況，我方文件本身
   也會過時——這與程式註解留在舊世界是同一種失真。）

### 0.2c 「受限」態的呈現（2026-08-12 裁定，起因 ArduPilot 搖桿需機端 SYSID_MYGCS=254）

四態中「受限」＝**能力存在，但有使用者可自行滿足的前提**（對照：
「未驗證」＝我方尚未驗證、使用者無從自行解除）。三點定案：

1. **按鈕可按，不禁用。** 理由：前提在**機端**、我方無法探知是否已滿足
   （設好了也不會通知我們）。禁用等於替使用者判定「你沒設」——那是
   我方不知道的事。禁用還會讓已正確設定的使用者**永遠無法使用該功能**。
2. **視覺區別（不可混淆）**：
   | 態 | 語意 | 按鈕 | 標記 |
   |---|---|---|---|
   | 受限 | **可以按，但你要先做一件事** | **可按** | 鈕旁 `ⓘ` 弱色＋常駐前提句（一行，非橫幅） |
   | 未驗證 | **現在不准按** | **禁用** | warn 黃底橫幅（既有 §2.5）|
   受限**不用 warn 黃底**——黃底是「我方擋下」的語言，受限沒有擋。
3. **前提句常駐、不藏 tooltip**：例「需在機上設定 `SYSID_MYGCS=254`，
   否則指令會被忽略」。**因為失敗是靜默的**（指令被丟棄、無錯誤回傳），
   使用者沒有其他線索可循——這是唯一會告訴他真相的地方。
4. **靜默失敗的補償（關鍵）**：受限能力按下後，若**逾時未見預期狀態
   變化**（如搖桿送出但 flight_mode 未進手動、無姿態回應），
   **視同失敗並顯示該前提句**——不得永遠停在「送出中」。
   **原則：能力標記為受限時，UI 必須有能力偵測它的失敗**；否則
   受限與 ok 對使用者而言無異，標記形同虛設。

5. **偵測不到失敗時，必須降級為「未驗證」**（2026-08-12 實例）：
   ArduPilot 搖桿經後端協定分析——`MANUAL_CONTROL` 是**串流式輸入、
   MAVLink 協定上無 ACK**，機端信不信我方 sysid，我方看到的完全一樣；
   間接觀測（推桿後姿態變化）又受限於「只有飛行中可測、風擾與位置
   保持會誤判、且判定時機正好是操作員推桿沒反應的最危險那幾秒」。
   故**標 `unverified`（鎖住）而非 `limited`（可按但永遠不告訴你失敗）**。
   能力提示需同時寫明「為什麼鎖著」與「怎麼解」。

5b. **每廠牌數值限制必須是 UI 可讀的契約，不得是內部常數**
   （2026-08-12，起因：起飛高度預設 `10.0` 全域寫死不分廠牌）。
   若某廠牌最低起飛高度為 15 m，UI 上的「10」看起來與任何正常數字
   無異，使用者無任何線索——**我方替使用者做了一個我方沒有依據的
   判定**（同 §0.2c 形狀）。規則：**輸入欄位的預設值／最小值／最大值
   凡因機型而異者，一律由後端 `limits()` 隨 capability 提供，UI 不寫死**
   （同 `retention_days` 手法：單一事實源，顯示值與實際約束不可能不一致）。
   缺 limits 時：**不套用任何預設數字**，顯示佔位提示要求使用者輸入，
   而非假裝我方知道安全值。

6. **優於「事後偵測失敗」的作法：事前讀機端參數確認前提**（後端提出、
   採納為未來方向）。連上時讀 `SYSID_MYGCS`：等於 254 才把該能力開為
   `ok`，否則維持鎖住並顯示**具體事實**「機端 SYSID_MYGCS=255，需改為
   254」。**這比 limited 更符合誠實原則**——給的是可行動的事實，而非
   讓使用者按下去等一個靜默失敗。**通則：前提可事前查證時，就不要
   讓使用者用失敗去發現它。**

#### 規則

0b. **PX4 事件字典的呈現（014 落地，2026-08-13 裁定）**

   實測資料形狀（同一批事件內即混合）：
   ```
   有字典：event_name=check_modes_manual_control, text="No manual control input", dict_fw=1.14.3
   無字典：event_name=null, text=null, dict_fw=null（只有 event_id 與 args）
   ```

   **(a) 英文原文不翻譯成中文——維持既有原則。** 與 `LOITER（定點停懸）`
   的差別在**可窮舉性**：模式名是少量固定集合，PX4 事件文字有數百條且
   **隨韌體版本變動**——自建中文表＝**複製上游知識並保證漂移**（§0.2d
   同一原則：語意只能有單一來源）。且操作者同時使用 QGC（亦為英文），
   **術語一致比翻譯更有用**；翻錯比不翻更糟。
   **例外**：`event_name` 若對應到我們**已有中文語彙的既有事件**
   （如 `navigator_rtl_home_activated` ↔ 既有「自動返航」），可比照
   §0.2d 加括注——但**靠 event_name 對應、不靠 text 字串比對**。

   **(b) 混合狀態是誠實行為，但不得讓「無翻譯」看起來次要。**
   有 text → 顯示原文；無 text → 「機上事件 #<id>」（既有）。
   **兩者的 severity 樣式、排序、可點擊性完全相同**——
   **缺翻譯是我方字典的限制，不是事件本身不重要**。
   若讓無翻譯者視覺上退居次要，等於用我方的能力缺口去評價機上事件的
   重要性，那是把限制偽裝成判斷。

   **(c) `dict_fw` 版本比對旗標——三態，各有不同呈現（2026-08-13 定案）。**
   `dict_fw` 本身顯示於 modal（列表不顯示，避免噪音）。比對旗標為
   `match` / `mismatch` / `unknown`（後端定義；因唯讀邊界不放行萬用指令
   載體，機上版本改由 command 服務落 DB，落地前**恆為 unknown**）。

   | 旗標 | 呈現位置 | 文案 | 色 |
   |---|---|---|---|
   | `match` | 不呈現 | — | — |
   | `mismatch` | **逐事件**（列 `⚠`＋modal 全句） | 版本不符，翻譯可能不準 | warn 黃 |
   | `unknown` | **每個視圖各一次**（見下） | 未能確認字典版本與機上韌體相符 | 次要文字色 |

   **`unknown` 的去重單位是「視圖」不是「頁面」**（2026-08-13 修正）：
   標記要出現在**使用者實際讀到那句翻譯的地方**，且在該視圖內只出現一次。
   - **清單視圖**（即時頁事件卡）→ 標頭一次。
   - **modal 視圖** → modal 內一次。modal 是 `position:fixed; inset:0` 全屏
     遮罩（45% 黑），**開啟時標頭那句被蓋住**——「面板層已標過」在此不成立。
   - **回放頁**（無事件清單，只有時間軸三角標）→ **不新增頁面層位置**，
     由 modal 內那次涵蓋。三角標開的是同一顆 EventModal，指涉完整。

   **判定範圍＝「帶 `dict_fw_match` 的事件」**：未經字典翻譯的事件
   （statustext、系統事件）**不參與全體判定**——否則事件流裡混進一筆
   系統訊息就會把面板態誤判成混合態，逐事件標記憑空出現。
   範圍亦隨來源篩選（全部／機上訊息／系統）連動：**判定的是使用者當下
   讀得到的那份清單**，與視圖去重同一條原則。

   **形狀分離**：mismatch 用 `⚠`＋warn 色，unknown 用 `?`＋次要文字色。
   兩者同列並排時，**形狀與顏色雙重可辨**（§0.1「顏色永不單獨傳達語意」），
   讀得出「這筆可能不準」與「這筆未確認」的差別。

   **不可重複標記**：標頭與逐事件標記由同一判定反向共用——`unknown`
   為全體時只出現在標頭，非全體時只出現在事件列，**結構上不可能兩者
   同時出現**。

   **混合態回歸逐事件**：當清單中 `unknown` **非全體**（版本路徑落地後，
   多機各自韌體不同即會發生：A 機 match、B 機 unknown），`unknown` 改為
   **逐事件標記**。理由是本條原始論證的反面——面板層去重的前提是
   **零區辨力**；一旦它能區辨哪幾筆未確認，全域一句反而**暗示全部未確認**，
   把局部缺口誇大成全體缺口。**逐項標記保留給逐項相異的性質**，這條在
   兩個方向上都要成立。

   **為何 unknown 現階段不逐事件標**：unknown 現階段**恆真**，逐事件標記等於
   在每一則上重複同一句話——**零區辨力的標記是純噪音，而噪音會訓練
   使用者忽略它**；等 mismatch 真正出現時，那個提示已經失去被看見的
   能力。**逐項標記應保留給逐項相異的性質**；unknown 是**系統狀態**
   （整個字典 vs 整台機的版本關係），標在面板層一次，**資訊量完全相同、
   噪音降為零**。版本路徑落地後出現 match/mismatch 混合時，逐事件標記
   自然只落在 mismatch 上，區辨力回復——**UI 屆時不需改動**。

   **為何 unknown 不用警告色**：unknown 不是異常，是**我方尚未具備的
   能力**；塗成警告色會讓使用者以為系統出了問題——那是另一種誤導。
   同 §0.2b 的形狀：**「不知道」不得冒充「有問題」**。兩句文案的主詞
   也刻意不同——unknown 說的是**我方未能確認**，mismatch 說的是
   **版本確實不符**。

   **為何不等 mismatch 出現才提示**：無法確認相符時就顯示翻譯而不聲明，
   等於**默認它正確**——unknown 不得被當成 match。此為 (c) 原始阻斷
   要求的完整應用（後端 2026-08-13 指出，成立）。

1. **內容依事件型別**：STATUSTEXT＝原句全文（不翻譯）；vehicle_event＝
   event_id＋args（hex）＋已知解譯（A.2 metadata 全文落地後同欄自動
   帶人話全文——**018 分層定案：列表＝摘要人話、modal＝細節層**）；
   系統事件＝detail 展開成鍵值表＋raw JSON 摺疊（誠實：加工顯示與
   原始並存，raw 不預設展開不嚇新手）。
2. **複製全文**：一鍵複製 plain-text 序列化（時間/機/來源/severity/
   型別/內容/raw）——除錯貼給別人用；複製後鈕短暫變「已複製」。
3. 開關：點事件列開（單一 modal，新點替換）；✕／Esc／點遮罩關。
4. 適用範圍：即時頁抽屜事件列表＋回放頁事件三角（點擊開同一 modal
   元件，取代現有 tooltip 的細節職責；tooltip 保留 hover 摘要）。
5. 列表 detail 若有截斷，modal 以單筆事件 API 取全文（後端側 PM 已

5. Phase 2/3（參數快照唯讀、ulog 回收）另案規格，不入本期。

### 2.6 IMU 卡（使用者核准 2026-08-11：專業數值改名 IMU、盡量全顯、
含高度三家安置——可實作）

#### 文字圖

#### 編排原則

1. **三軸一律純數字**（等寬對齊、x/y/z 弱字欄標、單位弱字）——迷你
   bar 需要發明滿刻度，對原始感測值是造假比例；數字才誠實。唯一例外
   **振動量條**：PX4 有權威門檻（30/60），有意義的刻度才畫圖形，
   條上標門檻線，超標段染 warn/danger 色＋clipping 三軸計數。
2. **缺欄不畫**（feature-detect 慣例，照 §0.2 空狀態原則）：後端契約
   給哪些欄畫哪些列，缺整列不佔位、不放「—」。
3. **非 IMU 項的安置（單一住所，資訊不消失）**：
   - 機型 chip（PX4）→ 任務控制面板**對象行**機名旁（身分歸身分）；
   - 就緒／模式 chips → 已在面板狀態列，抽屜重複**刪除**；
   - GPS → 已在面板狀態列（GPS 3·10顆），抽屜重複**刪除**；
   - 航向 → 併入姿態列 **Yaw（航向）**——航向本就是 yaw；
   - 垂直速度 → IMU 卡末「導航估計」列（括注來源語意，不冒充原始
     感測值——誠實原則）。
5. **選中機座標**（使用者指示 2026-08-12：簡約重整時被收掉、需要回來）：
   IMU 卡末「位置」列，**等寬字型、6 位小數、逗號分隔、點擊複製**
   （現場抄座標是真實場景，複製後短暫顯「已複製」）。**放這裡而非
   HUD**：座標是「查詢時才要」的精確值，非常駐掃視項（HUD 只放
   飛行中一眼要看的四項）。**與地圖右下的游標經緯度不衝突**——那是
   「你指的位置」，這是「機在的位置」，語意不同、兩者並存。
   無座標時**整列不畫**（feature-detect 慣例）。
   **相對高度在此列重複顯示**（HUD 已有）——例外理由：抄座標時通常
   連高度一起抄，兩個數字分處畫面兩端會抄錯；此處為「查詢用的完整
   位置」，與 HUD 的「掃視用高度」用途不同。

4. **高度的三個家**：相對高度＝HUD（常駐快讀）；
   海拔（alt_msl，原本無家）＝導航估計列；氣壓計原始值＋氣壓高度
   （契約有才畫）＝感測列。

- 取代現行圓點/球體的**俯視四旋翼剪影**：機身＋四臂四旋翼，**隨
  heading 旋轉**（heading 已有；缺值時**不旋轉並停用方向語意**——
  不畫一個永遠指北的假朝向）。
- **著機隊識別色**（§0.1 三槽＋灰），**文字標籤規則不變**（一律配
  機名、同位錯開）。
- **影像背景上的可辨性**：圖示加 1.5px 暗色描邊＋輕微陰影（僅圖示，
  不加在軌跡上——軌跡靠暗化 overlay 保對比）。
- **3D 球體換模型：不做**（PM 定案）——2D＋底圖先上線看效果再議。

#### 回放頁的機體表示（2026-08-12 裁定）

**回放頁改用同一套 2D 四旋翼圖示、隨 heading 旋轉**（與即時頁一致）。
關鍵事實：**回放 track 有 heading 且全程有值**（實測 117/117 筆、
0–360° 完整範圍）——「回放無朝向資料」的前提不成立，故「維持球體」
的理由（朝向用不上）隨之消失。

**規格層的語意區分**（本可成為維持球體的理由，但不適用）：即時頁圖示
＝「機現在在哪、朝哪」；回放頁圖示＝「**你拖到的這個時刻，機在哪、
朝哪**」——後者是時間游標，但它指向的仍是**當時真實的機體姿態**，
不是抽象位置標記。既然朝向是真實記錄的資料，就該畫出來：**能還原的
事實不因它是「回放」而降級呈現**。

**配套**：回放頁圖示需與軌跡在視覺上可分（游標比軌跡點大、加白色外圈
或同等強調），避免使用者把游標誤讀為「軌跡上的一個點」。

**底圖切換：回放頁一併支援**（與即時頁同一入口位置與三態），
理由同上——回放是研究判讀的主場景，空間定位需求不低於即時。

#### 三項實作裁定（2026-08-12）

1. **`billboard:false` 貼地平面——維持，不改 billboard:true。** 傾斜
   視角下造型被壓扁是代價，但 `billboard:true` 會讓**機頭方向不再對應
   地面方位＝朝向淪為裝飾**。**朝向是飛行語意，造型是美觀**——衝突時
   語意優先（同「顏色永不單獨傳達語意」的精神）。
   **緩解（非改 billboard）**：圖示尺寸隨俯角補償（pitch 越大、
   圖示短軸放大係數越高，抵銷透視壓縮），以「俯視時正常、傾斜時仍
   看得出四旋翼輪廓」為驗收標準；仍不足時加大整體尺寸而非改朝向語意。
2. **「此區無影像」第三態——保留**（前端補位、核可）。NLSC 僅涵蓋
   臺灣，境外回 200 但為空白磚——**若只有「底圖離線」一種說法，
   使用者在境外開底圖會看到「開了卻沒變化」而以為壞掉**。三態各自
   對應不同事實：`底圖：影像`（正常）／`底圖離線`（抓不到瓦片）／
   **`此區無影像`（服務不涵蓋此範圍）**。措辭定為「**此區無影像
   （圖資僅涵蓋臺灣）**」——說明為什麼，而非只說沒有。
3. **CVD 重驗的執行條件**：模擬場域在瑞士、無真實地物可取樣，
   **重驗須待臺灣場域實地或以台北座標取樣**。**在此之前底圖功能
   仍可上線**（預設關閉、opt-in），但**規格標注「影像背景之色盤對比
   未驗證」直到取樣完成**——不因未驗證而卡住功能，但也不假裝驗過。

當下的最上層**——**任何在它之後 `addLayer` 的 maplibre 圖層都會無聲

  ——測試時 plan source 是空的，所以沒撞到。**一條規則若只在特定
  資料狀態下成立，它給的是虛假的保障。**

  取得資料後 `setData`**。**症狀是「圖示不見了」，與新增的圖層看似

### 2.4d 3D 機體模型（**使用者核准 2026-08-13，可實作**：真 3D＋縮遠降級）

**起因**：使用者反饋「**2D 圖示角度一偏就以為機不見了**」——貼地平面的
圖示在低俯角下投影面積趨近零。**這是本節要解的唯一問題**，任何方案
若在某個視角下仍會消失，即為不合格。

#### 方案（使用者已選 (b)：真 3D 模型＋縮遠降級）

| 距離 | 呈現 | 理由 |
|---|---|---|
| **近**（縮放 ≥ 門檻） | **真 3D 四旋翼 mesh**：機身＋四臂四旋翼，有實體高度 | 任何視角都有投影面積，解「消失」問題；立體感讓姿態可讀 |
| **遠**（縮放 < 門檻） | **降級回 2D 圖示**（現行 `droneIcon.ts`） | 遠距時 mesh 只佔數像素、細節無意義且耗資源；圖示有最小像素保證 |
| 切換 | 門檻附近**淡入淡出**（不硬切），避免縮放時的跳動 | |

#### 硬約束（不得違反）

1. **離線可用——模型不得外部載入**。專案的離線場域約束照舊。
   `droneIcon.ts` 已有前例（**程序化產生 data URI、無外部依賴**），
   3D 模型**同樣採程序化建構 mesh**（圓柱機身＋四臂＋四旋翼盤，
   `SimpleMeshLayer` 餵自建 geometry），**不引入 glTF 檔或 CDN**。
2. **識別色照舊**（§0.1 三槽＋灰）：模型主體材質著識別色；**文字標籤
   規則完全不變**（一律配機名、同位錯開）——3D 化不得取代標籤。
3. **heading 缺值不假旋轉**（§2.4b 既有規則）：無 heading 時模型
   **維持固定朝向並移除機頭指示**，不得用預設值假裝知道朝向。
   ——注意 §2.4c #2 使用者已裁「**不要機頭箭頭**」，故 3D 模型
   **本體不加箭頭**；朝向由機身幾何自然呈現（有 heading 才旋轉）。
4. **永不被覆蓋**（§2.4c #3 硬規則）：模型與標籤仍在最上層；
   **注意 3D mesh 有深度**，需確認它不被軌跡的 3D 幾何遮蔽
   （必要時關閉該層深度測試或提高繪製順序）。
5. **最小可見尺寸**：模型在任何俯角下的螢幕投影**不得小於 2D 圖示的
   最小尺寸**——這是本節的驗收判準，**不是美觀問題而是功能問題**。

#### 驗收方法（明訂，避免重蹈今日的觀察錯誤）

以**像素量測**驗證，不憑目視：於**俯角 0°／30°／55°／75°**（75＝
三頁 `maxPitch` 實測值，**驗收角度以使用者實際可達的視角為準**——
驗一個到不了的角度沒有意義；原稿寫 80° 是我憑印象取整、未查證）與
**縮放門檻上下各一級**共 8 組條件截圖，量測機體像素面積；
**任一組低於 2D 圖示基準即不合格**。多機時同時驗識別色可辨與標籤未重疊。

### 4.4 每條航線的飛行約束（使用者 2026-08-13：從 .env 移到 plan 頁、
**逐 plan 動態設定**；待核准）

**資料模型變更（不只是搬位置）**：現況是全域三個常數
（`geofence_radius_m` 50／`geofence_alt_m` 15／`geofence_margin` 0.7），
**所有航線共用**。使用者要的是**每個 .plan 各自的約束**——這是
**一對多**：約束隨航線走、不同場域不同值。後端需 `missions` 加欄位＋
API，**全域值降為「新航線的預設起始值」**。

#### 使用者流程（重新設計）

```
路徑頁卡片 → ⋯ →「飛行約束」        ← 入口在卡片選單，不另設頁面
┌ 飛行約束 — complex-survey ──── ✕ ┐
│ 半徑上限   [  50 ] m              │ ← 預填目前生效值
│ 高度上限   [  15 ] m              │
│ 餘裕比例   [ 0.7 ]                │
│ ─────────────────────────────── │
│ ⚠ 此航線目前有 3 個航點超出新半徑  │ ← 即時預檢（改值當下就算）
│   （最遠 62m）                    │
│ 上次變更 8/13 14:02 · 50→40m ⊕全域 │ ← 含全域傳播（見下），⊕標來源
│              [取消]  [儲存並重檢] │ ← 危險操作：兩段式
└──────────────────────────────────┘
```

#### 規則

1. **入口在路徑頁卡片的 ⋯ 選單**（「飛行約束」）——**不新開頁面**：
   約束屬於航線，就住在航線旁邊（單一住所）。
2. **改值當下即時預檢**（不必等儲存）：顯示**這條航線有幾個航點會超出
   新值、最遠多少**——**讓後果在決定前可見，而不是儲存後才發現**。
3. **儲存採兩段式確認**（危險操作慣例）：按鈕文字「儲存並重檢」，
   點擊後變紅「確定？」。**理由：這是安全參數**，改鬆等於放寬飛行邊界。
4. **顯示目前生效值與最近一次修改**（時間＋新舊值）——**改過什麼要
   看得見**；完整歷程若後端有存，放 ⋯ 內不佔版面。
5. **既有航線的預檢結果會變**（使用者關切點）：儲存後**該航線的
   顯示中/預檢狀態立即重算**，並在卡片上標示「**約束已變更，預檢已重算**」
   直到使用者下次開啟該航線（一次性提示，不常駐）。
6. **未設定的航線沿用全域預設**，且**明示是預設值而非該航線自訂**
   （欄位旁弱字「使用預設」）——**分辨「沒設過」與「設成剛好等於預設」**
   是誠實原則的直接應用。

#### 資料契約（三方討論定案 2026-08-13，PM 主持）

- **Q1 既有航線遷移＝全部 null**（不填入當前全域值）——填值會把
  「從未設定」偽裝成「設過且剛好等於預設」，正是本設計要分辨的。
- **Q3 null 的語意＝跟隨現行預設（動態），非凍結建立時的值**——
  「沿用」的本義。**因此改動全域預設會傳播到所有 null 航線**，
  **UI 必須警示（見下）**。
- **Q2 修改紀錄＝append-only 留痕表**（後端定案）：
  `geofence_changes(time, scope['global'|'mission'], mission_id, client,
  old_value, new_value, **affected_mission_ids**)`。兩項補強：
  **全域預設的改動也留痕**（scope=global，影響面最大者不可不記）；
  **改動當下快照影響範圍**（事後重算得到的是今天的 N、不是當時的 N）。

#### 「上次變更」的顯示範圍（UI 裁量，2026-08-13）

**涵蓋兩種來源，且必須標明是哪一種**：

| 來源 | 顯示 |
|---|---|
| 本航線設定 | `8/13 14:02 · 半徑 50→40m` |
| 全域預設傳播（當時 affected 含本航線） | `8/13 14:02 · 半徑 50→40m ⊕全域` |

**為什麼要涵蓋全域**（採 PM 直覺）：對操作者而言「**我的航線邊界變了**」
不分來源；只顯示 mission-scope 會**漏掉最大宗的變因**——使用者會看到
預檢結果變了卻找不到任何修改紀錄，那比不顯示更糟。

**為什麼必須標來源**：兩者的**可回復性不同**——本航線的改動改回來只
影響自己；全域傳播來的，改回本航線值等於**脫離「沿用」變成明示設定**，
語意變了。**不標來源，使用者會用錯誤的心智模型去修正它。**

**排序**：兩種來源混合後**按時間取最近一次**（不分來源優先）——
因為使用者要問的是「上一次變成現在這樣是什麼時候」。完整歷程（含
兩種來源、可展開 affected 清單）放 ⋯ 選單，不佔卡片版面。
- 欄位：`missions.fence_radius_m` / `fence_alt_m` / `fence_margin`
  （nullable）；`PATCH /api/missions/{id}/fence`；預檢 API 改讀該航線值。
- schema 變更**同批更新 `doc/data-schema.md`**（既有慣例）。

#### 全域預設變更的傳播警示（Q3 定案的 UI 義務）

全域預設將從 `.env` 搬進系統設定（與本案是同一件事的兩層）。
**修改全域預設時必須警示傳播範圍**：

```
┌ 系統設定 · 飛行約束預設 ──────── ✕ ┐
│ 半徑上限  [ 50 ] → [ 40 ] m        │
│ ⚠ 此變更將影響 7 條使用預設的航線   │ ← 數量必顯
│   ▸ 查看清單                       │ ← 展開列出哪 7 條（可點進該航線）
│   其中 2 條的航點將超出新半徑 ▸     │ ← 後果預檢，非只列名單
│            [取消]  [變更並重檢]    │ ← 兩段式（安全參數）
└───────────────────────────────────┘
```

**設計理由**：null 的傳播是刻意的（「沿用」就該跟隨），但**傳播必須是
知情的**——使用者改一個數字可能同時放寬多條航線的飛行邊界。
**只顯示數量不夠，要能看見是哪幾條、以及哪幾條會因此超界**——
**後果在決定前可見**，與 §4.4 逐航線改值時的即時預檢同一原則。

### 5.4 回放影片同步（022 重點——使用者核准 2026-08-12，可實作）

```
┌ 回放頁 ─────────────────────────────┐
│（全幅地圖＋軌跡）      ┌影片 PiP────┐ │
│                      │ ●sim-uav-1 │ │ ← 窗角識別色點＋機名
│                      │  [影像]    │ │
│                      │▁▂▁色帶▄▅▂▁│ │ ← 底緣 3px SINR 同步色帶
│                      └───────────┘ │
│ ▶ ──█████──░░──█████────── ▲38m   │ ← 時間軸＋影像涵蓋帶
│      ↑有影像   ↑缺口  ↑有影像        │
└─────────────────────────────────────┘
```

- **雙向同步**：拖時間軸／點圖表 → 影片 seek 至對應段內時刻（依每段
  絕對時間錨點）；影片播放 → 時間軸游標＋地圖球體＋圖表 crosshair
  跟走；播放速度選項同步影片倍速。
- **時鐘源硬約束（前端 2026-08-12 提出的風險，列入驗收）**：段錨點
  `started_at` 必須與遙測時戳**同一時鐘源**（皆為 backend/DB 的 UTC）。
  若錨點取自錄製容器本地鐘，兩者的時鐘偏移會讓整段影片與資料**恆定
  偏移**——畫面看起來會播、但對照到的 SINR 是別的時刻的，**這種錯誤
  比明顯故障更危險**（研究結論會被靜默污染）。驗收必測：以可辨識瞬間
  （起飛離地／訊號劣化段畫面變糊）比對影片時刻與遙測事件時刻，偏移
  須 < 1s；若系統性偏移，屬阻斷級。**模擬環境實測已過**（後端
  2026-08-12：三容器共用核心時鐘，段結尾 vs 收錄指令 −0.192s≈0；
  段起始的 +1.371s 是等關鍵影格、不造成錨點錯誤）。

- **⚠️ 管線延遲：與研究變數相關的偏移（真機階段必測，不可只測一次）**
  `started_at` 的語意是「**影格抵達地面站的時刻**」，不是「**相機拍下
  的時刻**」，兩者差一個管線延遲（編碼＋傳輸＋抖動緩衝）。
  **模擬環境基線實測 0.41s（方向恆定：定位到 T 會看到 T+0.41s）**
  ——非時鐘錯配、亦非等關鍵影格（後端 GOP 1s vs 4s 對照實驗：
  +1.6s vs +1.55s，與 GOP 無關，故「等第一個 I-frame」的假設被推翻），
  屬錄製器「開始錄」與「第一幀落地」之間的固定管線延遲。
  **現階段不做補償**：硬編 0.41s 在真相機上必錯（編碼器/GOP/網路皆異），
  正解（讀第一幀時戳蓋錨）需 backend 具備媒體探測能力、屬架構改動。
  **改為明確記載基線**，真機階段量增量；**真 5G 上此延遲會隨鏈路劣化而變大——而鏈路劣化正是
  本專案的研究自變數**。因此它不是可事後校正的固定偏移，而是**與被
  研究變數相關的偏移**：畫面愈糊的時刻時戳愈晚，「畫質劣化 vs SINR」
  的對應會被系統性往後拖；且它在好鏈路時完全正常，最難察覺。
  - **UI 誠實義務**：影片窗與回放頁的說明處標示「影片時間＝抵達地面站
    時刻，與拍攝時刻差一個傳輸延遲」；**不假裝精準**。
  - **真機驗收方法（升級版）**：以畫面可辨識瞬間比對遙測事件，
    **分別在好鏈路與劣化鏈路各測一次**——若兩者偏移不同，即證實延遲
    與鏈路相關，須在 UI 標示不確定範圍，並評估 Phase 3 機端時碼
    （RTCP sender report NTP 對映或機上燒時碼）。
- **尾段 3 秒是刻意保留、不得裁切**（後端 `on_session_end` 在 disarmed
  後 sleep 3s 才收錄，避免切掉落地那一刻——那通常最該看）。實測影片
  比遙測晚收 +3.7~3.8s（3s 常數＋PATCH 往返＋flush）。**UI 處置**：
  涵蓋帶照實畫到影片實際結束（不對齊遙測結尾、不裁切）；影片時間軸
  超出遙測範圍的尾段，資料側游標停在最後一筆遙測即可（**不外插假資料**）。
  若後端輸出 `tail_pad_s`，回放頁說明處可標「落地後多錄 N 秒」——
  但**預設不特別解釋**（多錄不是異常，簡約優先）。
- **`final` 旗標：未結算的尾端不得斷言為缺口**（後端 2026-08-12 新增）。
  片段長度在落地後才收斂（暫時值→最終值），`final=false` 期間該段尾端
  的「還沒算完」與「真的沒錄到」在資料上**無法區分**。UI 規則：
  - `final=false` 的段，**尾端不畫涵蓋帶缺口、不顯「此時段無影像
    （錄製中斷）」**；scrub 進該區間顯示中性句「**影像處理中**」
    （非空態句、非故障句——它既不是沒錄到也不是壞掉，就是還沒算完）。
  - **涵蓋帶的第三種視覺**（前端補位、核可）：未定案尾端**留白＝讀作
    缺口（斷言沒錄到）、實心＝謊稱有影像**，兩者皆錯——故用
    **半透明條紋延伸至軸末**，與實心帶明顯可辨，語意＝「這段還不知道」。
    三態視覺與三種語意一一對應，不共用。
  - **必要配套：`final=false` 時 5 秒輪詢直到定案**（前端補位、核可）。
    無輪詢則「定案後重畫」永不發生——使用者不重整就永遠停在未定案
    視覺，規則等於失效。**規則本身若依賴某個狀態變化，就必須指定
    它如何被觀察到**，此為規格漏寫，已補。
  - 收斂為 `final=true` 後，該段依實際長度重畫涵蓋帶；此時若仍有缺口
    才是真缺口，才可顯「錄製中斷」。
  - **理由**：把「還在結算」說成「錄製中斷」＝把正常說成故障，與
    `missing`/`off` 不得混用同一原則。
  - **設計取捨紀錄**：UI/UX 原建議「未定案前不回該段」被後端否決且
    否決正確——不回傳會讓 `video_status` 算成 `missing`（整趟被說成
    錄製失敗），從「少給」變成「說謊」，比原問題更糟。**`final` 旗標
    是把判斷所需的事實給 UI，而不是要 UI 猜**，這是正解。
- **影像涵蓋帶**：時間軸上 3px 薄帶標示有影像的時段——fmp4 分段
  ＝帶分段，**段間空白就是真空白**（與後端「不得靜默拼接」硬約束成對）。
- **五種錄影狀態**：API 欄位為 **`video_status`**（後端算好；DB 內部欄位
  `video_mode` 只有 on/off/no_source 三值、**不外露**——它不知道「過期」
  與「該錄卻沒錄到」，那兩態需架次時間×保留天數推導，故一律後端算，
  **UI 不做日期運算**）。回放 API 形狀：
  `{retention_days, video_status, segments[{id, started_at, duration_s, url, …}]}`。
  五態**嚴格分句、不得混用**：

  | 狀態 | UI 呈現 |
  |---|---|
  | `available` | 播放器＋涵蓋帶。**有缺口不是空態**：帶上照實留白，scrub 進缺口才顯「此時段無影像（錄製中斷）」——「錄了但斷流」與「沒錄」意義相反，永不同句 |
  | `off`（刻意未錄） | 影片窗不顯示；header 弱字「本趟未錄影」；架次表同標 |
  | `no_source`（這台無影像來源） | 影片窗不顯示、不提示（沒有就不畫） |
  | `expired`（過保留期已清除） | 「影像已過保留期（{retention_days} 天），已清除」＋不顯涵蓋帶。天數動態帶入——後端已把它接上單一事實源（`.env` 一個變數同時餵清檔器與 API），UI 顯示不可能與實際清檔行為不一致 |
  | `missing`（**保留期內該錄卻整趟無流＝故障**） | **不用空態句**——空態句會把故障說成正常。走告警樣式：影片窗位置顯 warn 底卡「應有影像但未錄到（錄製故障）」＋事件流留 warn 事件，與 §2.9 的錄製異常 toast 同語言 |

- **畫質＝證據原件**：影片不轉碼原樣播放（後端定案互引）；SINR 色帶
  是**播放器 UI 疊層，絕不燒進影片檔**。畫面劣化與色帶對照＝研究證據。
- **多機 v1**：影片跟架次走（回放頁本為單架次頁），單窗；群飛多窗
  並排留待真實需求（明示界線，不預建）。
- 機隊頁架次表：opt-out 架次加弱字「未錄影」標記（有錄的不標——
  正常不宣告）。

## 6b. 前後比較頁（/compare/ab）——023 相同路徑前後任務訊號比較

### 6b.0 與既有頁的關係（盤點）

**⚠️ 入口缺失（使用者 2026-08-13 反饋：「比較頁面沒辦法看熱圖與前後對比」）**：
導覽列第四個 icon 指向 `/compare`（場域訊號頁），而 `/compare/ab`
**沒有任何 UI 入口**——只能直接輸入網址。**使用者心目中的「比較頁」
就是導覽列那顆 icon**，所以他點進去看到累積軌跡、找不到熱圖與前後對比，
結論是「這頁沒有那些功能」。**這是我的資訊架構失誤**：我把兩個不同
用途的頁面放在同一個入口位置，卻只給其中一個入口。

**定案（待核准）**：場域訊號頁**頂部加一列檢視切換**
`[ 場域訊號 ｜ 前後比較 ]`——兩者共用導覽列同一顆 icon（它們同屬
「回頭看資料」的情境），切換即換頁；前後比較頁同樣有此列可切回。
**理由**：不新增導覽 icon（§1 四 icon 已定），也不靠使用者記網址；
**同一入口下的兩個檢視，用檢視切換而非隱藏連結**。

**入口設計判準（前端 2026-08-13 提出，採為通則）**：
> **使用者為了到這個功能，需要先知道什麼？需要先知道的越多，
> 那個入口就越接近不存在。**

本案失誤即為實例：原設計「從軌跡卡進入」需要三層前置知識
（軌跡可點→點了有卡→卡裡有連結），**規格寫了、程式做了、雙方都可
宣稱完成，但使用者到不了**——這比「忘記做入口」更難發現。

**新開一頁，不改場域訊號頁（§6 v4）。** 兩者回答的問題不同：
v4＝「這個場域哪裡弱」（多趟累積、無基準）；本頁＝「**這條路徑，
改善措施前後差多少**」（兩趟對照、有前後之分）。使用者曾明確否決
「比較頁塞圖表」，故本頁**不是 v4 的回退**，而是有明確研究任務的
分析頁；入口從 v4 的軌跡卡或路徑頁使用紀錄「比對回放」進入。

### 6b.2 三張圖的規則

**① 沿路徑訊號（主圖）**
- X 軸＝**路徑弧長（里程 m）**，非時間——兩趟速度不同，時間對齊會錯位。
- 兩條線＝識別色前二槽（前 `#3987e5` 藍／後 `#d95926` 橘，CVD 實測
  ΔE 26.8 protan／31.8 normal，通過）；**差值帶**＝兩線之間填色，
  後優於前填藍向、劣於前填橘向（同兩色，不引入第三色）。
- 原始淡線＋平滑線並存（既有誠實規則），窗長標示於卡頭。
- **單一 y 軸**（dataviz 硬規則：絕不雙軸）。RSRP 對照見下。

**② 摘要表（取代 CDF——使用者 2026-08-12 二次否決該圖）**
- 分佈資訊**以數字呈現、不畫圖**：均值／p50／**p5**／Δ／樣本數。
- **p5 仍是重點欄位**（加粗）：尾部惡化比平均更有研究意義——平均掉
  2dB 無感、最差時刻掉 10dB 就斷鏈。**資訊保留，只是不用一張圖來載。**
- 決策紀錄：CDF 曾於 §6 v3→v4 被否決，本案再次提出並附「情境不同＋
  p5 用途」論證，使用者仍選「主圖＋熱區就夠」。**明著問而非偷渡，
  結果否決但決策乾淨**——同類情形照此辦理。

**③ 差值熱區（全寬）**
- 網格 ΔSINR（後−前），**發散色盤：兩極＋灰中點**（dataviz 硬規則，

- **兩趟都有樣本的格才上色**；只有一趟有樣本＝斜線紋理標「無對照」；
  兩趟都無＝不畫（誠實原則，與 v4 一致）。
- 格 hover：前/後各自的值與樣本數、Δ。

### 6b.3 RSRP 對照的呈現（方法論入 UI）

**規則：RSRP 持平＋SINR 降＝符合外部雜訊升高的特徵；RSRP 也降＝
變因在訊號強度側（距離／遮蔽／發射端）。**

**⚠️ 語意中性化（使用者 2026-08-13 定案）**：全站移除「干擾區」等
**先驗標注**——**機只知道訊號變差，不知道原因**；系統若標定「這裡是
干擾區」，等於把推測當事實、會導致誤判。**資料驅動的呈現不動**
（弱訊號區、分級色、熱區圖都是量測結果）；動的是**斷言原因的字眼**。
判讀句因此改用**現象描述而非成因結論**：「符合外部雜訊升高的特徵」
——它陳述的是可觀測的物理關係（RSRP 持平而 SINR 降），**把「是不是
干擾」留給研究者判斷**。
不要求使用者記這條規則，UI 直接呈現：

- **不做雙軸**（絕對禁止）。改為主圖下方一條**極簡 RSRP 迷你帶**
  （sparkline 高度 ~24px，同 X 軸對齊，僅畫前後兩趟的差值走勢）。
- **一句自動判讀**放在主圖卡頭 `ⓘ`：依整段中位數判定——
  「RSRP 大致持平而 SINR 下降 → **符合外部雜訊升高的特徵**」／
  「RSRP 同步下降 → **變因在訊號強度側**（距離、遮蔽或發射端）」／「兩者皆持平 →
  **無顯著變化**」。
- **判讀句必須可反駁**：句尾附依據數值（ΔRSRP 中位數 x.x dB、
  ΔSINR 中位數 y.y dB），使用者能自行檢查系統的結論。**系統給判讀，
  但不隱藏依據**——這是自動判讀不變成黑箱的唯一方式。
- **局部變化分支（2026-08-12 補；原規格缺陷）**：僅以「整段中位數」
  判定會在**變化集中於局部區段**時說出「無顯著變化」，而同頁摘要表
  的 Δp5 卻顯示明顯改善——**兩者各自正確卻互相打臉，使用者不知信誰**。
  規則：**逐段差值中位數持平，但 |Δp5| ≥ 3 dB **或** |ΔP50| ≥ 3 dB 時**，
  改判「整段差值持平，但（最差 5%／整體中位數）改善/惡化 X.X dB →
  變化集中在局部區段」，並提示看主圖差值帶找區段。
  **⚠️ 兩個「中位數」不是同一個東西（2026-08-13 實例）**：判讀句用
  **逐段差值的中位數** `median(後ᵢ−前ᵢ)`，摘要表用**各自中位數之差**
  `median(後)−median(前)`。**兩者可以同時正確卻相差 15.8 dB**——當
  差異集中在部分里程時（前趟早降、後趟晚降），逐段差值中位數為 0、
  整體中位數差卻很大。原規則只看 Δp5，遇上「兩趟都觸底所以 Δp5=0」
  就漏判，畫面上出現「無顯著變化」與「Δ P50 +15.8」並列。
  **判讀句須標明統計量**（「逐段差值中位數」而非「ΔSINR 中位數」），
  避免與摘要表同名不同義。
  **為何 Δp5 這次沒攔到（值得記的一般教訓）**：兩趟最差都觸到 -15 dB
  （模擬下限），**尾部被地板夾住就失去鑑別力**——**任何會飽和的指標
  都不能當唯一守門條件**。故改為「**摘要表任一欄顯著即觸發**」：
  守門條件與呈現內容綁定，**日後摘要表增欄位時必須同步加進判斷**
  （此對應關係已在程式碼註解標明）。
  **這類 bug 的特徵**：兩個數字都正確，所以任何斷言檢查都抓不到——
  **只有把它們放在同一畫面上才會現形**。

  **空態必須由資料明說，不能靠「畫面上沒東西」表達**（2026-08-13）：
  熱區**渲染失敗**與**兩趟無共同格**在畫面上完全同形——都是一片空白。
  此時**失效會冒充誠實空態**，而誠實空態正是我們刻意設計的
  （§0.2b 同一族：不得互相冒充）。故熱區在 `cells` 為空時要有明說文字；
  若文字說有格而圖上無格，那是**渲染故障而非資料狀態**，兩者不可再共用
  同一個畫面外觀。
  實例（2026-08-13 實測）：切換架次後熱區整層消失，**摘要與判讀句照常
  顯示同一組數字**——使用者只會以為「這兩趟沒得比」，不會懷疑畫面壞了。
  **驗收啟示**：熱區的空白**不能當作通過條件**，必須用注入已知必有格的
  資料去量彩色像素，否則測到的「符合預期的空白」與故障無法區分。

  **推廣到所有「空態即合法」的呈現，排序依據不是實作難度，而是
  「那個空態宣告的『沒事』有多接近『安全』」**：
  1. **事件流「尚無事件」** — 最高。它宣告的是**沒有異常發生**，
     靜默失效會讓故障中的飛機看起來健康；**空事件流是最強的安心宣告，
     也因此是最危險的謊**。
  2. **分級軌跡（無 SINR 欄就不畫）** — 次之。宣告「沒有量到訊號」，
     誤導研究判讀，但不涉飛安。
  3. **就緒三態的灰空心** — 最低。它宣告的是**資料不足**，
     渲染失效恰好落在保守側，**失效方向本身是安全的**。
  凡失效會落在「比真實狀況更令人安心」那一側的，排前面。
  **通則：同頁的自動判讀與數字表若可能互相矛盾，判讀句必須涵蓋數字
  表能揭露的情況**——否則使用者面對兩個都對的矛盾說法，只能靠猜。
  判讀句的責任不是「說出一個對的結論」，是「說出一個**不會與同頁其他
  證據衝突**的結論」。

### 6b.4 誠實規則（沿用全站）

- **樣本數必附**（摘要表獨立一欄、熱區每格 hover）。
- **無共同里程區間＝不畫空圖**（前端補位、核可）：兩趟若無重疊里程，
  直接說明「這兩趟沒有共同的里程區間——可能其中一趟未沿此路徑飛行」
  ＋附兩趟樣本數與分箱寬度；重疊 < 3 格時提示「趨勢不足採信」。
- **分箱寬度依樣本密度自適應、實際值標於卡頭**（前端補位、核可）：
  稀疏架次用固定 10m 格會導致兩趟永不落同格——**那不是「沒有差異」
  而是格子太細**，會把方法產物誤報成研究結論。
- 兩趟樣本數差距過大時（>3×）於摘要表加註「樣本數差異大，比較僅供
  參考」——**不阻止比較，但不假裝對等**。
- 分級不插值、未量測不上色、CVD 驗證照舊。
