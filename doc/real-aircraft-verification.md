# 實體驗證清單（首飛前）

> **用途**：目前系統的能力宣告**幾乎全部只有 SITL 證據**。這份清單列出每一項
> 「在模擬器上驗過、但在真機上沒驗過」的東西，以及**不驗的話會怎樣**。
>
> 對象：要把這台機第一次飛起來的人。逐項打勾。
>
> 相關：[`deploy-checklist.md`](deploy-checklist.md)（部署前設定）、
> [`autonomous-flight-state-machine.md`](autonomous-flight-state-machine.md)（狀態機設計）。

---

## 0. 為什麼需要這份清單：證據強度的落差

| 項目 | 目前的證據 | 落差 |
|---|---|---|
| 任務執行（`mission_start`／`mission_fly`） | ArduPilot **4.0.3** SITL | 機上是 **4.7.0**，差 7 個 minor |
| 續飛（`MISSION_SET_CURRENT`） | 同上 | 同上 |
| 起飛序列、模式切換 | 4.0.3 SITL ＋ 2026-08-12 一次實飛 | 部分有真機證據 |
| 5G 訊號欄位對照 | **FM350 手冊**推導 | 機上是 **FM160**，同家族但非同型 |
| 板子 UID 的穩定性 | 單次讀取 | **跨重開機／韌體升級沒驗過** |
| 幾何圍欄值 | `.env` 未設 → 程式預設 **50m / 15m** | 那是**模擬環境**的值 |

**SITL 用的映像 `radarku/ardupilot-sitl` 已經五年。** 今天實測就出現過一次
版本相關的行為差異（指令 224 不支援），所以「SITL 過了」與「真機可用」之間
的距離是實際存在的，不是形式上的免責聲明。

## 1. 地面即可驗（機體上鎖，零風險）

這些不需要起飛，機體上鎖時就能做完。**建議全部先做完再談首飛。**

### 1.1 機端身分與版本

- [ ] `/api/live` 的 `flight_sw_version` 與 `board_uid` 有值
- [ ] **重開飛控電源後，`board_uid` 不變**
      → 沒驗過就不能拿它當機體識別（issues/038 刻意還沒加告警，就是在等這個）

### 1.2 續飛機制在 4.7.0 上成不成立

- [ ] 上傳一份任務到機上
- [ ] `POST /api/command/1/mission/goto {"index": 1}`
- [ ] 回應 `ok: true` 且 `mission_seq` 等於 `wire_seq`

**風險**：4.0.3 拒絕指令 224、接受訊息 41。**4.7.0 兩者的支援可能都不同。**
不驗就實作「飛行中改航線」，等於把未驗證的機制放進飛安路徑。

### 1.3 `home` 是否佔 seq 0

- [ ] 上傳 N 個航點，`mission/upload` 回應的 `wire_items` 是 **N+1**
- [ ] 執行任務時 `mission_seq` 從 **1** 起算

**風險**：`wire_seq` 換算若在 4.7.0 上不成立，**續飛會差一個航點且沒有錯誤訊息**。

### 1.4 預檢與失效鏈

- [ ] 遙控器開機並綁定後，`PreArm: Radio failsafe on` 消失
- [ ] `/api/live` 的 `ready` 轉為 `true`（需室外 GPS）
- [ ] 逐項核定機端 failsafe 參數（`FS_*`、`BATT_*`）——目前**沒有任何一項核定過**
      （issues/033）

### 1.5 訊號欄位對照

- [ ] 拿 **FM160** 的原廠手冊覆核 `AT+GTCCINFO?` 欄位序
      → 目前是用 FM350 手冊＋兩份實測資料互相印證推出來的
      （見 [`reference/fibocom-fm160/README.md`](../reference/fibocom-fm160/README.md)）

**風險**：`pci`／`cell_id`／`band` 填錯**不會報錯**，只會讓干擾分析得到
看似合理的錯誤答案。

## 2. 需要起飛才能驗（**依序**，前一項沒過不做下一項）

> **每一項都要有人在遙控器旁邊、能隨時接管。**
> 場地圍欄值先依實際場地重設——`.env` 現在是模擬用的 50m/15m。

- [ ] **2.1 解鎖與起飛**：`mission/fly` 到 15m 並停住，讀回高度與模式
- [ ] **2.2 單點任務**：兩個航點的短航線，確認能進 AUTO 並飛完
- [ ] **2.3 中止**：飛行中下 `mode/hold` → **讀回機端真的進 hold**
- [ ] **2.4 返航**：`mode/rtl` → 確認自主返航並降落上鎖
- [ ] **2.5 續飛**：飛行中 `mission/goto` 跳到另一個索引 → **確認機體真的改道**
- [ ] **2.6 飛行中改航線**：上傳新航線 → 觀察是否如 SITL 那樣**立即改道**
      （issues/039 的核心危害，真機上要親眼確認）
- [ ] **2.7 地面站失聯**：切斷 5G（或擋掉 UDP）→ 確認代理在 30 秒後下 RTL
      **這一項尤其重要**：它是唯一「地面站看不到、只能靠機上」的防線

## 4. 紀錄方式

每一項驗完**寫下當時的韌體版本與日期**，不要只打勾。今天的教訓：

> `data/conformance/*.json` 原本宣稱記錄韌體版本，但那個欄位**根本不存在**，
> 於是「對某版驗過」這句話說不出後半段。補上之後才發現 ArduPilot SITL 是
> 4.0.3——而那個差距**改變了一個設計結論**。

**沒有版本的驗證紀錄，等於沒有驗證紀錄。**
