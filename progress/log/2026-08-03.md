## 首次實飛紀錄

環境：Docker 29.7.1、TimescaleDB `:35432`、PX4 SITL（iris/empty world）、
backend `:38000`、mavsdk 3.17.2。航線：蘇黎世起飛點 → 爬升 50m →
飛向 `sim-jammer-A` 中心 (47.3995, 8.5456) → 停留約 60s → RTL。

架次結果（`flight_sessions.summary` 自動計算）：

```json
{ "max_alt_rel": 49.9, "avg_sinr": 1.18, "min_sinr": -15.0,
  "avg_rtt_ms": 103.96, "samples_in_zone": 69, "samples_total": 165 }
```

**運作正常的部分**：MAVSDK 連線與六路遙測訂閱、armed→disarmed 自動切分架次
（2分47秒，落地後自動關閉並算出摘要）、1Hz 雙表入庫、WebSocket 實測 5.3 Hz、
干擾模型（進區前 SINR 10–12dB／RTT 35–50ms／丟包 0%，區內 SINR -15dB／RTT 200ms+／
丟包 72%）、mode_change 事件。

**踩到的環境地雷**：[#005](../../issues/005-sitl-mavlink-target-ip.md)——SITL 映像用
「預設閘道」當 MAVLink 目標，那是為 bridge 網路設計的假設；本專案用
`network_mode: host`，閘道變成區網 router，封包全飛到 192.168.137.1。
症狀是 backend 一切正常但永遠收不到遙測、且不報錯，靠 tcpdump 才定位。
已在 `docker-compose.yml` 用 `command: ["127.0.0.1", "127.0.0.1"]` 修掉。

**實測確認的既有問題**：[#001](../../issues/001-link-lost-event-never-fires.md)

## QGroundControl 整合調研

確認實務上校正與任務規劃都會用 QGC，做了資料蒐集 + SITL 實測，
產出 [doc/qgc-integration.md](../../doc/qgc-integration.md)。

實測方式：兩個 MAVSDK 連線分飾兩角（QGC 在 14550、backend 在 14540），
用新建的 `missions/interference-survey.plan` 走完上傳 → 擷取 → 執行 → 追進度。

| 驗證項目 | 結果 |
|---|---|
| `import_qgroundcontrol_mission()` 解析 `.plan` | ✅ 5 個 item 正確 |
| backend 從另一條 link 取得 QGC 上傳的任務 | ✅ 座標無誤 |
| `mission_changed()` 通知旁觀 link | ❌ 15 秒未觸發，不能當偵測訊號 |
| 輪詢 `download_mission()` 成本 | ✅ 8–13 ms，可每 5 秒輪詢 |
| 執行中追蹤 `mission_progress()` | ✅ 0/5 → 4/5 全程收到 |

**設計結論**：任務變更用輪詢 + 內容指紋比對；執行進度直接訂閱事件。
分工原則是「QGC 操作飛機、本系統記錄研究」。

**roadmap 3 改寫**：原本要自己做規劃 UI，確定用 QGC 後那是重造輪子，
且會有「兩邊都能規劃、以誰為準」的問題。改為被動擷取 QGC 上傳的任務 +
把計畫航線疊在實際軌跡上——對研究更有用（可看偏離航線處鏈路是否較差），
工作量也小得多。

順帶發現：QGC 校正動輒數十分鐘且全程 disarmed，讓
[#004](../../issues/004-writes-while-disarmed.md)（未 armed 仍持續入庫）
從「之後再說」變成需要優先決定。
